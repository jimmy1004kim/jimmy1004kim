## 이 문서는

프로젝트 또는 일정 구간(스프린트·Phase)을 마무리하면서 **"무엇이 잘 됐고, 무엇이 안 됐고, 다음에 어떻게 바꿀 것인가"** 를 정리하는 문서.

회고의 진짜 목적은 **"잘했다 못했다 평가"가 아니라 "다음에 어떻게 바꿀 것인가"**. Action Item 없는 회고는 그냥 감상문이다.

기획자 포트폴리오 관점에서는 **가장 가치 있는 문서**. "이 사람은 자기 일을 비판적으로 본다"는 증거가 됨.

## 언제 만드나

| 시점                      | 주기                                        |
| ----------------------- | ----------------------------------------- |
| **스프린트 회고**             | 1~2주마다 (애자일 방식 쓸 때)                       |
| **Phase 회고**            | 각 Phase 종료 시 (Discovery, Design, Build 등) |
| **프로젝트 종료 회고**          | 프로젝트 끝날 때 (필수)                            |
| **사건 회고 (Post-mortem)** | 큰 장애·실패 직후 (별도 템플릿 있음)                    |
|                         |                                           |

이 문서는 **정기 회고 + 프로젝트 종료 회고** 를 다룬다. 사후 분석(Post-mortem)은 별도.

## 어떤 툴로

|툴|추천도|이유|
|---|---|---|
|**노션**|⭐ 추천|회고 누적·검색·연결 모두 강점. 다른 산출물과 링크 자유|
|Miro / FigJam|추천|팀 회고에서 포스트잇 방식으로 진행할 때|
|구글 독스|보조|외부 공유·코멘트 협업|

**팁**: 노션에 "회고" DB를 만들고 회고할 때마다 페이지로 추가하면 시간순 누적 관리 좋음.

## 회고 프레임워크 (4가지 선택지)

상황에 따라 골라 쓰면 된다.

### KPT — 가장 흔함, 처음 쓰기 좋음

|구분|의미|
|---|---|
|**K** (Keep)|잘된 점, 계속 유지할 것|
|**P** (Problem)|문제점, 개선이 필요한 것|
|**T** (Try)|다음에 시도할 것 (Action Item)|

### 4Ls — 감정·학습까지 포함

|구분|의미|
|---|---|
|**Liked**|좋았던 것|
|**Learned**|배운 것|
|**Lacked**|부족했던 것|
|**Longed for**|있었으면 했던 것|

### Start / Stop / Continue — 가장 단순

|구분|의미|
|---|---|
|**Start**|새로 시작할 것|
|**Stop**|멈출 것|
|**Continue**|계속할 것|

### 5 Whys — 특정 실패의 근본 원인 찾기

문제 하나에 대해 "왜?"를 5번 반복하여 근본 원인 도달.

**추천**: 처음엔 **KPT**, 익숙해지면 상황에 맞게 다른 것 사용.

## 들어가야 할 것

- 회고 메타정보 (대상 기간, 참여자, 작성자)
- 진행한 일 요약 (무엇을 했는가)
- 회고 본문 (선택한 프레임워크 기준)
- 핵심 인사이트 (가장 중요한 깨달음 3~5개)
- 액션 아이템 (다음에 적용할 것)

## 작성 절차

1. **대상 기간 정함** — 어느 구간을 돌아볼지
2. **개인적으로 먼저 작성** — 팀 회고면 각자 적어옴
3. **함께 공유·정제** — 팀 회고면 같이 정리
4. **액션 아이템 도출** — 막연한 다짐 ❌, 실행 가능한 항목 ⭕
5. **차기 회고 때 점검** — 지난 액션 아이템 실행 여부 확인

|참여자|홍길동 (단독)|

# 📌 예시 2 — 프로젝트 종료 회고

> 가상의 외주 발주 프로젝트 사례 (예시용)

## 프로젝트 메타

|항목|내용|
|---|---|
|프로젝트명|사내 인사 시스템 구축 (외주)|
|기간|2026-05-01 ~ 2026-09-15 (약 4.5개월)|
|기획 유형|유형 4 (내부 시스템) + 유형 2 (외주/구축, 발주측)|
|참여자|김기획, 박PM, 외주사 B사|
|회고 작성일|2026-09-20|
|작성자|김기획|

## 1. 프로젝트 개요 요약

- **목적**: 수기 엑셀로 관리되던 사내 인사 정보를 통합 시스템으로 전환
- **범위**: 직원 정보, 휴가 신청, 조직도 관리
- **결과**: B사 납품 완료, 9월 1일부터 사내 운영 시작

## 2. 성과

### 정량 성과

|지표|목표|결과|달성률|
|---|---|---|---|
|휴가 신청 처리 시간|평균 1일 → 1시간|30분|200%|
|직원 정보 조회 시간|5분 → 30초|20초|150%|
|일정 준수|9/15 완료|9/15 완료|100%|
|예산 준수|1억 이내|9,800만원|102%|

### 정성 성과

- 인사팀 만족도 높음 (체감 업무 시간 50% 감소)
- 외주사와의 협업 관계 양호 → 향후 다른 프로젝트 협력 가능성

## 3. 잘된 점

- RFP 작성에 시간을 충분히 들여 모호함 최소화 → 외주사 견적 편차 적었음
- 변경 관리 대장으로 Change Order 깔끔하게 처리 (총 5건, 모두 비용·일정 반영)
- 외주사 PM과 주간 회의 정기 진행 → 이슈 조기 발견
- 검수 기준서를 계약에 첨부 → 검수 단계 분쟁 없음

## 4. 아쉬운 점

- 사용자(인사팀) 인터뷰가 초기 1회로 끝남 → 중간에 요구 변경 다수 발생 (CR-002, CR-004)
- 외주사 선정 평가에서 "유지보수 체계"를 5점 척도로만 평가 → 정성 평가가 모호했음
- 운영 인계 준비를 너무 늦게 시작 (납품 1주 전) → 인계 기간 부족

## 5. 배운 점

- **RFP의 모호함은 비용으로 돌아온다** — 처음에 시간 들여 명확하게 쓰는 게 가장 싸다
- **외주 프로젝트의 핵심은 변경 관리** — 변경 관리 대장 없이 외주 진행 불가능
- **사용자 인터뷰는 한 번이 아니다** — 설계 전, 설계 후, 검수 전 최소 3번
- **운영 인계는 개발 일정에 포함되어야** — 별도 항목으로 잡지 않으면 늘 뒤로 밀림

## 6. 다음 프로젝트에 적용할 것

|#|적용할 것|비고|
|---|---|---|
|1|RFP 평가 기준을 정량 지표 중심으로 재구성|다음 외주 발주 시|
|2|사용자 인터뷰를 Phase별로 의무화 (Discovery·Design·Test)|모든 프로젝트|
|3|운영 인계를 WBS의 별도 Phase로 분리 (1~2주 확보)|모든 구축 프로젝트|
|4|RFP 작성 가이드를 공통 템플릿으로 정리|자산화|

## 7. 자산화 항목

|#|산출물|이동할 위치|
|---|---|---|
|1|RFP 작성 가이드|공통 템플릿|
|2|외주사 평가 매트릭스 양식|유형 2(외주/구축) 템플릿|
|3|Change Order 절차서|공통 템플릿|
|4|검수 기준서 양식|유형 2(외주/구축) 템플릿|
|5|운영 인계서 양식|공통 템플릿|

## 작성 팁

- **혼자 하는 회고도 가치 있음** — 1인 프로젝트라도 반드시. 포트폴리오 자산의 핵심
- **솔직하게** — "다 잘됐어요"는 회고가 아님. 안 된 것을 인정해야 다음이 있음
- **액션 아이템은 구체적으로** — "더 잘 하겠습니다" ❌, "RFP 평가 기준을 정량화한다" ⭕
- **차기 회고에서 점검** — 지난 액션 아이템 실행 여부를 다음 회고 첫 항목으로
- **자산화 섹션 챙기기** — 회고에서 발견한 좋은 산출물·기법을 템플릿으로 빼두는 게 노하우 축적의 핵심
- **감정도 인정** — 4Ls 같은 프레임워크에서 "좋았던 것" "있었으면 했던 것"은 감정·동기 영역. 무시하면 다음 동기 부여 안 됨

## 자주 하는 실수

- **회고를 평가로 착각** — 잘잘못 따지면 솔직한 의견 안 나옴. "다음에 어떻게"가 목적
- **Action Item 없음** — Keep/Problem만 적고 끝. 회고 의미 없음
- **너무 길게 씀** — A4 1~2장이 적정. 길면 안 봄
- **이전 회고 안 봄** — 같은 문제가 매번 반복되는데 인지 못 함
- **자산화 누락** — 좋은 산출물·기법을 그냥 프로젝트 안에 묻어둠 → 다음 프로젝트에서 또 처음부터
- **혼자 프로젝트라 안 함** — 가장 큰 손실. 1인 프로젝트일수록 회고가 유일한 학습 도구

## 작성 후 체크

- [ ] 잘된 점만 적고 끝나지 않았는가
- [ ] 액션 아이템에 담당자와 시점이 있는가
- [ ] 막연한 다짐이 아니라 구체적 행동으로 적혀 있는가
- [ ] 자산화할 산출물을 식별했는가 (프로젝트 종료 회고의 경우)
- [ ] 노션 회고 DB에 누적되었는가
