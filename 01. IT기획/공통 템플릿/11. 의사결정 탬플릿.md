## 이 문서는

프로젝트 진행 중 내린 **주요 의사결정과 그 근거**를 시간순으로 남기는 표.

"우리는 왜 X 대신 Y를 골랐는가?" 에 대한 답을 6개월 후의 본인 또는 새로 합류한 사람이 읽고 이해할 수 있게 기록한다.

회의록·RAID와 헷갈리기 쉬운데 셋의 역할이 다르다.

|구분|회의록|RAID (D)|의사결정 기록 (ADR)|
|---|---|---|---|
|시점|회의 중|프로젝트 진행 중 누적|프로젝트 진행 중 누적|
|단위|회의 1건|1줄 요약 (대장 형식)|결정 1건당 1페이지|
|깊이|논의 흐름|결정 사실만|**배경·옵션·근거·결과까지**|
|추적성|그 회의만|전체 결정 한눈에|결정의 맥락 풍부|

**ADR (Architecture Decision Record)** 이 원래 이름. 개발팀의 아키텍처 결정 기록 관행에서 출발했지만, 기획·운영·조직 결정에도 동일하게 쓸 수 있다.

### 왜 RAID-D와 별도로 두나

RAID-D는 표 형식이라 한눈에 보기엔 좋지만, **"왜 그 결정이었는가"** 가 들어갈 공간이 없다. 시간이 지나면 결정 문장만 남고 맥락이 사라진다. ADR은 결정 하나에 1페이지를 할당해서 맥락을 보존한다.

**역할 분담**:

- RAID-D = 결정 인덱스 (한 줄 요약 + 링크)
- ADR = 결정 본문 (배경·옵션·근거·결과)

## 언제 만드나

- 되돌리기 어려운 결정을 내릴 때 (One-way door decision)
- 여러 선택지 중 하나를 고를 때 (트레이드오프 있는 결정)
- 나중에 "왜 그렇게 했지?" 질문이 예상되는 결정
- 외부 이해관계자가 영향받는 결정
- 기술 스택·도구·플랫폼 선택
- 조직·역할 변경
- 범위·일정·예산의 중요한 변경
- 정책·규칙 변경

**기준**: "6개월 후 본인이 다시 봤을 때 '왜 그랬더라' 싶을 것 같으면 기록한다."

### 만들지 않아도 되는 것

- 일상적·반복적 결정 (작은 UI 디테일 등)
- 명백히 한 가지 답뿐인 결정
- 임시·실험적 결정 (취소되어도 영향 없는)

## 어떤 툴로

|툴|추천도|이유|
|---|---|---|
|**노션 DB**|⭐ 추천|결정 인덱스 + 본문이 한 곳, 검색·필터·태깅 강함|
|GitHub `docs/adr/` 디렉토리|추천|개발팀 결정·코드와 함께 관리|
|Confluence|보조|회사 표준이라면|
|Google Docs|비추|검색·누적 관리 약함|

**팁**: 노션에 "의사결정 기록" DB를 만들고 결정 1건 = 1페이지 형식으로 누적. 속성으로 결정일·상태·영향 범위·관련 프로젝트를 두면 필터·검색이 강해진다.

## ADR 상태 (Lifecycle)

|상태|의미|
|---|---|
|🟡 **Proposed**|검토 중, 의견 수렴 단계|
|🟢 **Accepted**|결정·승인됨, 현재 유효|
|🔵 **Superseded**|새 결정으로 대체됨 (대체 ADR 링크 필수)|
|🔴 **Deprecated**|폐기됨 (사유 명시)|
|⚫ **Rejected**|검토했으나 채택 안 함 (이것도 기록 가치 있음)|

**중요**: 결정을 바꿀 때 원본 ADR을 수정하지 않는다. **새 ADR을 만들고, 원본의 상태를 "Superseded"로 변경하면서 새 ADR을 링크.** 결정의 변천이 추적되어야 학습이 된다.

## 들어가야 할 것

- ADR 메타 (번호·제목·상태·일자·작성자·결정자)
- 맥락 (Context) — 어떤 상황에서 이 결정이 필요했는가
- 옵션 (Options) — 검토한 선택지들과 각 장단점
- 결정 (Decision) — 무엇으로 결정했고 왜
- 결과 (Consequences) — 이 결정의 긍정적·부정적 영향
- 후속 액션 (Follow-up)

## 작성 절차

1. **결정 사안 식별** — 일상 결정인지 ADR 가치 있는 결정인지 판단
2. **ADR 번호 부여** — `ADR-001`, `ADR-002` 순서대로
3. **맥락 작성** — 왜 결정이 필요한지 배경부터
4. **옵션 나열** — 검토한 선택지 모두 (채택 안 한 것까지)
5. **결정·근거 작성** — 무엇을, 왜
6. **결과 예측** — 긍정·부정·트레이드오프
7. **상태: Proposed로 등록**
8. **의사결정자 승인 → Accepted로 변경**
9. **RAID-D에 한 줄 + 본 ADR 링크 추가**
10. **결정이 바뀌면 새 ADR 작성, 원본은 Superseded**

# 📌 예시 — ADR-003. Worker를 Railway에 배포한다

> 가상 사례. 샵플링 자동화 프로젝트의 인프라 선택 결정

## ADR 메타

|항목|내용|
|---|---|
|ADR 번호|ADR-003|
|제목|Worker(자동화 실행기)를 Railway에 배포한다|
|상태|🟢 Accepted|
|결정일|2026-05-28|
|작성자|홍길동 (PM)|
|의사결정자|본부장 + 김데브 (개발)|
|영향 범위|샵플링 자동화 시스템 전체, 운영 비용·장애 대응|
|관련 프로젝트|샵플링 음수재고 자동화|
|대체 / 피대체|—|

## 1. 맥락

- **상황**: 자동화 실행기(Worker)를 클라우드에 올려야 함. Playwright 기반이라 실행 시간이 길고(평균 3~5분), Vercel Free의 10초 제한으로는 불가능. 별도 환경 필요.
- **제약 조건**:
    - 예산: 월 5만원 이내 (1차 출시 시점)
    - 무료 티어 활용 가능하면 우선
    - 운영팀이 직접 다루지 않으므로 관리 부담 적어야
    - 영업시간만 실행되므로 24/7 가동 불필요
- **이 결정으로 풀려는 문제**: 어떤 인프라에 Worker를 배포할 것인가

## 2. 검토한 옵션

### 옵션 A. Railway

- **개요**: PaaS, GitHub 연동 배포, 컨테이너 기반
- **장점**:
    - 무료 티어 월 5달러 크레딧, 영업시간만 가동 시 충분
    - GitHub 푸시로 자동 배포
    - Playwright 컨테이너 이미지 공식 지원
    - 로그·메트릭 대시보드 내장
- **단점**:
    - 무료 티어 한계 도달 시 유료 전환 필요 (월 5달러부터)
    - 한국 리전 없음 (싱가포르 최단)
- **비용·리스크**: 무료 → 월 1~2만원 예상

### 옵션 B. Fly.io

- **개요**: 글로벌 분산 PaaS
- **장점**:
    - 무료 티어 더 관대 (3개 인스턴스)
    - 도쿄 리전 있음 (한국에서 가까움)
- **단점**:
    - 설정 복잡도 Railway보다 높음
    - 결제 카드 등록이 무료 티어에도 필수
    - Playwright 셋업이 약간 까다로움
- **비용·리스크**: 무료 → 월 1만원 예상

### 옵션 C. Render

- **개요**: PaaS, Heroku 대안으로 인기
- **장점**:
    - UI 직관적, 설정 쉬움
    - 무료 티어 있음 (단, 15분 미사용 시 슬립)
- **단점**:
    - 무료 티어 슬립으로 인해 첫 실행 시 콜드 스타트 (30초+)
    - Worker 용도(스케줄 실행)에는 부적합
- **비용·리스크**: 무료 → 슬립 회피 시 월 7달러부터

### 옵션 D. 사내 서버

- **개요**: 회사 사무실 PC 또는 서버에 배포
- **장점**:
    - 비용 0원
    - 데이터 외부 이동 없음 (보안 측면)
- **단점**:
    - PC 끄면 실행 안 됨 (안정성 X)
    - 관리 책임 모호 (누가 재부팅·업데이트?)
    - 외부 IP·도메인·SSL 구성 필요
- **비용·리스크**: 0원 → 운영 부담 큼

### 옵션 비교 매트릭스

|평가 기준|가중치|A. Railway|B. Fly.io|C. Render|D. 사내|
|---|---|---|---|---|---|
|초기 셋업 난이도|中|5|3|4|2|
|운영 부담|高|5|4|5|1|
|Worker 적합성|高|5|5|2|3|
|비용 (1년)|中|4 (~월1만)|5 (~월0.5만)|3 (~월2만)|5 (0원)|
|확장성|低|4|5|3|1|
|한국 응답 속도|低|3|5|3|5|
|**가중 합계**||**34.5**|**32**|**24.5**|**18**|

## 3. 결정

- **선택한 옵션**: **A. Railway**
- **결정 근거**:
    - Worker 용도에 가장 적합 (콜드 스타트 없음, 스케줄 실행 안정적)
    - 운영 부담이 가장 낮음 (운영팀이 다루지 않는 영역이므로 중요)
    - Playwright 컨테이너 공식 지원 → 셋업 시간 절감
    - 비용 차이는 Fly.io 대비 월 5천원 수준 — 운영 부담 차이가 더 큼
- **반대 의견 / 우려 사항**:
    - 김데브: Fly.io의 한국 응답 속도가 더 빠른 점은 아쉬움 → 그러나 샵플링 응답 속도가 병목이라 영향 미미하다고 합의
    - 본부장: 비용 증가 가능성 우려 → 월 사용량 모니터링 + 임계치 알람 설정으로 합의

## 4. 결과

### 긍정적 영향

- Worker 셋업 시간 단축 (예상 1주 → 3일)
- GitHub 연동으로 배포 자동화 가능
- 운영 부담 최소화

### 부정적 영향 / 트레이드오프

- 한국 리전 없어 지연 약간 발생 (수십 ms, 무시 가능)
- 무료 티어 한계 도달 시 유료 전환 필요 (예산 영향)
- 특정 PaaS 의존도 (마이그레이션 비용 발생 시 별도 비용)

### 알려진 리스크

- Railway 서비스 중단·정책 변경 시 마이그레이션 필요
- 무료 티어 정책 변경 가능성

## 작성 팁

- **결정의 가치는 "왜"에 있다** — "Railway로 결정함"만 적으면 6개월 후 본인도 모름. **검토한 옵션과 근거가 핵심**
- **반대 의견을 명시한다** — 100% 합의된 결정은 거의 없다. 반대 의견이 무엇이었는지 적어두면 나중에 그 우려가 현실화될 때 빠르게 대응 가능
- **결정 안 한 옵션도 가치 있음** — "왜 옵션 B를 안 골랐나"는 다음 비슷한 결정에서 중복 검토를 줄여줌
- **결정을 바꿀 때는 새 ADR** — 원본 수정 X, 새 ADR 작성 + 원본 Superseded. 결정의 변천 추적이 학습의 핵심
- **Rejected ADR도 기록 가치** — "검토했으나 채택 안 함"도 결정. 6개월 후 누가 같은 제안을 또 했을 때 "이미 검토했음"을 보여줄 수 있음
- **RAID-D와 양방향 링크** — RAID-D는 인덱스, ADR은 본문. 둘이 끊겨 있으면 추적 못 함
- **번호는 글로벌 유니크** — 프로젝트별 번호 X, 자산 전체에서 ADR-001부터 순차. 검색·참조가 쉬워짐
- **짧을수록 좋다** — 옵션 비교 매트릭스는 핵심만, 본문도 1~2페이지. 너무 길면 안 봄
- **결정의 영향 범위를 분명히** — "이 결정이 영향을 주는 시스템·팀"이 명시되어야 다음에 검색·필터링이 쉬움

## 자주 하는 실수

- **결정만 기록, 근거 누락** — "X로 결정함" 한 줄. 6개월 후 본인도 왜인지 모름
- **검토한 옵션 누락** — 채택한 옵션만 적고 다른 옵션을 적지 않음 → 같은 검토를 또 함
- **결정 바뀌면 원본 수정** — 변천 추적이 사라짐. 새 ADR + Superseded가 원칙
- **너무 작은 결정도 ADR** — ADR이 100개 넘어가면 검색 의미 없음. 일상 결정은 회의록에
- **너무 큰 결정 누락** — 정작 중요한 결정은 머리로 기억하고 ADR 안 만듦 → 이게 가장 비싼 실수
- **RAID-D만 있고 ADR 없음** — 한 줄 결정만 남고 맥락 사라짐
- **승인 없이 Accepted** — 의사결정자 명시·승인 없이 Accepted로 변경 → 나중에 "그건 누가 결정한 거?" 분쟁
- **재검토 조건 누락** — "지금은 이게 맞다"라는 결정이 영원히 유효한 것처럼 됨. 조건이 바뀌면 재검토 필요

## 작성 후 체크

- [ ] ADR 번호가 유니크하고 순차적인가
- [ ] 상태가 명시되어 있는가
- [ ] 맥락에 결정이 필요한 이유가 분명히 있는가
- [ ] 검토한 옵션이 최소 2개 이상 있는가
- [ ] 결정 근거가 옵션 비교에 기반해 있는가
- [ ] 반대 의견·우려 사항이 기록되었는가
- [ ] 결과(긍정·부정·리스크)가 균형 있게 적혔는가
- [ ] 후속 액션에 담당자·기한이 있는가
- [ ] 재검토 조건이 명시되었는가
- [ ] RAID-D에 한 줄 인덱스가 추가되었는가
- [ ] (상태 변경 시) 원본을 수정하지 않고 새 ADR로 처리했는가
