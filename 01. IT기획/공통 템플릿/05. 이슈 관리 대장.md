## 이 문서는

프로젝트 진행 중 발생한 **문제·장애·블로커**를 한곳에 모아 관리하는 표.

"이슈"는 **지금 실제로 발생한 문제**를 말한다. 아직 발생 안 한 잠재적 문제는 리스크(RAID)로 따로 관리.

이게 없으면 같은 문제가 반복되거나, 누군가가 막혀있는 걸 모르고 지나간다.

## 이슈 vs 리스크 vs 변경

헷갈리기 쉬워서 미리 구분.

| 구분      | 의미                   | 예시                        |
| ------- | -------------------- | ------------------------- |
| **이슈**  | 지금 발생한 문제            | "샵플링 로그인 실패함"             |
| **리스크** | 아직 안 발생했지만 발생 가능한 문제 | "샵플링 UI가 바뀌면 자동화 깨질 수 있음" |
| **변경**  | 의도적으로 바꾸는 결정         | "MVP 범위에 알림 기능 추가하기로 결정"  |

리스크가 실제로 발생하면 → 이슈로 전환됨.

## 언제 만드나

프로젝트 시작 시 빈 대장을 만들어두고, 진행 중 이슈가 발생할 때마다 즉시 추가.

작은 프로젝트면 회의록 안에 섹션으로 넣어도 되지만, **이슈가 5건 이상 누적되면 별도 대장 필수**.

## 어떤 툴로

|툴|추천도|이유|
|---|---|---|
|**노션 (DB)**|⭐ 추천|상태별 필터·정렬·뷰 자유로움. 한 이슈를 페이지로 열어 상세 기록 가능|
|Jira|추천|개발팀 같이 쓸 때 강력. 워크플로 자동화 우수|
|구글 시트|보조|간단할 때|
|GitHub Issues|보조|개발 중심 프로젝트면 자연스러움|

**팁**: 노션 DB로 만들고 상태별로 보드 뷰(칸반)로 시각화하면 한눈에 잘 들어옴.

## 들어가야 할 것

|항목|설명|
|---|---|
|ID|ISS-001 형태 일련번호|
|제목|한 줄로 무슨 이슈인지|
|발생일|발견된 날짜|
|발생자|이슈를 처음 찾아낸 사람|
|담당자|이슈를 해결할 사람|
|우선순위|긴급도 (P0~P3)|
|영향 범위|어디까지 영향 미치는지|
|상태|신규 / 진행 / 보류 / 해결 / 종료|
|상세 내용|무슨 상황인지|
|해결 방안|어떻게 풀 것인지 / 풀었는지|
|종료일|해결된 날짜|

## 우선순위 (Priority) 기준

|단계|의미|대응 시간|예시|
|---|---|---|---|
|**P0 (긴급)**|프로젝트 전체 중단·심각한 장애|즉시|운영 시스템 다운|
|**P1 (높음)**|핵심 기능 중단, 우회 불가|1일 이내|핵심 기능에서 데이터 누락|
|**P2 (보통)**|일부 기능 영향, 우회 가능|1주 이내|특정 화면 오작동|
|**P3 (낮음)**|사소한 문제, 일정에 영향 없음|시간 날 때|오타, 사소한 UI 어긋남|

## 상태값

```
신규 → 진행 → (필요시 보류) → 해결 → 종료
```

- **신규**: 등록만 됨, 아직 누가 안 봤음
- **진행**: 담당자가 처리 중
- **보류**: 정보 부족·외부 대기 등으로 멈춤 (사유 필수 기재)
- **해결**: 해결 완료, 검증 대기
- **종료**: 검증·확인 완료, 닫힘

## 작성 절차

1. **이슈 발견** → 즉시 대장에 신규 등록 (제목·발생자·발생일만 먼저)
2. **분류** → 우선순위·영향 범위·담당자 지정
3. **진행** → 상태 "진행"으로 변경, 상세 내용·해결 방안 채움
4. **해결** → 해결 후 상태 "해결"로, 종료일 기록
5. **검증** → 발생자가 확인 후 "종료"로 변경
6. **회고** → 프로젝트 종료 시 이슈 대장을 한 번 훑으며 패턴·교훈 정리

# 📌 예시 2 — 이슈 상세 페이지

> ISS-001을 노션 페이지로 열었을 때의 모습

**ID**: ISS-001 **제목**: Playwright 로그인 시 캡차 발생 **상태**: 진행 **우선순위**: P1 **담당**: 홍길동 **발생일**: 2026-06-25

### 상황

- Playwright로 샵플링 자동 로그인 시도 시 캡차 화면이 나타남
- 수동 로그인 시에는 캡차가 안 나오는데, 자동화 로그인은 매번 나옴
- 재현: 자동화 스크립트 실행 → 로그인 페이지 → ID/PW 입력 후 캡차 발생

### 영향

- 자동화 전체 동작 불가 (로그인 단계에서 막힘)
- 해결 안 되면 MVP 출시 일정 지연 (M3 목표 7/17 영향)

### 원인 분석

- User-Agent가 자동화 도구로 식별됨
- IP가 클라우드(Railway) 대역이라 의심 트래픽으로 분류 가능성

### 해결 방안

1. User-Agent를 일반 브라우저로 위장 → **1차 시도**
2. Playwright Stealth 모드 적용 → 2차 시도
3. 위 둘 다 실패 시 → 샵플링 측에 API 요청 또는 IP 화이트리스트 요청

### 진행 기록

- 06-25: 이슈 등록
- 06-26: User-Agent 변경 시도 → 캡차 여전히 발생
- 06-27: Playwright Stealth 적용 → 캡차 발생 빈도 50% 감소했으나 완전 해결 안 됨
- 06-28: 샵플링 측에 IP 화이트리스트 가능 여부 문의 (운영팀장 통해)

### 종료

- 검증자: -
- 재발 방지: (해결 후 작성)

## 작성 팁

- **이슈는 발견 즉시 등록** — "나중에 적어야지"는 거의 항상 누락됨
- **제목은 한 줄로 명확하게** — "안 됨" ❌, "로그인 시 캡차 발생" ⭕
- **우선순위는 정확히** — P0~P1을 남발하면 신뢰 잃음. 대부분 P2~P3
- **재현 절차 기록** — 다른 사람이 따라 할 수 있어야 해결 빠름
- **종료 시 재발 방지 한 줄** — 같은 이슈가 또 안 나오게 하는 가장 중요한 부분
- **노션 DB로 만들면** 상태별 보드 뷰, 우선순위별 정렬, 담당자별 필터 모두 가능

## 자주 하는 실수

- **이슈와 리스크 혼동** — 발생한 건 이슈, 안 발생한 건 리스크
- **모든 게 P0** — 다 긴급이면 아무것도 긴급 아님. 정확히 분류
- **담당자 미지정** — "다 같이" = "아무도 안 함". 한 명 지정 필수
- **진행 기록 안 남김** — 종료 후 "이거 어떻게 풀었지?"가 됨. 그때그때 기록
- **재발 방지 누락** — 같은 이슈를 두 번 만나면 그건 시스템 문제
- **종료 후 안 닫음** — 해결됐는데 "해결" 상태로 남아있으면 검증 안 된 것

## 작성 후 체크 (이슈 등록 시)

- [ ] 제목이 한 줄로 명확한가
- [ ] 발생자·담당자가 지정되어 있는가
- [ ] 우선순위가 합리적으로 매겨졌는가
- [ ] 재현 절차 또는 상황 설명이 충분한가

## 작성 후 체크 (이슈 종료 시)

- [ ] 해결 방안이 기록되었는가
- [ ] 검증자가 확인했는가
- [ ] 재발 방지 한 줄이 있는가
- [ ] 상태가 "종료"로 변경되었는가
