## 이 문서는

프로젝트 진행 중 발생하는 **범위·일정·산출물의 공식 변경 요청과 처리 결과를 기록하는 표**.

처음 합의한 내용이 그대로 끝나는 프로젝트는 없다. 반드시 도중에 "이거 추가해주세요", "이건 빼야겠어요", "일정을 늦춰야겠어요" 같은 요청이 들어온다. 이걸 그때그때 말로 처리하면 분쟁의 씨앗이 된다.

변경 관리 대장은 **"누가, 언제, 무엇을, 왜 바꿨는가"의 흔적**을 남긴다.

## RAID의 Decisions와 어떻게 다른가

헷갈리기 쉬워서 미리 구분.

|구분|의미|예시|
|---|---|---|
|**Decisions (RAID)**|프로젝트 진행 중의 모든 의사결정|"Worker는 Railway에 배포하기로"|
|**변경 관리 대장**|합의된 기준(Charter·계약·일정)을 **바꾸는** 변경|"MVP 범위에 알림 기능 추가"|

모든 변경은 결정이지만, 모든 결정이 변경은 아님. **합의된 기준선(Baseline)을 건드리는 것만 변경 관리 대상.**

## 언제 만드나

프로젝트 시작 시 빈 대장을 만들어두고, 변경 요청이 들어올 때마다 즉시 등록.

특히 **외주·수주 프로젝트에서 필수**. 계약 범위를 건드리는 변경은 비용·일정 영향이 직결되므로 기록 안 하면 분쟁.

자체 프로젝트도 Charter v1.0 합의 이후엔 변경 관리 대장이 필요.

## 어떤 툴로

|툴|추천도|이유|
|---|---|---|
|**노션 (DB)**|⭐ 추천|상태별 필터, 페이지로 상세 기록, 결정사항·이슈와 링크 자유로움|
|구글 시트|추천|간단할 때. 외주 프로젝트에서 고객과 공유하기 좋음|
|Jira|보조|개발 프로젝트에 자연스러움|

## 변경 유형 (5가지)

|유형|의미|예시|
|---|---|---|
|**범위** (Scope)|만들 기능·산출물의 추가·제거|"알림 기능 추가"|
|**일정** (Schedule)|마일스톤·종료일 변경|"M3을 2주 연장"|
|**산출물** (Deliverable)|결과물의 형태·품질 변경|"보고서 → PPT로 변경"|
|**비용** (Cost)|예산 증감|"유료 플랜으로 전환"|
|**기타** (Other)|위에 안 맞는 것|"사용 기술 변경"|

## 처리 흐름

```
요청 접수 → 영향 분석 → 승인 검토 → 결정 → (승인 시) 적용 → 결과 확인
```

|단계|핵심 작업|
|---|---|
|요청 접수|대장에 즉시 등록 (제목·요청자·날짜)|
|영향 분석|일정·비용·다른 산출물에 미치는 영향 정리|
|승인 검토|승인자(보통 PM·고객·운영자)에게 안건 올림|
|결정|승인 / 반려 / 보류 + 사유|
|적용|승인된 경우 실제 반영 (Charter·WBS 등 기준 문서 업데이트)|
|결과 확인|적용 결과를 대장에 기록|

## 결정 권한 (누가 승인하는가)

변경의 종류에 따라 승인자가 다르다. 미리 정해두는 게 좋음.

| 변경의 영향            | 승인자                        |
| ----------------- | -------------------------- |
| 일정 / 비용 영향 없음     | PM 단독                      |
| 일정 1주 이내 영향       | PM + 사용자 합의                |
| 일정 1주 초과 또는 비용 영향 | 프로젝트 오너 / 승인자              |
| 계약 범위 변경 (외주)     | 양사 공식 승인 (Change Order 절차) |

# 📌 예시 2 — 변경 요청 상세 페이지 (승인 케이스)

**ID**: CR-001 **제목**: 자동 검증 로직을 MVP에 포함 **요청일**: 2026-05-27 **요청자**: 박OO (운영팀 사용자) **변경 유형**: 범위 (Scope)

### 변경 내용

- (현재): MVP 범위에는 다운로드 → 가공 → 업로드만 포함되어 있음. 업로드 후 결과 검증은 사람이 수기로 확인.
- (변경 후): 업로드 직후 결과를 자동으로 검증하고, 실패 시 알림 표시하는 로직을 MVP에 포함.

### 변경 사유

- 사용자 인터뷰에서 박OO가 "업로드 후 결과 확인을 매번 수기로 해서 불안하다"고 강하게 의견 제시
- 자동 검증이 없으면 자동화의 신뢰가 떨어져서 결국 사람이 다시 확인하게 됨 → 자동화 효과 반감

### 영향 분석

- **일정 영향**: 개발 +2일 (Phase 2의 워크플로 엔진 작업에 포함)
- **비용 영향**: 없음
- **산출물 영향**:
    - 요구사항 정의서: 검증 로직 요구사항 추가
    - 화면설계서: 검증 결과 표시 영역 추가
    - 워크플로 정의서: 검증 단계 추가 (Step 5)
- **이해관계자 영향**: 사용자 만족도 ↑, 개발 일정 소폭 증가
- **리스크**: 일정 버퍼 20%로 흡수 가능

### 검토 의견

- 운영팀장: "사용자 신뢰가 핵심이니 포함 찬성"
- 홍길동: "구현 난이도 낮음, 일정 영향 작음. 동의"
- 다른 사용자(김OO, 이OO): "필요하다고 봄"

### 결정

- **결정**: 승인
- **결정일**: 2026-05-27
- **승인자**: 운영팀장 (최OO)
- **결정 사유**: 사용자 핵심 니즈, 일정 영향 작음, 구현 난이도 낮음

### 적용

- **적용일**: 2026-05-28
- **함께 갱신된 문서**: Charter v1.1, 요구사항 정의서 v0.3, WBS v1.1
- **적용 결과**: 워크플로 정의서에 Step 5(검증) 신규 추가, MVP 범위 명시

# 📌 예시 3 — 변경 요청 상세 페이지 (반려 케이스)

**ID**: CR-002 **제목**: Slack 알림 기능 MVP에 추가 **요청일**: 2026-06-15 **요청자**: 김OO (운영팀 사용자) **변경 유형**: 범위 (Scope)

### 변경 내용

- (현재): MVP에서 실행 결과는 대시보드에서만 확인 가능. Slack 알림 없음 (후속 범위로 명시됨)
- (변경 후): 워크플로 성공·실패 시 Slack 채널로 알림 발송

### 변경 사유

- 운영팀 일과 중 대시보드를 매번 들어가서 확인하기 번거로움
- Slack은 항상 켜져 있으니 알림이 즉시 보임

### 영향 분석

- **일정 영향**: 개발 +5일 (Slack API 연동, 알림 템플릿, 실패 알림 정책 설계)
- **비용 영향**: 없음 (Slack 무료 플랜으로 가능)
- **산출물 영향**:
    - 요구사항 정의서: 알림 요구사항 추가
    - 화면설계서: 알림 설정 화면 추가
    - 데이터 모델: 알림 설정 테이블 추가
- **이해관계자 영향**: 개발 일정 5일 증가 → M3(MVP 출시) 일정에 직접 영향
- **리스크**: 일정 버퍼 거의 소진. 다른 변경 들어오면 일정 폭발 가능

### 검토 의견

- 홍길동: "기능 자체는 가치 있지만 일정 영향이 큼. MVP 출시 후 추가하는 게 안전"
- 운영팀장: "MVP는 핵심에 집중하자. 알림은 곧 후속으로"
- 김OO: "꼭 MVP에 필요한 건 아니라면 이해함"

### 결정

- **결정**: 반려 (후속 범위로 이관)
- **결정일**: 2026-06-16
- **승인자**: 운영팀장 (최OO)
- **결정 사유**:
    - MVP 범위 관리 (이미 CR-001로 검증 로직 추가됨)
    - 일정 버퍼 소진 위험
    - MVP 출시 후 1차 개선 항목으로 이관 결정

### 적용

- **적용일**: -
- **함께 갱신된 문서**: Charter v1.2 (Future Scope에 "Slack 알림" 추가)
- **적용 결과**: MVP 출시 후 2주 내 추가 개발 예정 (별도 일정 잡음)

## 작성 팁

- **모든 변경 요청은 일단 등록** — 반려될 거라도 기록. 흔적이 남아야 회고에서 학습 가능
- **즉답 금지** — "그거 좋네요, 추가합시다"는 가장 위험한 말. 영향 분석 후 결정
- **영향 분석 빠뜨림 = 일정 폭발** — 일정·비용·다른 산출물·리스크까지 다 봐야
- **반려도 정중하게** — "MVP 범위 관리"라는 이유와 "후속으로 이관"이라는 대안 제시
- **승인되면 기준 문서 갱신** — Charter, WBS, 요구사항 정의서 등을 같이 업데이트하고 버전 올림
- **변경이 많아지면 의심** — 잦은 변경은 초기 분석 부족의 신호. 회고 때 점검

## 자주 하는 실수

- **말로만 합의하고 기록 안 함** — "그때 합의했잖아요"는 분쟁의 시작
- **영향 분석 없이 즉답 승인** — 일정·비용 폭발의 직접 원인
- **변경 후 기준 문서 갱신 누락** — Charter는 그대로인데 실제는 다른 상황 = 혼란
- **반려 사유 안 적음** — 나중에 같은 요청이 또 들어옴
- **외주 프로젝트에서 Change Order 절차 생략** — 비용 회수 불가
- **사소한 것까지 다 변경 관리** — 기준선 안 건드리는 작은 것은 결정사항(RAID-D)으로 충분

## 작성 후 체크 (변경 요청 등록 시)

- [ ] 변경 내용이 "현재 → 변경 후" 형태로 명확한가
- [ ] 영향 분석에 일정·비용·산출물·리스크가 모두 있는가
- [ ] 승인자가 명확히 지정되어 있는가

- [ ] 승인된 경우, 기준 문서(Charter, WBS 등)가 새 버전으로 업데이트되었는가
- [ ] 이해관계자에게 결정 결과가 공유되었는가
