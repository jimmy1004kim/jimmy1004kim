## 정의

프로젝트를 따내기 위해 사전에 수행하는 기획. 실제 구축이 일어나기 전 단계이며, **목적이 "수주"** 라는 점이 모든 다른 유형과 다르다. 만들기 위한 기획이 아니라, 일을 받아오기 위한 기획.

## 발생 상황

- 고객사로부터의 직접 문의·제안 요청
- 입찰 공고 / RFP 발행
- 파트너사와의 협업 제안
- 영업이 가져온 건에 대한 기술·기획 검토
- 기존 고객의 추가 사업 의뢰

## 업무 흐름

```
고객 접촉 → 요구 파악 → 제안 전략 수립 → 제안서·견적 작성 → 발표·설득 → 수주 여부 결정
```

|단계|핵심 작업|
|---|---|
|고객 접촉|영업 미팅 동행, 1차 정보 수집|
|요구 파악|RFP 정독, 행간 읽기, 고객사 배경 조사|
|제안 전략 수립|차별화 포인트(Win Theme) 결정|
|제안서·견적 작성|문서 구성·견적 산정·일정 추정|
|발표·설득|PT 진행, Q&A 대응|
|수주 여부 결정|수주 시 유형 2(구축)로 이관, 실주 시 회고|

## 기획자 역할

- **고객 요구의 빠른 이해·구조화** — 짧은 시간에 모호한 요구를 기능 단위로 정리
- **RFP 정독·해석** — 명시된 요구만이 아니라 "왜 이 요구를 했는가"를 읽어내는 능력
- **차별화 전략 수립** — "왜 우리여야 하는가"에 대한 한 문장 답
- **제안 범위 정의** — 무엇이 포함되고 무엇이 빠지는지 명확히 (수주 후 분쟁 예방)
- **제안서 기획·구성** — 문제 인식 → 해결 방안 → 기대 효과의 설득 흐름
- **견적·일정 산정** — 기능 단위 작업량 추정, 리소스 고려, 수익성 검토
- **리스크 식별** — 요구사항 모호성, 일정 빠듯함, 기술 난이도 등 사전 식별
- **고객 커뮤니케이션·발표** — 제안 설명, 피드백 반영, PT 발표
- **수주 후 인계 설계** — 실제 구축팀이 받아서 진행할 수 있도록 정보 정리

## 주요 산출물 (✅ = 필수)

### 사전 분석

- ✅ RFP 분석서 — 요구 해석, 핵심 키워드, 평가 기준 파악
- ⬜ 고객사 조사 자료 — 사업 현황, 의사결정 구조
- ⬜ 경쟁사 분석 — 누가 같이 입찰하는가, 강·약점

### 제안 본체

- ✅ 제안서 (Proposal) — 문제 → 해결 → 기대 효과
- ✅ 기능 리스트 / 범위 정의서
- ✅ 서비스 구조도 (간략 IA)
- ✅ 견적서
- ✅ 일정 계획 (Timeline)
- ✅ 발표 자료 (Pitch Deck)
- ⬜ User Flow 요약
- ⬜ 화면 컨셉 시안 (필요 시)
- ⬜ 기술 아키텍처 개요 (기술 제안 비중 높은 경우)

### 전략·관리 (내부용)

- ✅ 제안 전략서 (Win Theme)
- ⬜ 리스크 및 가정 정의서
- ⬜ 수익성 분석 (내부용)
- ⬜ 예상 Q&A 자료
- ⬜ 회의록 / 커뮤니케이션 로그

### 사후 (수주 결과와 무관)

- ⬜ 제안 회고 — 수주든 실주든 반드시 회고

## 특징

- **구축 없이 끝날 수 있음** — 실주하면 모든 산출물이 내부 자산으로만 남음
- **속도와 설득력이 핵심** — 완성도보다 결정을 유도하는 힘이 중요
- **정보가 제한적** — 고객사 내부 사정을 모르는 상태에서 추정해야 함
- **문서보다 사람** — 결국 평가위원·의사결정자를 설득하는 게임
- **수주 여부가 곧 다음 프로젝트** — 수주하면 유형 2로 매끄럽게 이관 필요

## 자주 빠지는 함정

- 고객 요구 대신 우리가 하고 싶은 것을 제안
- 차별화 메시지 없음 — "잘 하겠습니다" 반복
- 낙관적 견적 → 수주 후 적자 프로젝트
- RFP 평가 기준을 안 읽고 본인 강점만 강조 — 채점 못 받음
- 전문용어 남발 — 평가위원이 비전공자면 못 알아듣고 떨어짐
- 수주 후 인계 부재 — 제안팀과 구축팀의 정보 단절
