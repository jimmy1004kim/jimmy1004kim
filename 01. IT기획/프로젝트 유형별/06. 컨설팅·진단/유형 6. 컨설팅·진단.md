## 정의

만들지 않고, 분석하고 권고만 하는 일. 결과물은 **보고서**이며, 실행은 고객이 한다. 다른 유형과 결정적으로 다른 점은 "구현물이 없다"는 것. 그래서 분석의 깊이와 권고의 설득력이 가치의 전부다.

## 발생 상황

- 핵심 지표 저하의 원인을 내부에서 찾지 못할 때
- UX/UI 문제로 사용자 불만이 누적된 경우
- 외부 전문가의 객관적 진단이 필요할 때
- 리뉴얼·재구축 프로젝트 착수 전 사전 분석
- 신사업 진출 전 시장·역량 진단
- 디지털 전환(DX) 수준 평가

## 업무 흐름

```
범위·방법 합의 → 현황 파악 → 분석·인터뷰 → 문제 정의 → 개선 방향 수립 → 보고서 작성 → 보고·전달
```

|단계|핵심 작업|
|---|---|
|범위·방법 합의|무엇을 어디까지 진단할지, 어떤 프레임워크로|
|현황 파악|서비스·시스템·조직 구조 이해|
|분석·인터뷰|데이터 분석, 다양한 계층 인터뷰|
|문제 정의|핵심 문제와 우선순위 도출|
|개선 방향 수립|To-Be 방향, 실행 가능한 권고|
|보고서 작성|분석 → 인사이트 → 권고 흐름|
|보고·전달|경영진 보고, 후속 액션 합의|

## 기획자 역할

- **진단 범위 합의** — 어디부터 어디까지 볼지 명확히 (스코프 폭주 방지)
- **진단 프레임워크 선택** — 성숙도 모델·SWOT·5 Forces 등 객관성을 담보하는 도구
- **현황 파악** — 서비스 구조, IA, User Flow, 운영 방식 이해
- **데이터 분석** — KPI·사용자 행동 분석, 이탈·병목 지점 찾기
- **인터뷰 설계·진행** — 다양한 계층·부서 균형 있게 (편향 방지)
- **문제 정의·우선순위 설정** — 핵심 문제와 영향도 정리
- **To-Be 방향 수립** — 실행 가능한 권고. 이상론 아닌 실현 가능안
- **개념 수준 개선안 설계** — 화면·기능 컨셉까지 (상세 스펙은 후속 프로젝트의 몫)
- **보고서 작성·발표** — 경영진 언어로 핵심 전달
- **후속 프로젝트 연결** — 진단 결과가 구축·개선 프로젝트로 이어지도록 설계

## 주요 산출물 (✅ = 필수)

### 진단 설계

- ✅ 진단 계획서 — 범위·방법·일정
- ✅ 진단 프레임워크 정의서 — 어떤 기준으로 평가할 것인가
- ⬜ 인터뷰 대상자 리스트
- ⬜ 데이터 수집 계획

### 진단 수행

- ✅ 인터뷰 가이드
- ✅ 인터뷰 결과 정리
- ✅ AS-IS 분석 리포트 — 서비스·시스템·운영 구조
- ✅ 데이터 분석 리포트
- ⬜ 설문 결과 분석
- ⬜ 벤치마킹 / Best Practice 비교

### 결과 보고

- ✅ 문제 정의서 — 핵심 문제·원인
- ✅ 인사이트 도출 문서
- ✅ 개선 방향 정의서 (To-Be)
- ✅ 최종 보고서 — 분석·인사이트·권고 통합
- ✅ 경영진 요약본 (Executive Summary) — 1~3페이지
- ✅ 발표 자료 (Presentation Deck)
- ⬜ 구조 개선안 (IA 컨셉)
- ⬜ User Flow 개선안
- ⬜ UX/UI 개선 컨셉 (Wireframe)
- ⬜ 우선순위 정의 / 로드맵 제안
- ⬜ 예상 효과·ROI 추정

## 특징

- **구현이 없다** — 결과물은 문서·발표·인사이트
- **분석의 깊이가 가치** — 표면 분석으로는 돈 안 됨
- **객관성과 설득력이 핵심** — 정치적 압력에도 흔들리지 않아야
- **단기 프로젝트가 많음** — 보통 4~12주
- **후속 프로젝트의 시작점** — 컨설팅이 곧 다음 구축의 입구가 됨
- **권고의 실행 가능성이 평가 기준** — "디지털 전환이 필요합니다" 수준은 무가치

## 자주 빠지는 함정

- 프레임워크 없는 인상비평
- 인터뷰 대상 편향 — 특정 부서·계층만 만나서 그림이 왜곡
- 권고가 일반론 — "디지털 전환", "데이터 기반 의사결정" 같은 추상어
- 실행 가능성 검토 부재 — 좋은 말이지만 우리 회사에선 못 함
- 정치적 압력에 휘둘려 객관성 상실
- 보고서가 두꺼울수록 좋다는 착각 — 경영진은 요약본만 봄
