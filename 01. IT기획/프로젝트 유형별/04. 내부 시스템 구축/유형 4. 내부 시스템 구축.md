## 정의

사내 직원이 사용하는 도구·시스템을 만드는 일. 외부 사용자가 아니라 **우리 회사 직원이 사용자**라는 점이 결정적 특징이다. 멋진 디자인보다 매일 끊김 없이 도는 안정성이 우선이고, "쓰기 좋다"는 정성평가보다 "시간이 얼마나 줄었나"라는 정량 평가가 더 중요하다.

## 발생 상황

- 수작업·엑셀 관리의 한계 도달 (실수·중복·누락)
- 같은 일을 여러 사람이 따로따로 하고 있음
- 반복 업무가 늘어나 자동화 필요
- 데이터가 부서별로 흩어져서 통합 관리 필요
- 외주 솔루션으로 풀기엔 우리 업무가 특수함

## 업무 흐름

```
요구 수집 → AS-IS 업무 분석 → TO-BE 설계 → 시스템 설계 → 개발 → 적용·교육 → 운영·개선
```

|단계|핵심 작업|
|---|---|
|요구 수집|실무자 인터뷰, 페인 포인트 파악|
|AS-IS 분석|현재 업무 흐름·시간·휴먼 에러 정량화|
|TO-BE 설계|자동화 후 흐름·역할 재정의·예상 효과 산정|
|시스템 설계|메뉴·기능·데이터·권한 명세화|
|개발|단계적 출시 가능하면 그렇게|
|적용·교육|실무자 교육, 사용 매뉴얼 배포, 안정화|
|운영·개선|실 사용 피드백 반영, 효율 개선 지속|

## 기획자 역할

- **업무 분석 (AS-IS)** — 현장에 직접 가서 보고, 실무자 인터뷰. 외부 사용자 인터뷰보다 만나기 쉽지만 그래서 오히려 소홀하기 쉬움
- **문제 정량화** — "월 30시간 수작업"처럼 숫자로 환산. 예산 정당화의 근거
- **TO-BE 설계** — 자동화 후 업무 흐름과 담당자 역할이 어떻게 바뀌는지 그림
- **요구사항 정리** — 실무자 요구를 기능 단위로 구조화
- **시스템 구조 설계** — 메뉴·관리자 구조·User Flow
- **상세 스펙 설계** — 기능·화면·정책·데이터·상태 흐름·권한
- **권한 설계** — 누가 뭘 볼 수 있고, 뭘 수정·승인할 수 있는지. 사내 시스템에서 자주 놓치는 영역
- **자동화 로직 설계** — 조건 기반 처리, 스케줄링, 알림
- **개발 협업·일정 관리**
- **실무 기반 QA** — 실제 업무 시나리오로 검증
- **변화 관리·교육** — 새 시스템 도입은 곧 일하는 방식 변경. 저항을 다루는 능력 필요
- **운영·개선 사이클 운영** — 도입 후 6개월이 진짜 시작

## 주요 산출물 (✅ = 필수)

### 분석·전략

- ✅ AS-IS 업무 분석서 — 현재 흐름·시간·문제
- ✅ TO-BE 설계서 — 개선 후 흐름·역할
- ✅ 요구사항 정의서
- ⬜ ROI 분석서 — 정량적 효과 (예산 정당화 필요 시 필수)
- ⬜ 이해관계자 분석 / RACI
- ⬜ 사용자 인터뷰 가이드·결과

### 구조·상세 설계

- ✅ IA (메뉴·관리자 구조)
- ✅ 업무 흐름도 (Process Flow)
- ✅ 기능 정의서 (업무 처리 단위)
- ✅ 화면 정의서 (Admin Screen Spec)
- ✅ 정책 정의서 (Business Rule)
- ✅ 데이터 정의서 (Data Spec)
- ✅ 권한 정의 (Role & Permission)
- ⬜ 상태 흐름도 (State Flow) — 결재·승인 흐름 있는 경우
- ⬜ 자동화 로직 정의서 — 스케줄·조건 처리
- ⬜ API / 연동 정의서
- ⬜ 보안 설계서

### 실행·관리

- ✅ 일정 계획
- ⬜ 개발 백로그 / 우선순위 리스트

### 검증·전환

- ✅ QA 체크리스트 / 테스트 시나리오 — 실 업무 시나리오 기반
- ✅ 운영 매뉴얼 / 사용자 가이드
- ✅ 변화 관리 계획 — 도입 시 담당자 역할 재정의 포함
- ⬜ 사용자 교육 자료
- ⬜ 운영 인계서
- ⬜ 개선 요청 백로그

## 특징

- **사용자가 동료** — 거리감이 가까운 만큼 불만도 직접적
- **효율·정확성이 핵심** — 멋보다 안 끊김
- **업무 프로세스 이해가 가장 중요** — 도메인 지식 없으면 헛다리
- **관리자·운영 기능 비중이 큼** — 화려한 사용자 UI보다 권한·승인·로그가 더 중요
- **도입이 곧 성공은 아님** — 만들어도 안 쓰면 실패
- **숫자로 효과를 증명할 수 있어야** — 다음 자동화 프로젝트의 추진력이 됨

## 자주 빠지는 함정

- 실무자 인터뷰 생략 — "어차피 사내 직원이니까"
- ROI 정량화 없이 추진 → "이거 왜 만들었냐"는 질문에 답 못 함
- 운영 인계 누락 — 만든 사람만 아는 시스템
- 기존 업무 흐름 무시 → 도입했는데 안 씀
- 권한·보안 설계 미흡 — "사내니까" 안일하게
- 변화 관리 부재 — 자동화 후 담당자 역할 재정의가 없어서 저항 발생
