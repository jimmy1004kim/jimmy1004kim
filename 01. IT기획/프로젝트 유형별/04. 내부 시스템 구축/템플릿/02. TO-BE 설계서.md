## 이 문서는

AS-IS 분석을 바탕으로 **앞으로 (To-Be) 업무·시스템이 어떤 모습이어야 하는지를 정의한 청사진**.

T4 산출물 흐름에서의 위치:

```
[T4-1 AS-IS] → [T4-2 TO-BE] → [T4-3 요구사항] → [T4-4 ROI] → [T4-6 기능]
       ↓             ↓                ↓               ↓
  "현재 어떻게"  "앞으로 어떻게"   "무엇을 만들까"  "투자 가치 있나"
```

다른 산출물과의 비교:

|구분|T4-1 AS-IS|**T4-2 TO-BE**|T4-3 요구사항|T4-6 기능 정의|
|---|---|---|---|---|
|시점|현재|**미래 (1~3년)**|미래 (요구)|미래 (구현)|
|깊이|사실·관찰|**비전·청사진**|무엇을 만들까|어떻게 만들까|
|청중|운영팀·BA|**의사결정자·전체 팀**|개발·설계|개발·QA|
|변경|변경 불가 (현실)|**변경 가능** (목표·전략)|명세|구현|

**핵심**: TO-BE는 "이상적 미래"가 아니라 **"의사결정자가 동의한 실행 가능한 미래"**. AS-IS 페인 포인트와 1:1 연결되어야 함.

### TO-BE 설계의 5가지 책임

1. **AS-IS 페인 포인트와 1:1 연결** — 모든 TO-BE 항목은 AS-IS 문제를 해결
2. **시스템 청사진** — 어떤 시스템·모듈·인터페이스
3. **새 업무 프로세스 정의** — TO-BE에서 사람·시스템이 무엇을 하나
4. **변화 영향 식별** — 누가·무엇이 바뀌는가
5. **단계적 로드맵** — Phase 1·2·3 — 한 번에 다 안 함

### TO-BE의 3가지 깊이

|깊이|의미|적용|
|---|---|---|
|**Level 1. 비전·목표**|무엇을 달성하나 (정성·정량)|의사결정자 합의|
|**Level 2. 시스템 아키텍처**|어떤 시스템·모듈·연동|기술 설계|
|**Level 3. 새 업무 프로세스**|TO-BE에서 사람·시스템이 무엇을|운영 설계|

### TO-BE 설계의 4가지 함정

|함정|증상|대응|
|---|---|---|
|**유토피아**|"AI로 모든 걸 자동화" 같은 추상|구체적 시스템·기능 단위|
|**AS-IS 무관**|페인 포인트와 연결 없음|1:1 매핑 표 필수|
|**빅뱅**|한 번에 전체 전환|단계적 로드맵 (Phase 1·2·3)|
|**사용자 무관**|운영팀 참여 없이 PM·BA 단독 설계|운영팀 워크숍·검토|

본 가이드는 4가지 함정 모두 회피하는 절차.

### 단계적 전환의 원칙 (3가지 옵션)

|전환 방식|의미|적용|
|---|---|---|
|**Big Bang (빅뱅)**|한 번에 전체 전환|작은 시스템·간단한 변경|
|**Phased (단계적)**|Phase별 점진 전환|**내부 시스템 권장** ⭐|
|**Parallel (병행)**|신·구 시스템 동시 운영|미션 크리티컬 시스템|

T4 (내부 시스템) 는 **Phased + 부분 Parallel** 조합 권장.

## 언제 만드나

- AS-IS 분석 완료 후 (T4-1 발효 직후)
- 요구사항 정의 (T4-3) 작성 전

**기준**: AS-IS의 페인 포인트를 알고 있고, 미래 청사진 합의 필요한 시점.
