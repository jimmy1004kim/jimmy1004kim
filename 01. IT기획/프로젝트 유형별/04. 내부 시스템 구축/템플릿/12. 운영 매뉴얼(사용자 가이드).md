# T4-12. 운영 매뉴얼 / 사용자 가이드 (Operation Manual & User Guide)

## 이 문서는

내부 시스템을 **운영팀이 실제로 사용할 수 있도록 작성한 가이드 + 시스템 운영자가 시스템을 운영할 수 있도록 작성한 매뉴얼**.

T4 산출물 흐름에서의 위치:

```
[T4-6 기능] + [T4-7 화면] + [T4-11 자동화 로직] → [T4-12 매뉴얼·가이드] → 사용자·운영자
```

### 매뉴얼 vs 가이드 — 2종 문서

|구분|**사용자 가이드 (User Guide)**|**운영 매뉴얼 (Operation Manual)**|
|---|---|---|
|대상|운영팀 8명 (MD·재고·정산·CS)|시스템 운영자 (신규 1명·CTO 팀)|
|강조|**"내 업무를 어떻게 시스템으로 하는가"**|**"시스템을 어떻게 운영·트러블슈팅하는가"**|
|내용|UI 사용법·업무 절차·예외 케이스|모니터링·장애 대응·외부 API·로그 분석|
|형식|스크린샷·step-by-step·시나리오|명령어·아키텍처·트러블슈팅 트리|
|학습 시간|4~8시간|16~40시간|

본 가이드는 **2종 문서 모두** 다룸.

### 왜 매뉴얼·가이드가 핵심인가

내부 시스템에서 가장 흔한 실패:

- **"시스템은 잘 만들었는데 안 씀"** — 운영팀이 이해 못 함·반발
- **"베테랑 떠나면 운영 못 함"** — 매뉴얼 없음
- **"외부 API 변경 대응 못 함"** — 시스템 운영자 매뉴얼 부실
- **"교육 후 다 잊음"** — 참고할 문서 없음

매뉴얼·가이드가 위 4가지 모두 해결.

### 사용자 가이드의 5대 원칙

|원칙|의미|
|---|---|
|**업무 시나리오 중심**|"버튼 X 누름" 이 아니라 "주문 처리 절차"|
|**스크린샷 풍부**|화면 캡처·강조 표시|
|**단계별 (Step-by-Step)**|1·2·3 순서 명확|
|**예외 케이스 포함**|"이럴 땐 어떻게?"|
|**검색 가능**|노션·검색 인덱스|

### 운영 매뉴얼의 5대 원칙

|원칙|의미|
|---|---|
|**트러블슈팅 트리**|"이 증상 → 이 원인 → 이 해결"|
|**명령어·코드 정확**|복사·붙여넣기 가능|
|**아키텍처 이해**|시스템 전체 구조|
|**장애 대응 절차**|시간 SLA·에스컬레이션|
|**변경 이력**|변경 사항·근거 추적|

### 매뉴얼·가이드 작성의 4가지 함정

|함정|증상|대응|
|---|---|---|
|**개발자 관점 작성**|기술 용어 가득|운영팀 관점·일상 언어|
|**장황한 설명**|1단계당 1페이지|핵심 + 스크린샷 + 짧은 설명|
|**갱신 안 함**|v1.0 그대로·시스템 변경 미반영|변경 시 매뉴얼 갱신 의무화|
|**사용 테스트 안 함**|"잘 작동한다" 가정|실제 신규 직원으로 사용성 검증|

## 언제 만드나

- **사용자 가이드**: 운영팀 교육 1~2주 전
- **운영 매뉴얼**: 시스템 운영 인계 1개월 전
- 시스템 변경 시 동시 갱신
- 분기 정기 점검 시

### 6. FAQ

**Q1**: OpsHub에서 일이 자동으로 처리되는데, 내가 뭘 해야 하나요? **A**: 자동화가 처리하지 못하는 **예외·판단·고객 응대**에 집중합니다. 메인 대시보드 "내 작업 큐"가 "지금 해야 할 일"을 보여줍니다.

**Q2**: 9개 채널 어드민에는 이제 들어가지 않아도 되나요? **A**: 거의 들어가지 않아도 됩니다 (90% 감소). 단, 정말 드문 예외 (예: 채널 정책 변경 시 수동 설정)는 직접 접근할 수 있습니다.

**Q3**: 자동화 결과가 이상해요. 어떻게 하나요? **A**: 1) OpsHub 대시보드에서 자동화 작업 로그 확인 → 2) 시스템 운영자에게 슬랙 (#opshub-support) 보고. 절대 결과를 임의 보정 X.

**Q4**: 내 권한이 부족해요. **A**: 운영팀장이 권한 부여 책임자. 슬랙 DM 또는 직접 요청.

**Q5**: 휴가 갈 때 내 일을 누가 하나요? **A**: 임시 권한 부여 절차 (T4-10 6.4 임시) — 운영팀장에게 요청.

**Q6**: 시스템 다운이면 어떻게 하나요? **A**: 시스템 운영자가 1차 대응 (1시간 SLA). 그동안 9채널 어드민 직접 사용 가능 (백업 모드).

|🟠 **High**|일부 기능 다운·9채널 중 일부 장애·자동화 1시간+ 멈춤|30분|4시간|CTO 1시간|

|🟢 **Low**|UX 이슈·로그 경고·복구 가능한 일시 장애|다음 영업일|7일|운영팀장 주간 보고|

#### 4.2 장애 대응 절차 (공통)

```
1. 알람 인지 (Slack #opshub-critical or #opshub-alerts)
   ↓
2. Severity 분류
   ↓
3. 대응 시작 (시간 기록)
   ├─ Critical: CTO·운영팀장 즉시 알림
   ├─ High: CTO 1시간 내 알림
   └─ Medium·Low: 일일·주간 보고
   ↓
4. 원인 분석 (Datadog·Sentry·로그)
   ↓
5. 임시 조치 (서비스 복구 우선)
   ├─ 외부 API 장애: fallback 또는 자동 재시도 모니터링
   ├─ DB 장애: Read Replica 전환
   └─ 코드 버그: 롤백 (이전 배포)
   ↓
6. 근본 원인 분석 (RCA)
   ↓
7. 영구 해결
   ↓
8. 사후 분석 (Post-mortem) — Critical·High 시
```

#### 4.3 장애별 런북 (3개 발췌)

##### 장애 유형 1: 9채널 재고 동기화 다중 실패

**증상**: F-011 동기화 실패율 >10% (정상 <1%)·F-014 알람 다수

**원인 가능성**:

1. 채널 API 일시 장애
2. OpsHub-채널 네트워크 장애
3. 채널 API 정책 변경 (4xx 다수)
4. RabbitMQ 큐 적체
5. 인증 토큰 만료 (다수 채널 동시)

**대응 절차**:

```
[Step 1] OpsHub 대시보드 → 어느 채널 실패인지 확인 (1분)
   ├─ 모든 채널 실패 → OpsHub 자체 문제 (Step 2)
   └─ 일부 채널만 → 해당 채널 문제 (Step 3)

[Step 2] OpsHub 자체 점검 (5분)
   ├─ Datadog OpsHub Health: 정상이면 → Step 3
   ├─ RabbitMQ 큐 적체: 일시 정지 후 처리량 ↑ → Worker 스케일 ↑
   └─ DB 장애: Step 5 (DB 장애 런북)

[Step 3] 특정 채널 점검 (10분)
   ├─ 채널 API Status Page 확인
   ├─ 채널 API 응답 코드 (4xx vs 5xx)
   │   ├─ 5xx 다수: 채널 일시 장애 → Step 4
   │   └─ 4xx 다수: 정책 변경 가능성 → Step 6
   └─ 토큰 만료: AUTO-010 토큰 갱신·실패 시 수동 갱신

[Step 4] 채널 일시 장애 대응
   ├─ 자동 재시도 모니터링 (대부분 자동 복구)
   ├─ 1시간 이상 지속: 채널 운영팀 문의
   └─ 운영팀에 보고: "쿠팡 채널 일시 장애, 자동 복구 대기 중"

[Step 5] DB 장애 대응
   → "DB 장애 런북" 참조 (별도)

[Step 6] 채널 정책 변경 의심
   ├─ 채널 공지·개발자 문서 확인
   ├─ 어댑터 (F-080~086) 코드 점검
   ├─ 변경 사항 식별 → 어댑터 수정 → 배포
   └─ 운영팀·MD에게 영향 안내
```

**복구 후**:

- Slack `#opshub-incidents` 에 보고
- Post-mortem 작성 (Critical·High 시)

##### 장애 유형 2: OpsHub 자체 다운

**증상**: OpsHub 접속 불가·모든 API 5xx·Datadog 알람

**원인 가능성**:

1. ECS 컨테이너 다운
2. RDS 장애
3. 배포 직후 버그
4. 메모리·CPU 부족 (스파이크)

**대응 절차**:

```
[Step 1] 즉시 Critical 알람 인지 (15분 내)
   ↓
[Step 2] CTO·운영팀장 즉시 통보 (Slack #opshub-critical + 전화)
   ↓
[Step 3] 영향 범위 파악
   ├─ Datadog: 어느 모듈·서비스 다운?
   ├─ AWS Console: ECS·RDS 상태?
   └─ 최근 배포 (지난 24시간)?
   ↓
[Step 4] 임시 복구
   ├─ 최근 배포 직후 → 이전 버전 롤백 (5분)
   ├─ ECS 컨테이너 unhealthy → 강제 재시작
   ├─ RDS 장애 → Multi-AZ failover (자동·15분)
   └─ 메모리 부족 → 스케일 ↑
   ↓
[Step 5] 운영팀 안내
   "OpsHub 일시 점검 중. 9채널 어드민 직접 사용 (백업 모드)"
   예상 복구 시간 공지
   ↓
[Step 6] 영구 해결
   └─ RCA + Post-mortem
```

##### 장애 유형 3: 정산 자동 수집 실패

**증상**: 매일 02:00~03:00 정산 수집 실패·박정산 슬랙 알람

**원인 가능성**:

1. 채널 정산 API 일시 장애
2. CSV 다운로드 (네이버 등) 실패 — 셀레니움·로그인 변경
3. 데이터 형식 변경 (정규화 실패)
4. CafeBean 자동 입력 (F-024) 실패

**대응 절차**:

```
[Step 1] 알람 인지 (박정산 슬랙)
   ↓
[Step 2] OpsHub 대시보드 → settlement_collection_log 확인
   ↓
[Step 3] 실패 채널·원인 분류
   ├─ API 5xx → Step 4 (재시도)
   ├─ CSV 다운로드 실패 → Step 5 (셀레니움 점검)
   ├─ 정규화 실패 → Step 6 (어댑터 수정)
   └─ CafeBean API 실패 → Step 7 (CafeBean 점검)
   ↓
[Step 4] 채널 API 재시도
   ├─ 수동 트리거: `python -m opshub.scripts.retry_settlement --channel X --date Y`
   └─ 다음 영업일까지 자동 복구 대기

[Step 5] 셀레니움 점검
   ├─ 채널 로그인 페이지 변경 확인
   ├─ 셀레니움 스크립트 수정·테스트
   └─ 배포

[Step 6] 어댑터 수정
   ├─ 변경된 데이터 형식 식별
   ├─ 어댑터 매핑 수정
   └─ 배포

[Step 7] CafeBean 점검
   ├─ CafeBean Status 확인
   └─ 박정산 수동 입력 fallback
```

**복구 후**: 박정산에게 결과 통보·월말 정산에 영향 없는지 확인
