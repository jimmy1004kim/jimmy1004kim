## 이 문서는

내부 시스템 구축에서 **각 기능을 개발·QA가 구현 가능한 수준으로 명세한 문서**.

T4 산출물 흐름에서의 위치:

```
[T4-3 요구사항] → [T4-5 업무 흐름도] → [T4-6 기능 정의서] → 구현
       ↓                ↓                    ↓
  "무엇을 만들까"   "어떤 순서로"        "어떻게 만들까"
```

다른 T 유형의 기능 정의서와의 차이:

|구분|T1 기능 정의서 (신규)|T2 기능 리스트 (외주)|T3 기능 변경 정의서 (개선)|**T4 기능 정의서 (내부 시스템)**|
|---|---|---|---|---|
|단위|기능 1개 (FR-XXX)|기능 인벤토리 47개|변경 1건|**기능 1개 (F-XXX)**|
|청중|외부 사용자 대상 디자인·개발·QA|발주자·BuildCo|운영 중 변경 팀|**내부 사용자 (운영팀)·개발·QA**|
|강조|사용자 경험|계약 범위|Before·After|**업무 효율·시스템 통합·자동화 로직**|
|핵심|UI·인터랙션|인벤토리·계약|회귀·롤백|**자동화·예외 처리·외부 연동**|

**핵심**: T4 기능 정의서는 **"운영팀 업무를 시스템이 어떻게 대신하는가"**의 상세. 자동화 로직·외부 시스템 연동·예외 처리가 핵심.

### T4 기능의 5가지 유형

|유형|의미|예시|
|---|---|---|
|**자동화 (Automation)**|사람 작업을 시스템이 대신|주문 자동 처리·재고 동기화|
|**통합 (Integration)**|외부 시스템과 연동|9개 채널 API·CafeBean 연동|
|**모니터링 (Monitoring)**|상태·이상 감지·알람|재고 부족·정산 오차|
|**운영 도구 (Operation Tool)**|사람이 시스템을 활용하는 UI|통합 대시보드·수동 보정|
|**보고·분석 (Reporting)**|데이터 집계·시각화|KPI 대시보드·정산 보고서|

내부 시스템 기능 정의서는 **5가지 유형에 따라 강조점이 다름**.

### 기능 정의의 8가지 측면

|측면|핵심 질문|
|---|---|
|**개요·목적**|무엇을·왜 하는가|
|**사용자·역할**|누가 사용·트리거|
|**입력·출력·처리**|무엇이 들어가고·나오고·처리되나|
|**자동화 로직**|알고리즘·조건·계산|

|**데이터**|어떤 테이블·이벤트·로그|
|**수용 기준**|QA Pass/Fail 명확|

본 가이드는 8가지 측면 모두 다룸.

### 자동화 기능의 추가 강조점

T4의 핵심 기능은 대부분 자동화 — 추가로 정의:

1. **트리거**: 무엇이 자동화를 시작하나
2. **스케줄·빈도**: 언제·얼마나 자주
3. **idempotency** (멱등성): 중복 실행 방지
4. **롤백·보상**: 실패 시 원복 절차
5. **운영 가시성**: 사람이 모니터링·수동 개입 가능한가

### F-001: 신규 주문 자동 수집

#### A. 메타

|항목|내용|
|---|---|
|기능 ID|F-001|
|기능명|신규 주문 자동 수집|
|유형|**자동화 + 통합**|
|모듈|MOD-001 (주문 처리 엔진) + MOD-009 (어댑터)|
|우선순위|M (Must)|
|Phase|1|
|관련 FR|FR-001|
|관련 BIZ (AS-IS)|BIZ-001 (신규 주문 확인)|

#### B. 개요·목적

9개 채널에서 발생한 신규 주문을 OpsHub이 자동 수집하여 통합 대시보드(P-101)에 표시. 운영팀이 9개 채널 어드민을 일일이 확인하는 작업을 제거.

#### C. 사용자·역할·트리거

- **사용자**: MD (조회), 시스템 (자동)
- **트리거**:
    - 채널 Webhook 수신 (지원 채널: 쿠팡·네이버·11번가)
    - 5분 간격 polling (지원 안 하는 채널: G마켓·옥션·카카오·기타)
- **스케줄**: Webhook 즉시 + 5분 polling 백업
- **빈도**: 일 약 1,500건 주문 수집

#### D. 입력·처리·출력

- **입력**:
    - 채널 API 응답 (주문번호·상품·수량·고객·금액·배송지·상태)
    - 또는 Webhook payload
- **처리**:
    1. 채널 API 호출 또는 Webhook 수신
    2. 데이터 validation (필수 필드·형식)
    3. 중복 감지 (`channel_id + channel_order_id`)
    4. OpsHub `orders` 테이블에 적재
    5. 이벤트 발행 (`order.created`)
    6. 통합 대시보드 실시간 갱신 (WebSocket)
- **출력**:
    - OpsHub `orders` DB 레코드
    - `order.created` 이벤트 (RabbitMQ)
    - 통합 대시보드 표시

#### E. 자동화 로직

- 상세는 T4-11 (AUTO-001) 참조
- 핵심:
    - Polling: 채널별 `last_synced_at` 이후 주문만 fetch
    - Idempotency: `channel_id + channel_order_id` 유니크 제약
    - Webhook vs Polling 충돌 시 Webhook 우선

#### F. 외부 연동

|외부 시스템|연동 방식|데이터|
|---|---|---|
|쿠팡|Webhook + REST API|주문 정보|
|네이버 스토어팜|Webhook + REST API|주문 정보|
|11번가|REST API (polling)|주문 정보|
|G마켓·옥션·카카오·기타 6개|REST API (polling)|주문 정보|

→ 어댑터 (F-080~086) 활용

#### G. 예외 처리·재시도·롤백

|#|예외|처리|
|---|---|---|
|1|채널 API 5xx·timeout|자동 재시도 3회 (지수 백오프)|
|2|채널 API 인증 만료 (401)|토큰 갱신 → 재시도|
|3|중복 주문 (channel_order_id 충돌)|skip (idempotency)|
|4|데이터 형식 변경|로그·슬랙 알람·수동 대응|
|5|OpsHub DB 장애|재시도 또는 큐 보관|
|6|Webhook 누락 가능성|5분 polling 백업|

**롤백**: 잘못 수집된 주문은 `is_active=false` 처리 (소프트 삭제), 로그 보존

#### H. 데이터

|항목|내용|
|---|---|
|입력 API|채널별 API·Webhook|
|출력 테이블|`orders` (T4-9)|
|이벤트 발행|`order.created` (RabbitMQ)|
|로그|`order_sync_log` (외부 API 호출 이력)|

#### I. 화면 연결

- **P-101 주문 관리 대시보드** (T4-7): 신규 주문 실시간 표시
- 사용자 인터랙션: 조회·필터·검색

#### J. 권한·정책

- 접근 권한 (T4-10): MD·운영팀장 (읽기·쓰기) / 재고·CS·정산 (읽기)
- 관련 정책 (T4-8): POL-001 (주문 데이터 보관 90일)·POL-005 (개인정보 처리)

#### K. SLA·성능

|지표|목표|
|---|---|
|Webhook 수신 → DB 적재|**5초 이내**|
|Polling 갱신 주기|5분|

#### L. 수용 기준

1. 9개 채널 신규 주문이 발생 후 5분 이내 OpsHub에 적재된다
2. 동일 주문이 중복 적재되지 않는다 (channel_id + channel_order_id 유니크)

4. 1시간 누적 주문 누락 0건
5. Webhook과 Polling이 충돌해도 중복 적재 없음
6. 통합 대시보드(P-101)에 실시간 표시된다 (WebSocket)
7. 외부 채널 API 인증 만료 시 토큰 자동 갱신된다

#### M. 관련 산출물

### F-011: 9개 채널 재고 자동 동기화

#### A. 메타

#### C. 사용자·역할·트리거

- **사용자**: 시스템 (자동)
- **트리거**: F-010 (재고 변동 이벤트) → RabbitMQ 큐 → F-011 처리

    4. 결과 수집
    5. 모두 성공 시 → F-013 (정합성 검증) 트리거
    6. 일부 실패 시 → F-012 (자동 재시도) 트리거

    - 9개 채널 재고 업데이트

#### E. 자동화 로직

- 상세는 T4-11 (AUTO-002) 참조
- 핵심:
    - 병렬 호출 (asyncio.gather)
    - SKU별 큐 FIFO (동시 변동 충돌 방지)
    - Timeout 30초·재시도 3회

#### F. 외부 연동

## 5. 공통 처리 표준

### 5.1 인증·세션

- 사용자: SSO (Google Workspace OAuth) + JWT 세션 (8시간)
- 외부 API 토큰: AWS KMS 암호화 저장·자동 갱신
- 권한 체크: 모든 API 호출 시 RBAC 검증 (T4-10)

### 5.2 로깅 표준

```
{
  "timestamp": "ISO 8601",
  "level": "INFO·WARN·ERROR",
  "request_id": "uuid",
  "user_id": "uuid·null (시스템)",
  "module": "MOD-XXX",
  "action": "action_name",
  "input": {...},
  "result": "success·fail",
  "duration_ms": 123,
  "error": null·{...}
}
```

- 보관 기간: 90일 (NFR-025)
- 검색: Datadog·CloudWatch

### 5.3 에러 응답 표준

|HTTP|의미|응답 형식|
|---|---|---|
|400|잘못된 요청|`{error_code, message, details}`|
|401|인증 실패|`{error_code, message}`|
|403|권한 없음|`{error_code, message}`|
|404|자원 없음|`{error_code, message}`|
|409|충돌 (중복)|`{error_code, message}`|
|429|Rate Limit|`{error_code, message, retry_after}`|
|500|서버 오류|`{error_code, message, request_id}`|
|503|외부 의존성 장애|`{error_code, message, dependency}`|

### 5.4 알람 표준

|레벨|채널|임계치|예시|
|---|---|---|---|
|🔴 **Critical**|슬랙 (`#opshub-critical`) + 이메일 + (전화)|즉시|시스템 다운·매출 손실 발생|
|🟠 **High**|슬랙 (`#opshub-alerts`)|즉시|재고 동기화 3회 실패·정산 오차 ≥10만원|
|🟡 **Medium**|슬랙 (`#opshub-alerts`, 요약)|일일 모음|재시도 1회 실패·외부 API 일시 지연|
|🟢 **Low**|로그만|주간 리포트|정상 작업·일반 이벤트|

### 5.5 멱등성 (Idempotency)

|자원|Idempotency Key|
|---|---|
|주문|`channel_id + channel_order_id`|
|재고 동기화|`event_id` (RabbitMQ 메시지 ID)|
|정산|`channel_id + settlement_date + settlement_id`|
|CS 문의|`channel_id + channel_inquiry_id`|

→ 모든 자동화 기능에 idempotency 필수 적용

## 자주 하는 실수

- **자동화 로직 불명확** — "잘 동기화한다" 같은 모호
- **외부 연동 명세 부족** — API 종류·인증·Rate Limit 누락
- **예외 처리 누락** — 정상 흐름만
- **idempotency 누락** — 중복 실행으로 재고 0 되는 사고

- **화면·데이터 연결 안 함** — 산출물 따로 놂
- **운영팀 검토 X** — 실제 업무와 안 맞음
- **Phase 배정 없음** — 한 번에 다 → Big Bang
- **자동화 vs 사람 역할 모호** — "이건 누가?"
- **외부 API 변경 대비 없음** — 어댑터 표준화 누락
