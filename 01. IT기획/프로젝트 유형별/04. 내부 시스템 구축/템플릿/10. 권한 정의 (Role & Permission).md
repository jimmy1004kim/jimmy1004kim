## 이 문서는

내부 시스템의 **역할 (Role)·권한 (Permission)·접근 제어 정책을 정의한 명세 문서**.

T4 산출물 흐름에서의 위치:

```
[T4-6 기능 정의] + [T4-8 정책] + [T4-9 데이터] → [T4-10 권한 정의] → 구현 (RBAC)
                                                      ↓
                                          "누가·무엇을·어떻게 접근"
```

### 왜 권한 정의가 핵심인가

내부 시스템에서 권한 설계가 부실할 때 발생하는 문제:

- **과도한 권한 부여** — 모든 사용자가 모든 데이터 접근 (개인정보·정산 사고)
- **부족한 권한** — 필요한 작업도 못 함 (운영팀 불만)
- **권한 변경 추적 불가** — 누가 언제 무슨 권한 부여했나
- **법령 위반 위험** — 개인정보보호법·내부 통제 위반
- **퇴사·직무 변경 대응 부실** — 권한 회수 안 됨

권한 정의가 위 5가지 모두 해결.

### 권한 모델 3가지

|모델|의미|적용|
|---|---|---|
|**RBAC (Role-Based)**|역할에 권한 부여|**표준 — 내부 시스템 권장** ⭐|
|**ABAC (Attribute-Based)**|속성 (사용자·자원·환경) 기반|복잡한 조건 (시간·IP 등)|
|**PBAC (Policy-Based)**|정책 엔진|대형 조직·복잡 정책|

본 가이드는 **RBAC 중심 + ABAC 보조** 권장.

### RBAC의 3가지 구성요소

```
사용자 (User) ──→ 역할 (Role) ──→ 권한 (Permission) ──→ 자원 (Resource)
   김운영           운영팀장          orders.read·write       orders 테이블
```

- **사용자 (User)**: 운영팀 8명·시스템 운영자 1명
- **역할 (Role)**: 6개 (운영팀장·MD·재고·정산·CS·시스템 운영자)
- **권한 (Permission)**: 자원·동작 (예: `orders.read`, `orders.write`)
- **자원 (Resource)**: 테이블·기능·화면·API

### 권한 설계의 7대 원칙

|원칙|의미|
|---|---|
|**최소 권한 원칙 (Least Privilege)**|업무에 필요한 최소만|
|**직무 분리 (Separation of Duties)**|한 사람이 모든 권한 X (예: 정산 + 환불 분리)|
|**명시적 부여**|기본 거부·필요 시 부여|
|**권한 위임 불가**|사용자 간 권한 양도 X|
|**이중 인증 (Critical 자원)**|민감 자원은 추가 인증|
|**모든 접근 로그**|audit_log 필수|
|**정기 권한 검토**|분기 1회 권한 정리|

본 가이드는 7대 원칙 모두 반영.

### 권한의 4가지 영역

|영역|의미|예시|
|---|---|---|
|**데이터 접근**|테이블·필드 읽기·쓰기|orders.read, customers.read (개인정보)|
|**기능 실행**|기능 호출|bulk_ship.execute|
|**화면 접근**|UI 페이지|P-301 정산 대시보드|
|**시스템 관리**|설정·권한·연동|api_credentials.manage|

### 민감 자원의 추가 보호

|자원|민감도|추가 보호|
|---|---|---|
|고객 개인정보 (customers PII)|🔴 高|접근 로그·정기 감사|
|외부 API 토큰 (api_credentials)|🔴 高|KMS·접근 로그|
|정산 데이터 (daily_settlements)|🟠 中|정산 담당+CFO만|
|권한 관리 (roles·permissions)|🟠 中|운영팀장·시스템 운영자만|
|데이터 삭제|🔴 高|이중 확인·소프트 삭제만|

## 6. 권한 부여·회수 절차

### 6.1 신규 직원 권한 부여

```
1. HR 입사 처리 (HR DB)
   ↓
2. 직무 확인 → Role 자동 매핑 (사전 정의된 매핑 표)
   ├─ MD → ROLE-MD
   ├─ CS → ROLE-CS
   └─ ...
   ↓
3. 운영팀장 + 시스템 운영자 공동 권한 부여 (P-901)
   ├─ Role 부여 (자동 매핑된 권한 세트)
   ├─ 이중 인증 셋업 (Critical 동작 필요 시)
   └─ 시간·IP 제한 적용
   ↓
4. 운영 매뉴얼 교육 (T4-12)
   ↓
5. 첫 30일 권한 사용 점검
   ├─ 사용하지 않는 권한 → 회수 검토
   └─ 필요한 추가 권한 → 신청·승인
   ↓
6. 30일 후 정상 운영
```

### 6.2 직무 변경 시

```
1. HR 직무 변경 처리
   ↓
2. 기존 Role 회수 + 신규 Role 부여 (공동 결재)
   ↓
3. 변경 사유·승인자 audit_log 기록
   ↓
4. 사용자 통보 (이메일·슬랙)
```

### 6.3 퇴사·직무 종료 시 (가장 중요)

```
1. HR 퇴사 처리 (D-Day 또는 사전 지정일)
   ↓
2. **권한 즉시 회수** (D-Day 00:00)
   ├─ 모든 Role 제거
   ├─ JWT 세션 즉시 만료
   ├─ SSO 비활성화 (Google Workspace 연동)
   └─ 외부 API 토큰 회수 (시스템 운영자)
   ↓
3. 회수 로그 기록 (90일 보존)
   ↓
4. 인수인계 완료 확인 (운영팀장)
   ↓
5. 30일 후 비활성 계정 처리·90일 후 삭제
```

### 6.4 임시 권한 부여 (특수)

|케이스|절차|
|---|---|
|**휴가 대체** (예: 박정산 휴가 → 김운영 임시)|사유·기간 명시·운영팀장+시스템 운영자 공동 승인·기간 종료 시 자동 회수|
|**외부 컨설팅**|별도 Role (제한적)·기간 명시·NDA·종료 시 즉시 회수|
|**개발 디버깅**|시스템 운영자만·시간 제한·로그 추가|

## 작성 팁

- **RBAC + 일부 ABAC 권장** — 단순 + 유연
- **6대 Role 분명히** — 운영팀 직무 기반
- **7대 원칙 적용** — 최소 권한·직무 분리·명시적·위임 X·이중 인증·로그·정기 검토
- **Permission ID 표기 표준** — `{resource}.{action}`
- **민감 자원 식별·추가 보호** — PII·API 토큰 등
- **직무 분리 명확** — 환불 신청 vs 승인·권한 관리 vs 사용
- **이중 인증 (OTP)** — Critical 동작
- **시간·IP 제한** — ABAC 옵션
- **부여·회수 절차** — 신규·변경·퇴사·임시
- **정기 검토** — 분기·반기·연
- **감사 로그** — 90일 + 변조 방지
- **법무·CFO·CTO 검토** — 개인정보·정산·시스템
- **운영팀 워크숍 합의** — 실제 사용성

## 자주 하는 실수

- **과도한 권한** — 모든 사용자 admin → 사고 위험
- **부족한 권한** — 필요 작업 못 함 → 운영 불만
- **직무 분리 안 함** — 환불 신청 + 승인 동일인
- **이중 인증 없음** — Critical 동작 노출
- **감사 로그 누락** — 사고 추적 불가
- **퇴사 권한 회수 늦음** — 보안 사고
- **정기 검토 안 함** — 권한 누적
- **개인정보 권한 광범위** — 법령 위반
- **외부 API 토큰 공유** — 보안 사고
- **시간·IP 제한 없음** — 외부 접근 위험
- **HR 시스템 미연동** — 입퇴사 권한 누락
- **권한 변경 이력 추적 X** — 누가 부여했는지 모름
- **법무·CFO·CTO 검토 X** — 법령 위반·내부 통제 부실
