## 이 문서는

운영 중인 서비스의 **기존 기능 변경·신규 기능 추가·기능 삭제·기능 이전**을 상세히 정의한 문서.

T3 산출물 흐름에서의 위치:

```
[T3-4 개선 기획서] → [T3-6 기능 변경 정의서] + [T3-7 화면 변경 정의서] + [T3-9 회귀 테스트]
         ↓                       ↓                       ↓
   "무엇을 개선" 청사진      "기능 단위 상세"        "화면 단위 상세"
```

T1·T2와의 차이:

|구분|T1 기능 정의서|T2 기능 리스트|**T3 기능 변경 정의서**|
|---|---|---|---|
|시점|신규 서비스 출시 전|외주 계약 시|**운영 중 서비스 개선 시**|
|청중|디자인·개발·QA|발주자·BuildCo|**PM·디자인·개발·QA·운영팀·CS**|
|단위|기능 1개 (FR-XXX)|기능 47개 인벤토리|**변경 1건** (FC-XXX)|
|깊이|신규 기능 명세|기능 인벤토리·요구사항|**변경 사항·영향·롤백**|
|강조|What·How|계약 범위|**Before vs After·영향 분석**|

**핵심**: T3 기능 변경 정의서는 **"변경" 자체의 상세**. Before·After 양쪽을 명시하고, 영향·롤백·회귀 모두 포함.

### 기능 변경의 4가지 유형

|유형|의미|처리 강조|
|---|---|---|
|**변경 (Modify)**|기존 기능 동작 변경|Before·After 비교, 회귀 영향|
|**추가 (Add)**|신규 기능 추가|신규 명세, 기존 기능과의 통합|
|**삭제 (Remove)**|기능 제거|사용자 영향, 마이그레이션, 데이터 처리|
|**이전 (Migrate)**|화면·플로우 이동|기존 진입점 처리, 데이터 이전|

이 가이드는 4가지 모두 다룰 수 있음. **변경 (Modify)** 가장 흔함.

### 왜 별도 문서가 필요한가

T1·T2의 기능 정의서를 그대로 쓰면 안 되는 이유:

1. **운영 중 서비스는 변경 단위가 다름** — "전체 명세"가 아니라 "변경 사항"이 중심
2. **Before가 있다** — 신규 서비스에는 없는 정보
3. **회귀 영향 식별이 핵심** — 기존 사용자·기능에 미치는 영향
4. **롤백 절차 필수** — 신규 서비스보다 운영 중 서비스가 롤백 위험 큼
5. **CS·운영팀 안내 필수** — 기존 사용자가 알아차림

## 2. Before vs After (F-005 매칭 알고리즘)

### 2.1 Before (현재 동작)

#### 사용자 흐름

- 기업이 프로젝트 등록 (요구 기술·예산·위치 입력)
- 시스템이 매칭 알고리즘 실행 → Top 5 프리랜서 추천
- 기업이 추천 결과 확인 → 메시지 또는 패스
- (현재 매칭→계약 전환율 32%)

#### 로직·계산식 (Before)

매칭 점수 = (각 요소 가중치 × 점수)의 가중합

```
matching_score(freelancer, project) =
    0.40 × tech_match_score    +    # 기술 스택 일치도
    0.15 × verified_score       +    # 검증 마크 (Boolean → 0·1)
    0.15 × rating_avg_score    +    # 평균 평가 (1~5 → 0~1)
    0.10 × rating_count_score  +    # 평가 누적 수 (log scale)
    0.10 × budget_match_score  +    # 단가·예산 매칭
    0.10 × location_match_score      # 위치·근무형태 매칭
```

#### 정책·규칙 (Before)

- POL-005 v1.0: "매칭 알고리즘은 기술 스택 일치도를 가장 중요한 요소로 한다"

#### 데이터 흐름 (Before)

- 입력: project (요구사항) + freelancer 풀
- 처리: 가중합 점수 계산 → 상위 5명 선택
- 출력: 5명 프리랜서 리스트 (점수 내림차순)

### 2.2 After (변경 후 동작)

#### 사용자 흐름

- (Before와 동일)
- 단, **추천 5명이 신뢰 신호 강한 프리랜서 위주**로 구성됨

#### 로직·계산식 (After)

```
matching_score(freelancer, project) =
    0.30 × tech_match_score    +    # 기술 스택 일치도 (↓ 10pp)
    0.25 × verified_score       +    # 검증 마크 (↑ 10pp)
    0.20 × rating_avg_score    +    # 평균 평가 (↑ 5pp)
    0.15 × rating_count_score  +    # 평가 누적 수 (↑ 5pp)
    0.05 × budget_match_score  +    # 단가·예산 매칭 (↓ 5pp)
    0.05 × location_match_score      # 위치·근무형태 매칭 (↓ 5pp)
```

**Total 합: 100% (Before와 동일)**

#### 정책·규칙 (After)

- POL-005 v1.1: "매칭 알고리즘은 **신뢰 신호(검증 마크·평균 평가·평가 누적)를 가장 중요한 요소(60%)** 로 하고, 기술 스택 일치도(30%)·기타(10%) 순으로 한다"

#### 데이터 흐름 (After)

- 입력·처리·출력 (Before와 동일, 가중치만 다름)
- A/B 실험 분기: 사용자 ID 해시 기준 50:50 무작위 (Sticky)

### 3.2 로직·알고리즘 상세

```python
# matching_service.py (변경 후)

def get_matching_weights(user_id: str) -> dict:
    """
    A/B 실험 동안: 사용자 ID 해시 기준 Control·Variant 분기
    Rollout 후: 모든 사용자에게 Variant 가중치 적용
    """
    if amplitude_experiment.is_in_variant(user_id, "matching_weight_v2"):
        # Variant (After)
        return {
            "tech_match": 0.30,
            "verified": 0.25,
            "rating_avg": 0.20,
            "rating_count": 0.15,
            "budget_match": 0.05,
            "location_match": 0.05,
        }
    else:
        # Control (Before)
        return {
            "tech_match": 0.40,
            "verified": 0.15,
            "rating_avg": 0.15,
            "rating_count": 0.10,
            "budget_match": 0.10,
            "location_match": 0.10,
        }


def calculate_matching_score(freelancer, project, weights) -> float:
    score = 0.0
    score += weights["tech_match"] * tech_match_score(freelancer, project)
    score += weights["verified"] * verified_score(freelancer)
    score += weights["rating_avg"] * rating_avg_score(freelancer)
    score += weights["rating_count"] * rating_count_score(freelancer)
    score += weights["budget_match"] * budget_match_score(freelancer, project)
    score += weights["location_match"] * location_match_score(freelancer, project)
    return score
```

- **Before 누락** — After만 적음 → 변경 사항 모호

- **영향 받는 기능 누락** — 직접만 봄, 간접 영향 놓침
- **회귀 영향 분석 X** — 출시 후 부작용 발견
- **롤백 절차 모호** — 부작용 시 우왕좌왕
- **CS·운영팀 안내 사전 준비 X** — 출시 후 문의 폭주
- **A/B 분기 코드·가중치 모호** — Control·Variant 혼동
- **성능 영향 미검증** — 응답 시간 ↑ 출시 후 발견

- **승인자 누락** — 단독 결정 → 책임 모호
- **변경 이력 안 기록** — v0.1·v1.0 변경 사항 추적 X
