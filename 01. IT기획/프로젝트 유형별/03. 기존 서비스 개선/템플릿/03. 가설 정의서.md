## 이 문서는

기존 서비스에서 발견한 문제나 기회에 대해 **"무엇을 변경하면 어떤 결과를 만들 것인가"** 를 명시화한 문서.

T3 산출물 흐름에서의 위치:

```
[T3-1 문제 정의서] → [T3-2 데이터 분석] → [T3-3 가설 정의서] → [T3-4 개선 기획서] → [T3-5 A/B 테스트 설계서]
```

다른 산출물과의 비교:

|구분|T3-1 문제 정의서|T3-3 가설 정의서|T3-4 개선 기획서|
|---|---|---|---|
|단위|문제 1건|**가설 1건** (HYP-XXX)|개선 프로젝트 1건|
|깊이|무엇이·왜 문제|**무엇을 → 어떤 결과**|어떻게 실행할 것|
|청중|의사결정자·팀|팀 + 분석가 + 의사결정자|의사결정자·전체 팀|
|효력|우선순위 근거|**A/B 테스트 설계 근거**|실행 계획|

**핵심**: 가설은 **실험 가능한 형태로 명문화**되어야 한다. 모호하면 검증 불가. "이거 해보면 좋을 듯" ❌, "버튼 위치를 X로 바꾸면 클릭률이 Y% 증가할 것" ⭕.

### T1 MVP 가설 vs T3 개선 가설

T1과 T3 모두 "가설"을 다루지만 성격이 다르다:

|구분|T1 MVP 가설 (MVP-H)|T3 개선 가설 (HYP)|
|---|---|---|
|시점|**출시 전** (서비스 존재 검증)|**출시 후** (운영 중 개선)|
|영향|사업 성립 여부|지표 개선|
|데이터|0 (예상치)|**누적 데이터 활용**|
|검증|베타·정식 출시|**A/B 테스트·코호트 분석**|
|범위|큰 가설 1~3개|**작은 가설 다수**|
|우선순위|사업 영향력|**ICE·RICE 등 매트릭스**|

T3 가설은 **작고 자주 검증 가능**해야 한다. 데이터·실험 기반.

### 가설의 표준 구조

좋은 가설은 4가지 요소를 모두 포함:

```
[변경] If we [무엇을 변경] for [누구에게]
[기대] then [어떤 행동·지표] will [어떻게 변할 것이다]
[근거] because [데이터·관찰·사용자 피드백 등]
[검증] We will know this is true if [지표가 어떻게 되면]
```

**예시**:

- ❌ "매칭 알고리즘을 개선하자"
- ⭕ "신뢰도 가중치를 검증 마크·평가 점수로 재조정하면 (변경), 상위 5명 프리랜서의 메시지 전송률이 (지표) 40%→55%로 증가할 것이다 (기대), 현재 사용자 인터뷰에서 '검증 안 된 사람과 대화하기 부담' 답변이 60%이기 때문 (근거). 4주 A/B 테스트에서 통계적 유의성 p<0.05로 메시지 전송률 +12pp 이상이면 가설 검증 (검증)."

### 가설의 4가지 유형

|유형|의미|예시|
|---|---|---|
|**행동 변화 가설**|사용자 행동이 어떻게 바뀔 것|"사이즈 가이드 표시 → 반품률 감소"|
|**인지·태도 가설**|사용자 인식·신뢰가 어떻게 바뀔 것|"검증 마크 강조 → 매칭 신뢰도 ↑"|
|**퍼널 가설**|전환율·이탈률이 어떻게 바뀔 것|"결제 단계 단순화 → 전환율 ↑"|
|**참여·잔존 가설**|장기 사용·재방문이 어떻게 바뀔 것|"주간 추천 이메일 → 30일 재방문 ↑"|

## 언제 만드나

- 문제 정의서 작성 후 (해결안 도출 단계)
- 개선 기획서 작성 직전 (가설이 출발점)
- A/B 테스트 설계서 작성 직전 (가설이 실험의 근거)
- 데이터 분석에서 인사이트 발견 시 (가설로 정리)

**기준**: "이걸 해보자"는 아이디어가 나왔을 때, 실행 전 가설로 정리.

## 어떤 툴로

|툴|추천도|이유|
|---|---|---|
|**노션 DB**|⭐ 강력 추천|가설 1개 = 1행. 우선순위·상태·결과 필터|
|Confluence|추천|회사 표준이면|
|Google Docs|보조|협업 강함|
|Optimizely·Amplitude Experiment|보조|A/B 테스트 도구 연동|

**최적**: 노션 DB로 가설 인벤토리 + 가설별 상세 페이지.

## 표준 구성

```
1. 가설 메타 (ID·작성자·상태)
2. 문제·기회 (배경)
3. 가설 본문 (If-Then-Because-Validation)
4. 우선순위 (ICE·RICE)
5. 검증 방법·기간
6. 성공·실패 기준
7. 관련 산출물 링크
8. 변경 이력·승인
```

- 가설 ID·이름·작성자·작성일
- 관련 문제 (문제 정의서 링크)
- 4요소 가설 (변경·기대·근거·검증)
- 영향 받는 지표 (Primary·Secondary)
- 우선순위 점수 (ICE·RICE)
- 검증 방법 (A/B·코호트·관찰)
- 예상 영향력·신뢰도·노력
- 성공·실패 기준
- 결과·다음 액션 (검증 후)

## 작성 절차

1. **문제·기회 식별** — 데이터·인터뷰·관찰 (T3-1, T3-2 산출물 활용)
2. **가설 초안 작성** — If-Then-Because-Validation 4요소
3. **우선순위 평가** — ICE 또는 RICE 점수
4. **검증 방법 결정** — A/B·코호트·관찰·인터뷰

6. **이해관계자 합의** — 분석가·디자인·개발
7. **승인** — 우선순위 높은 가설은 의사결정자 승인
8. **실행** — A/B 테스트·코호트 분석 등
9. **결과 기록·다음 액션** — 검증 후 결과 추가

# 📌 예시 — TalentMatch HYP-007 매칭 알고리즘 신뢰도 가중치 조정

> 가상 사례. 2028-Q2 개선의 우선순위 1번 가설

## 가설 메타

|항목|내용|
|---|---|
|가설 ID|HYP-007|
|가설명|매칭 알고리즘 신뢰도 가중치 재조정으로 매칭→계약 전환율 향상|
|작성자|홍길동 (PM) + 김데이터 (데이터 분석가)|
|작성일|2028-04-10|
|상태|🟢 Approved (2028-04-15 의사결정 회의)|
|우선순위|🔴 Critical|
|분류|인지·태도 가설 + 퍼널 가설|
|관련 문제 정의서|PROB-003 (매칭→계약 전환율 정체)|
|관련 데이터 분석|DA-2028Q1-005 (funnel 분석)|
|검증 시작일|2028-05-06|
|검증 종료일|2028-06-02 (4주)|

## 1. 문제·기회

### 1.1 현재 상태

- 매칭→계약 전환율: **32%** (출시 시점 H1 검증값 유지, 1년간 정체)
- 매칭→메시지 전송률 (단계 1): 75% (높음)
- 메시지 전송→계약 전송률 (단계 2): **43%** (병목)
- 검증 마크 보유자의 전환율: 미보유자 대비 1.42배 (출시 시점과 유사)

### 1.2 문제·기회

- 메시지 전송 단계까지는 사용자 활발하나, **메시지→계약 전환 단계에서 큰 이탈** 발생
- 사용자 인터뷰 (28명, 2028-03):
    - "추천받은 5명 중 누가 진짜 신뢰할 만한지 모르겠다" (응답 60%)
    - "검증 마크가 있지만 그게 얼마나 신뢰할 만한 지 판단 어렵다" (45%)
    - "평가 1~2개로는 부족하다" (52%)
- 검증 마크가 있어도 평가 누적이 적은 프리랜서는 계약까지 가지 못함

### 1.3 영향 받는 사용자

- **기업 사용자**: 매월 매칭 시작하는 약 1,200건 (월 600개사 평균)
- **프리랜서 사용자**: 매칭 추천에 포함되는 약 3,800명 (활성)

## 2. 가설 본문

### 2.1 변경 (If)

**무엇을 변경할 것인가**: 매칭 알고리즘의 **신뢰도 가중치를 재조정**한다.

**구체적 변경**:

|항목|현재 가중치|변경 가중치|
|---|---|---|
|기술 스택 일치도|40%|30% (↓10pp)|
|검증 마크 보유|15%|25% (↑10pp)|
|평균 평가 점수|15%|20% (↑5pp)|
|평가 누적 수|10%|15% (↑5pp)|
|단가·예산 매칭|10%|5%|
|위치·근무형태 매칭|10%|5%|

**핵심**: 기술 일치도 비중 ↓ + 신뢰도(검증·평가·누적) 비중 ↑

**대상**: 기업 측 매칭 요청 사용자 (전체 풀의 50% 무작위 노출 — A/B 테스트)

### 2.2 기대 (Then)

**어떤 지표가 어떻게 변할 것인가**:

|지표|현재값|목표값 (4주 후)|
|---|---|---|
|**Primary**: 매칭→계약 전환율|32%|**40%** (+8pp, 25% 향상)|
|Secondary: 메시지 전송→계약 전송률|43%|55% (+12pp)|
|Secondary: 매칭 결과 만족도 (인터뷰)|6.8/10|7.5/10|
|Guardrail 1: 매칭→메시지 전송률|75%|70% 이상 유지 (악화 X)|
|Guardrail 2: 매칭 응답 시간 (P95)|2.4초|3.0초 이하 유지|
|Guardrail 3: 프리랜서 이탈률|28%|30% 이하 유지|

### 2.3 근거 (Because)

#### 정량 근거 (데이터, DA-2028Q1-005)

- 검증 마크 보유자의 메시지→계약 전환율: **52%** (미보유자 대비 1.8배)
- 평가 누적 5건 이상 프리랜서의 메시지→계약 전환율: **58%** (누적 1~2건의 1.6배)
- 현재 매칭 Top 5 중 검증 마크 보유자: 평균 **3.1명** (60%) — 비중 증가 여지 있음
- 알고리즘 가중치 vs 전환율 상관:
    - 기술 일치도 가중치 40%, 상관 0.18 (낮음)
    - 평가 누적 가중치 10%, 상관 0.48 (강함)

#### 정성 근거 (인터뷰)

- 사용자 인터뷰 28명 중:
    - "신뢰할 만한 사람을 더 잘 찾고 싶다" (75%)
    - "기술 스택은 많이 일치하지 않아도 신뢰 가는 사람과 일하고 싶다" (68%)
    - "검증된 평가가 많은 사람을 우선 추천받았으면 좋겠다" (61%)

#### 외부 근거

- Upwork·Toptal 등 글로벌 IT 프리랜서 매칭 플랫폼의 알고리즘: 신뢰도(평가·검증)가 기술 일치도보다 50% 이상 높은 가중치
- 매칭 추천 시스템 논문 (RecSys 2025): "신뢰 신호가 강할수록 전환율 +10~15pp 증가"

### 2.4 검증 (We will know this is true if)

**검증 방법**:

- **A/B 테스트** (대조군 50% vs 실험군 50%)
- 4주 운영
- 기업 사용자 무작위 배정 (사용자 ID 해시 기준)

**통계적 유의성**: p < 0.05

**성공 기준**:

- 매칭→계약 전환율 **+8pp 이상** (32% → 40%)
- 통계적 유의성 p < 0.05
- Guardrail 지표 모두 미악화

**실패 기준**:

## 작성 팁

- **4요소 (If-Then-Because-Validation) 모두 포함** — 하나라도 빠지면 가설 아님
- **정량 + 정성 근거 모두** — 데이터만 ❌ (왜 그런지 모름), 인터뷰만 ❌ (영향력 모름)
- **Primary·Secondary·Guardrail 3분류** — 핵심 지표 1개·보조 1~2개·악화되면 안 되는 1~3개
- **Guardrail 필수** — Primary만 보면 부작용 놓침. "전환율 ↑ 인데 이탈률도 ↑" 자주 발생
- **ICE/RICE 점수 일관** — 모든 가설 동일 기준으로 평가. 우선순위 비교 가능
- **통계적 유의성 명시** — p < 0.05 기본. 표본 충분한지 사전 계산
- **실패 기준도 명확** — 성공만 적으면 "애매한 결과"에 결정 못 함
- **중간 점검 시점** — 1주·2주차 등. 부작용 조기 발견
- **외부 근거 활용** — 유사 사례·논문·업계 사례. 신뢰도 ↑
- **노션 DB로 관리** — 가설 인벤토리 + 상태·결과 추적
- **가설 폐기도 학습** — 실패한 가설도 "왜 실패했나" 회고 → 다음 가설 정교화
- **포트폴리오 자산** — 검증된 가설은 케이스 스터디. 실패도 가치 있음

## 자주 하는 실수

- **모호한 가설** — "이거 좋아질 것" → 검증 불가
- **근거 없음** — "그냥 해보자" → 실패 시 학습 안 됨
- **Guardrail 누락** — Primary만 봄 → 부작용 놓침
- **성공 기준만, 실패 기준 없음** — 결과 모호 → 결정 못 함
- **통계적 유의성 무시** — 우연한 변동을 성과로 착각
- **너무 큰 가설** — "매칭 시스템 전체 개편" → 검증 불가, 작게 쪼개야
- **너무 작은 가설** — "버튼 색 변경" → 영향력 미미, 우선순위 ↓
- **ICE/RICE 점수 일관성 없음** — 가설마다 다른 기준 → 우선순위 무의미
- **검증 기간 너무 짧음** — 1주 → 표본 부족 → 무의미
- **중간 점검 없음** — 4주 끝까지 → 부작용 발견 늦음
- **부분 성공·실패 분류 모호** — "애매하게 됐다" → 다음 액션 결정 못 함
- **실패 가설 폐기·회고 안 함** — 학습 손실, 같은 실수 반복
- **포트폴리오 자산화 누락** — 검증된 가설 다음 프로젝트에서 처음부터
