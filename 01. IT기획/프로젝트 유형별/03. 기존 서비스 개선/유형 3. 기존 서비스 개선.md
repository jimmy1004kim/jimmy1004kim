## 정의

이미 운영 중인 서비스의 특정 지표·경험을 개선하는 일. 신규 개발과 가장 큰 차이는 **이미 사용자가 있고, 데이터가 쌓여 있다**는 점이다. 짐작이 아니라 데이터로 문제를 정의하고, 가설을 세우고, 실험으로 검증하는 사이클이 핵심.

## 발생 상황

- 핵심 지표 하락 (전환율, 잔존율, 매출 등)
- 특정 기능의 사용률이 기대 이하
- VOC(고객의 소리) 누적
- 경쟁사 대비 경험 격차 발생
- 데이터팀·CS팀에서 문제 제기

## 업무 흐름

```
문제 발견 → 데이터 분석 → 가설 수립 → 실험·개선 설계 → 개발 → 반영 → 성과 측정 → 반복
```

이 흐름은 **반복 사이클**이다. 다른 유형이 시작-종료가 있는 직선이라면, 이 유형은 원을 그리며 계속 돈다.

|단계|핵심 작업|
|---|---|
|문제 발견|KPI 모니터링, VOC 수집에서 신호 포착|
|데이터 분석|퍼널·코호트·세그먼트 분석으로 병목 식별|
|가설 수립|"이걸 바꾸면 이 지표가 이만큼 오를 것이다"|
|실험·개선 설계|A/B 테스트 설계 또는 일괄 적용 설계|
|개발|변경 영향도 고려해서 진행|
|반영|점진 배포(롤아웃) 또는 일괄 배포|
|성과 측정|가설 검증, KPI 변화 확인|
|반복|결과 기반으로 다음 사이클|

## 기획자 역할

- **지표 모니터링·문제 정의** — 정상 범위에서 벗어난 지표를 포착하고 문제로 정의
- **데이터 분석·인사이트 도출** — SQL이나 분석 도구로 직접 들여다보거나 분석가와 협업해서 병목 찾기
- **가설 수립** — 막연한 "개선" 대신 검증 가능한 가설 문장으로 표현
- **실험 설계** — A/B 테스트 가능한 영역인지 판단, 표본 크기·기간·지표 설정
- **변경 설계** — 기존 흐름·정책·화면의 어느 부분을 어떻게 바꿀지 명세
- **변경 영향도 분석** — 다른 기능에 미치는 영향 사전 확인 (회귀 방지)
- **개발 협업·반영** — 기존 코드와 충돌 최소화, 안전한 배포
- **성과 검증** — 가설이 맞았는지 데이터로 확인, 결과 공유
- **반복 사이클 운영** — 결과를 다음 가설로 연결

## 주요 산출물 (✅ = 필수)

### 분석·정의

- ✅ 문제 정의서 — 어떤 지표가 어떻게 이상한지
- ✅ 데이터 분석 리포트 — 병목·이탈 지점
- ✅ 가설 정의서 — 원인 가설·해결 가설
- ⬜ VOC 분석서
- ⬜ 경쟁사 비교 분석

### 개선 설계

- ✅ 개선 기획서 — 무엇을 어떻게 바꿀 것인가
- ✅ 기능 변경 정의서
- ✅ 화면 변경 정의서 (Before / After)
- ✅ 정책 변경 정의서
- ⬜ User Flow 수정안
- ⬜ IA 변경안
- ⬜ 실험 설계서 (A/B 테스트 — 가능한 경우)
- ⬜ 변경 영향도 분석서
- ⬜ 롤백 계획서

### 실행·검증

- ✅ QA 시나리오 / 회귀 테스트 체크리스트
- ✅ 이벤트 트래킹 추가·변경 정의 — 측정 가능해야 검증 가능
- ✅ 성과 분석 리포트 — 가설 검증 결과
- ⬜ 사용자 공지 자료 (큰 변경의 경우)
- ⬜ 개선 결과 보고서 — 적용 결과·인사이트·다음 사이클

## 특징

- **데이터가 출발점이자 종착점** — 시작도 데이터, 검증도 데이터
- **가설-실험-측정의 반복 구조** — 한 번에 끝나지 않음
- **기능 추가가 아니라 개선이 목적** — 새 기능을 더하는 게 아니라 기존 흐름을 다듬는 일
- **빠른 사이클이 중요** — 한 사이클이 너무 길면 학습이 안 됨
- **KPI로 성과가 분명히 평가됨** — 좋아졌는지 나빠졌는지 숫자로 나옴

## 자주 빠지는 함정

- 개선이 어느새 신규 기능 추가로 변질 — "이왕 손대는 김에"
- 측정 없는 끝맺음 — "느낌상 좋아진 것 같음"
- 회귀(Regression) — 새 변경이 기존 다른 기능을 깨뜨림
- A/B 테스트 표본·기간 부족 → 통계적으로 무의미한 결과로 결정
- 가설을 정량적으로 안 쓰고 "더 좋게" 같은 표현으로 흐림
