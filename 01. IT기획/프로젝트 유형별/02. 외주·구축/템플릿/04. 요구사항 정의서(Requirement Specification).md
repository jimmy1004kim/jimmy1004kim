## 이 문서는

고객의 **모든 요구사항을 추적 가능한 형태로 정리한 공식 문서**.

"고객이 무엇을 원하는가 → 그것을 어떤 기능·산출물로 충족할 것인가" 를 ID 단위로 추적한다.

다른 산출물과의 관계:

| 구분  | 제안서 / SoW | 요구사항 정의서                        | 기능 정의서 / 화면 정의서 |
| --- | --------- | ------------------------------- | --------------- |
| 단위  | 프로젝트 전체   | **요구사항 1건** (REQ-XXX)           | 기능 1개 / 화면 1개   |
| 깊이  | 무엇·왜 우리   | **무엇을 원하는가 (요구) + 어떻게 충족 (대응)** | 어떻게 작동 / 어디 어떻게 |
| 청중  | 의사결정자     | **양 당사자 합의**                    | 개발·디자인·QA       |
| 시점  | 계약 전      | Phase 1 (요구사항 수집·확정)            | Phase 2 (설계)    |
| 효력  | 설득 자료     | **검수 기준의 근거**                   | 개발의 근거          |

**핵심**: 요구사항 정의서는 **검수의 기준이 되는 문서**. 여기에 적힌 요구사항이 충족되면 검수 통과, 안 되면 검수 실패. SoW에 명시된 작업 범위의 세부.

### 요구사항의 4가지 유형

|유형|약어|의미|예시|
|---|---|---|---|
|**기능적 요구사항**|FR (Functional)|시스템이 무엇을 해야 하는가|"회원가입 가능", "결제 가능"|
|**비기능적 요구사항**|NFR (Non-Functional)|어떻게 작동해야 하는가 (성능·보안 등)|"응답 시간 3초 이내", "동시 사용자 1,000명"|
|**제약 조건**|CON (Constraint)|외부적·법적·기술적 제약|"Node.js 18 이상", "PCI-DSS 준수"|
|**비즈니스 요구사항**|BR (Business)|사업·운영 요구|"출시일 2027-02-01 절대 사수"|

요구사항 정의서는 이 4가지를 모두 다룬다.

### 요구사항 정의의 두 가지 출처

|출처|특징|작성 시점|
|---|---|---|
|**명시적 요구사항 (Explicit)**|RFP·고객 인터뷰에서 직접 언급|Phase 1 초기|
|**암묵적 요구사항 (Implicit)**|행간·관행·법적 의무 등|Phase 1 중기 (수주자가 발굴)|

좋은 수주자는 **암묵적 요구사항을 적극 발굴**한다. 그것이 차별화.

### 요구사항 추적 매트릭스 (RTM)

요구사항 → 기능 → 화면 → 테스트 케이스로 추적 가능해야 한다.

```
REQ-001 (회원가입 필요)
   ↓
FR-001 (회원가입 기능) + P-031 (회원가입 화면)
   ↓
TC-001 (회원가입 정상 테스트) + TC-002 (예외 테스트)
   ↓
검수 통과 / 실패 판단
```

이 추적 가능성(Traceability)이 외주 프로젝트의 신뢰 기반.

## 언제 만드나

- 계약 체결 후 Phase 1 (Discovery·요구사항) 단계
- 일반적으로 계약 후 첫 2~4주 내 v1.0 확정
- 변경 발생 시 (CR로 부속 갱신)
- 검수 직전 (검수 기준 확정용)

**기준**: SoW에 명시된 작업 범위를 **검수 가능한 항목 단위**로 분해하는 시점.

## 작성 절차

1. **RFP·계약서·SoW 정독** — 명시적 요구사항 추출
2. **고객 인터뷰** — 핵심 이해관계자 인터뷰 (5~10명)
3. **현황 분석 (As-Is)** — 현재 시스템·업무 흐름
4. **요구사항 도출** — 명시 + 암묵 모두
5. **분류** — FR·NFR·CON·BR
6. **ID 부여 + 우선순위** — REQ-XXX 부여
7. **검수 기준 정의** — 각 요구사항이 충족되었음을 어떻게 판단할지
8. **RTM 작성** — 요구사항 ↔ 기능·화면·테스트 매핑
9. **이해관계자 리뷰** — 모든 핵심 이해관계자 확인
10. **양 당사자 승인** — 정식 발효
11. **변경 관리** — CR 발생 시 갱신

## 1. 프로젝트 배경

StyleHaus는 30~40대 여성 캐주얼 의류 브랜드로, 2018년 설립 이래 오프라인 매장 6개와 도매 채널(백화점·온라인 셀러) 중심으로 운영. 연 매출 200억, 도매 비중 75%. 최근 3년 도매 의존도·마진율 압박이 심화되어 자사몰 신규 구축을 통한 D2C 채널 확보 필요.

## 2. 프로젝트 목적

1. 자사몰 매출 비중 30% 달성 (3년 내)
2. 도매 의존도 완화 → 마진율 향상
3. 고객 데이터 직접 확보 → CRM 기반 구축
4. 2027-02-01 신규 라인 런칭과 동시 오픈

## 3. 프로젝트 범위

### 3.1 In Scope

- PC + Mobile Web 자사몰 (47개 기능)
- 관리자 시스템 (15개 화면)
- 결제 통합 (토스·네이버·카카오), 본인 인증 (NICE), 배송 (CJ대한통운)
- 6개 오프라인 매장 재고 연동
- 운영 매뉴얼·교육 2회

### 3.2 Out of Scope

- 모바일 앱 (v2)
- 해외 진출·다국어 (v2)
- AI 추천·개인화 (v2)
- 도매 채널 통합
- 회계·세무 시스템 연동

## 5. As-Is / To-Be

### 5.1 As-Is

- **시스템**: 자사몰 없음. 도매 플랫폼(외부)·매장 POS·엑셀로 운영
- **업무**: 재고는 매장별 엑셀·수기. 매장 간 재고 이동은 전화·문자
- **데이터**: 고객 데이터 부재 (회원제 없음)
- **페인**:
    - 도매 의존도 75% → 마진율 압박
    - 고객 데이터 부재 → 마케팅·재구매 유도 불가
    - 매장 재고 통합 안 됨 → 품절·재고 과잉 빈발
    - 신규 라인 출시 채널 부재

### 5.2 To-Be

- **시스템**: 자사몰 (PC·Mobile) + 관리자 + 통합 재고 시스템
- **업무**: 자사몰·관리자에서 주문·재고·회원·CS 통합 운영
- **데이터**: 회원 데이터 직접 확보. 매장별 재고 실시간 연동
- **개선**:
    - D2C 채널 확보 → 자사몰 매출 비중 30% (3년)
    - 회원 데이터 → CRM·재구매 마케팅
    - 통합 재고 → 품절·과잉 감소
    - 신규 라인 즉시 출시 가능

### 5.3 As-Is → To-Be 요약

|영역|As-Is|To-Be|
|---|---|---|
|판매 채널|도매·매장|도매·매장 + 자사몰|
|재고 관리|매장별 엑셀|통합 자동 (자사몰 + 매장 6개)|
|고객 데이터|없음|회원 시스템·CRM 기반|
|신규 라인 출시|도매 플랫폼·매장|+ 자사몰 동시|

## 6. 기능적 요구사항 (FR) — 발췌 47개 중 5개

### FR-001. 회원가입 (이메일·소셜)

|항목|내용|
|---|---|
|ID|FR-001|
|분류|기능적 요구사항|
|우선순위|🔴 Critical|
|상태|🟢 Approved|
|출처|RFP 명시 + 운영팀 인터뷰 (2026-09-10)|
|출처 상세|RFP 3.2조 + 박운영 인터뷰 "회원 데이터 확보가 가장 시급"|

**요구사항 내용**: 사용자는 이메일 또는 소셜(카카오·네이버) 계정으로 회원가입을 할 수 있어야 한다. 본인 인증(NICE) 완료 후 회원 활성화.

**배경·이유**: 회원 데이터 확보가 본 프로젝트의 핵심 목적 중 하나. 14세 이상 본인 인증 의무 (개인정보보호법).

**충족 기준 (Acceptance Criteria)**:

- AC-1. 이메일·카카오·네이버 3가지 가입 방식 모두 지원
- AC-2. 본인 인증 (NICE) 완료해야 가입 완료 처리
- AC-3. 가입 완료 시 환영 이메일 발송
- AC-4. 동일 이메일 중복 가입 차단
- AC-5. 14세 미만 가입 차단 (법정 대리인 동의 절차 별도, 본 프로젝트 범위 외 — Out of Scope)

**관련 산출물**:

- 기능 ID: F-001
- 화면 ID: P-031 (이메일 가입), P-032 (소셜 가입)
- 테스트 케이스: TC-001 ~ TC-005

**비고**:

- 14세 미만 처리는 v2에서 검토 (별도 견적)

### FR-030. 통합 재고 관리 (자사몰 + 오프라인 6개 매장)

|항목|내용|
|---|---|
|ID|FR-030|
|분류|기능적 요구사항|
|우선순위|🔴 Critical|
|상태|🟢 Approved|
|출처|RFP + 운영팀·매장 매니저 인터뷰|
|출처 상세|RFP 4.5조, 매장 매니저 6명 인터뷰 (2026-09-15)|

**요구사항 내용**: 자사몰 재고는 오프라인 6개 매장의 재고와 통합 관리되어야 하며, 자사몰·매장 양쪽에서 실시간으로 재고 변동이 반영되어야 한다.

**배경·이유**:

- As-Is에서 재고 불일치로 인한 품절·과잉이 매월 발생
- 자사몰 도입 후에도 재고 분리되면 동일 문제 반복
- 매장 POS 시스템(현재 사용 중)과 자사몰 재고 시스템 연동 필수

**충족 기준**:

- AC-1. 자사몰에서 주문 발생 시 → 매장 재고 차감 (1분 이내 반영)
- AC-2. 매장 POS에서 판매 발생 시 → 자사몰 재고 차감 (1분 이내 반영)
- AC-3. 자사몰 상품 페이지에 "전체 재고" + "이 매장 재고" 표시 (사용자가 매장 선택 시)
- AC-4. 관리자 시스템에서 매장별 재고 현황 실시간 조회
- AC-5. 재고 일치율 99.5% 이상 (월 1회 정합성 검증)

**관련 산출물**:

- 기능 ID: F-030
- 화면 ID: P-110 (상품 상세), P-310 (관리자 재고 관리)
- 테스트 케이스: TC-050 ~ TC-058

**비고**:

- 매장 POS 시스템은 외부 시스템 (포스소프트). API 연동 가능 여부 확인 완료 (2026-09-20, POS 사 협의)
- 폴링 방식 (1분 주기) 합의. Webhook 방식은 POS 사 미지원

## 작성 팁

- **명시 + 암묵 모두** — RFP만 보면 안 됨. 인터뷰·관행·법적 의무까지 발굴
- **요구사항 1건 = 명확한 1개 요구** — "회원 시스템" ❌ (너무 광범위), "이메일·소셜·본인인증 가입" ⭕
- **충족 기준 (Acceptance Criteria) 필수** — 모호하면 검수 분쟁. "잘 작동" ❌, "P95 3초 이내" ⭕
- **ID 명명 규칙 일관** — FR/NFR/CON/BR Prefix. 도중에 바꾸지 말 것
- **우선순위 4단계** — Critical/High/Medium/Low. 모두 Critical은 무의미
- **출처 기록** — RFP·인터뷰·회의·암묵 등. 변경 시 추적 가능
- **NFR도 측정 가능하게** — "성능 좋게" ❌, "P95 3초 이내" ⭕
- **법적 의무 빠뜨리지 말기** — 개인정보보호법·전자상거래법 등 제약 조건으로 명시
- **RTM 작성** — 요구사항 ↔ 기능 ↔ 화면 ↔ 테스트 매핑. 검수의 근거
- **양 당사자 승인** — 정식 서명·날인. 이후 변경은 CR
- **변경은 CR로** — 발효 후 임의 변경 X. CR 절차로
- **이해관계자 인터뷰 5~10명** — 의사결정자·사업·운영·IT·실사용자·법무. 다양한 출처
- **As-Is / To-Be 시각화** — 표로 비교. 변화가 명확하게 보임
- **포트폴리오 자산** — 잘 만든 요구사항 정의서는 다음 수주에서 80% 재사용

## 자주 하는 실수

- **명시적 요구만** — RFP만 보고 작성 → 행간·암묵·법적 의무 누락 → 검수 단계 분쟁
- **요구사항 너무 광범위** — "회원 시스템" 한 줄 → 검수 기준 모호
- **충족 기준 누락** — "이게 충족됐다고 어떻게 판단?" 답 못 함
- **NFR 모호** — "성능 좋게" → 측정 불가 → 검수 분쟁
- **법적 의무 누락** — 개인정보보호법·전자상거래법 안 적음 → 출시 후 위반
- **RTM 누락** — 요구사항 ↔ 기능 ↔ 테스트 추적 안 됨 → 검수 못 함
- **이해관계자 부족** — 의사결정자만 인터뷰 → 운영·실사용자 요구 누락
- **As-Is 누락** — To-Be만 적음 → 변화 안 보임
- **양 당사자 승인 없음** — 임의 작성 → 검수 단계 "이거 우리가 합의 안 했는데" 분쟁
- **변경은 임의로** — CR 절차 없이 갱신 → 책임 모호
- **암묵적 요구 발굴 안 함** — 명시만 충족 → 차별화 손실, 다음 수주 안 됨
- **출처 기록 안 함** — 누가·언제 요구했는지 모름 → 변경 시 추적 불가
- **포트폴리오 자산화 누락** — 다음 수주에서 처음부터 작성

## 작성 후 체크

- [ ] 메타 (프로젝트·버전·작성자·승인자) 완료되었는가
- [ ] 프로젝트 배경·목적·범위가 명확한가
- [ ] 이해관계자 인터뷰 (5~10명) 완료되었는가
- [ ] As-Is·To-Be 명시되었는가
- [ ] 요구사항 분류 (FR/NFR/CON/BR) 명확한가
- [ ] 모든 FR에 충족 기준 (Acceptance Criteria) 있는가
- [ ] 모든 NFR이 측정 가능한 형태인가
- [ ] 법적 의무 (개인정보보호법·전자상거래법 등) 포함되었는가
- [ ] 출처 (RFP·인터뷰·회의·암묵) 모든 요구사항에 명시되었는가
- [ ] 우선순위 (Critical/High/Medium/Low) 부여되었는가
- [ ] RTM (요구사항 ↔ 기능 ↔ 화면 ↔ 테스트) 작성되었는가
- [ ] 가정·전제 명시되었는가
- [ ] 양 당사자 승인·서명 완료되었는가
- [ ] 변경 이력 누적되고 있는가
- [ ] 검수 기준의 근거로 활용 가능한가
