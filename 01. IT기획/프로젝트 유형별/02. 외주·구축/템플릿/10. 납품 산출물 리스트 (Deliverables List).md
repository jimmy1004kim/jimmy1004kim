## 이 문서는

외주 프로젝트가 **고객에게 납품해야 할 모든 산출물의 인벤토리**.

다른 산출물과의 관계:

|구분|SoW (3.1 Deliverables)|납품 산출물 리스트|인계 확인서|
|---|---|---|---|
|단위|계약 첨부 산출물 명세|**전체 산출물 인벤토리 + 진행 상태**|인계 시점 확인|
|깊이|계약 단위 (12~15개)|**세부 모든 산출물 (60~150개)**|인계 항목별 체크|
|시점|계약 시|**프로젝트 전 기간 (살아있는 문서)**|인계 시점|
|변경|CR로 갱신|**수시 갱신** (산출물 추가 시)|1회 서명|

**핵심**: 납품 산출물 리스트는 **"우리가 무엇을 만들고 무엇을 인계하는가"의 살아있는 인벤토리**. SoW의 산출물(D-001~012)은 큰 카테고리, 본 문서는 그 아래 **세부 산출물 모두**.

### 산출물 리스트 vs 산출물 인덱스 (C-12)

|구분|공통 산출물 인덱스 (C-12)|T2 납품 산출물 리스트|
|---|---|---|
|청중|**내부 (작업·관리)**|**고객 + 내부** (인계 대상)|
|강조|작업 산출물 관리|**계약 산출물·인계 대상**|
|변경 영향|작업 영향|**계약·결제 영향**|
|사용 시점|작업 중|**계약·인계 시점**|

같이 운영. 산출물 인덱스(내부 관리) + 납품 산출물 리스트(외부 합의)는 같은 데이터·다른 뷰.

### 산출물의 4가지 카테고리

|카테고리|예시|인계 방법|
|---|---|---|
|**기획·설계 문서**|요구사항·기능·화면·데이터·정책 정의서, 회의록|PDF + 노션 이전|
|**개발 산출물**|소스코드·DB 스키마·API 명세·인프라 구성|GitHub ownership 이전, 문서|
|**디자인 산출물**|Figma 시안·디자인 시스템·이미지·아이콘 원본|Figma 이전·원본 파일|
|**운영 산출물**|운영 매뉴얼·사용자 가이드·관리자 가이드·교육 자료|PDF·동영상|
|**계정·라이선스**|AWS·도메인·PG·인증·외부 API 등|ownership 이전|

본 문서는 모두 포함.

## 언제 만드나

- 요구사항 정의서·SoW 발효 직후 (Phase 1 종료)
- 산출물 추가·삭제 시 수시 갱신
- 인계 직전 (인계 확인서의 기준)

**기준**: SoW에 명시된 산출물을 **세부 항목 단위로 펼치는 시점**.

## 어떤 툴로

|툴|추천도|이유|
|---|---|---|
|**노션 DB**|⭐ 강력 추천|산출물 1개 = 1행. 진행 상태·담당자·인계 방법 필터|
|Excel·Google Sheets|추천|인쇄·검수 시 빠른 활용|
|Jira|보조|개발 산출물만|
|Confluence|보조|회사 표준이면|

**최적**: 노션 DB (관리) + Excel·PDF (계약 첨부·인계 시점).

## 표준 구성

```
1. 메타 (프로젝트·버전·총 산출물 수)
2. 산출물 분류 체계
3. 산출물 ID 명명 규칙
4. 산출물 리스트 (전체 표)
5. 카테고리별 합계·진행률
6. 인계 절차·방법
7. 변경 이력
```

## 들어가야 할 것

- 메타 (프로젝트·버전·총 산출물 수)
- 산출물 분류·ID 명명 규칙
- 산출물 1개당: ID·이름·카테고리·상태·담당자·납품 시점·인계 방법·인계 여부·검수 기준 링크
- 카테고리별 진행률
- 인계 절차·방법
- 변경 이력

## 작성 절차

1. **SoW 기반 추출** — SoW의 산출물 항목을 펼침
2. **카테고리 분류** — 5개 카테고리

4. **납품 시점 매핑** — 어느 마일스톤에 납품할지
5. **인계 방법 명시** — GitHub·노션·Figma·계정 이전 등
6. **검수 기준 연결** — 검수 기준서 항목 매핑
7. **이해관계자 합의** — 양 당사자 합의
8. **수시 갱신** — 산출물 추가·삭제 시
9. **인계 시점 검증** — 인계 확인서 작성 시 기준으로 활용

## 인계 절차·방법 — 발췌

### GitHub 저장소 ownership 이전 (DEV-001~003·005)

**Step**:

1. **사전 협의** (인계 1주 전): StyleHaus GitHub 조직 (`github.com/stylehaus`) 생성·확인
2. **저장소 transfer 실행**: BuildCo Owner → StyleHaus Owner로 transfer
3. **권한 셋업**: StyleHaus 측 admin·메인테이너 지정
4. **CI/CD 재연결**: GitHub Actions·시크릿 재설정
5. **검증**: StyleHaus가 저장소 admin 권한 + 빌드·배포 정상 작동 확인

**소요 시간**: 저장소당 약 1시간 (협의 + 실행 + 검증)

### AWS 계정 ownership 이전 (ACC-001)

**Step**:

1. **사전 협의** (인계 2주 전): StyleHaus IT 담당 (정IT)과 인계 절차·일정 합의
2. **Root 이메일 변경**: BuildCo 이메일 → StyleHaus 이메일 (handover@stylehaus.kr)
3. **결제 카드 변경**: BuildCo 카드 → StyleHaus 카드 (사전 등록)
4. **계정 별칭·연락처 변경**
5. **IAM 사용자 정리**: BuildCo 사용자 제거, StyleHaus 사용자 추가
6. **검증**: StyleHaus 단독 로그인 + 결제 카드 작동 확인

**소요 시간**: 약 1주 (사전 협의·실행·검증 포함)

**주의**:

- 결제 카드 변경 전에 BuildCo 카드 결제 잔액 정산 필요
- 인계 시점 이전 비용은 BuildCo 부담, 이후는 StyleHaus 부담 (분리 명시)

### Figma 파일 이전 (DSN-001~018)

**Step**:

1. **사전 협의**: StyleHaus Figma 조직 (`stylehaus`) 확인
2. **Move to Organization**: BuildCo workspace → StyleHaus organization
3. **권한 셋업**: StyleHaus 디자이너에게 admin 권한
4. **검증**: StyleHaus가 파일 편집·export 가능 확인
