## 이 문서는

신규 서비스를 **아이디어부터 출시·운영 전환까지** 진행하는 표준 절차.

"문제 정의에서 정식 출시까지 어떤 순서로, 어떤 산출물을 만들고, 어떤 게이트를 통과하는가" 를 정리한다.

다른 워크플로우와의 관계:

|워크플로우|다루는 범위|
|---|---|
|**새 프로젝트 시작 워크플로우** (공통)|프로젝트 착수 첫 1주 절차 (모든 유형 공통)|
|**신규 서비스 개발 표준 절차** (T1, 본 문서)|신규 서비스 전체 라이프사이클 (이 워크플로우 안에서 새 프로젝트 시작 워크플로우 호출)|
|**MVP 정의 절차** (T1)|신규 서비스 절차 중 "범위 정의" 단계의 세부 절차|
|**출시 체크리스트** (T1)|신규 서비스 절차 중 "출시" 단계의 세부 체크|
|**프로젝트 종료 워크플로우** (공통)|프로젝트 닫는 절차 (모든 유형 공통)|

**핵심**: 본 워크플로우는 **신규 서비스 라이프사이클의 큰 흐름**. 세부 절차는 다른 워크플로우와 산출물로 분기.

## 언제 사용하나

- 신규 서비스 프로젝트 착수 시점
- 신규 라인·신사업 추진 시점
- 본 절차를 처음 보는 새 PM·PO에게 가이드 제공 시
- 진행 중 "지금 어느 단계인지" 확인이 필요할 때
- 회고 시점에 절차 준수 점검

## 어떤 툴로

|툴|추천도|이유|
|---|---|---|
|**노션**|⭐ 추천|단계별 페이지·체크리스트·산출물 링크|
|Confluence|추천|회사 표준이면|
|Jira (Epic·Phase 매핑)|보조|작업 추적|

**팁**: 노션에 신규 서비스 프로젝트 폴더 만들 때 본 워크플로우의 Phase 구조를 그대로 폴더 구조로 가져갈 수도 있음.

## 전체 라이프사이클 (큰 그림)

```
Phase 0. Discovery
   ↓ Gate 1: 추진 결정
Phase 1. Definition
   ↓ Gate 2: 본격 설계 진입
Phase 2. Design
   ↓ Gate 3: 개발 착수
Phase 3. Build
   ↓ Gate 4: QA 진입
Phase 4. Validate
   ↓ Gate 5: 베타 출시
Phase 5. Launch
   ↓ Gate 6: 정식 출시
Phase 6. Operate
   ↓
(유형 3 - 기존 서비스 개선 사이클로 전환)
```

**6개 Phase + 6개 Gate**. 각 Gate는 다음 Phase 진입 가능 여부를 판단하는 의사결정 지점.

## 각 Phase 한눈에

|Phase|기간|핵심 활동|핵심 산출물|
|---|---|---|---|
|0. Discovery|2~6주|문제·시장·사용자 탐색|서비스 컨셉서, 시장 분석, 페르소나|
|1. Definition|2~4주|무엇을 만들지 정의|PRD, MVP 범위 정의서, 릴리즈 계획|
|2. Design|3~6주|어떻게 만들지 설계|IA, User Flow, 기능·화면·정책·데이터 정의서|
|3. Build|6~16주|실제 구현|코드, API, 이벤트 트래킹, QA 시나리오|
|4. Validate|2~4주|검증·안정화|QA 결과, 베타 사용자 피드백, 출시 체크리스트|
|5. Launch|1~2주 (출시 시점)|시장 진입·공개|출시 발표, 모니터링·운영 준비|
|6. Operate|지속|운영·개선|회고, 자산화, 다음 사이클 진입|

# 🔲 양식 — 단계별 체크리스트

## Phase 0. Discovery (문제·시장·사용자 탐색)

### 목표

**"우리가 풀려는 문제가 진짜 존재하는가, 풀 만한 가치가 있는가"** 검증

### 핵심 활동

- [ ] 문제 가설 정의 (누구의 어떤 문제)
- [ ] 시장·경쟁 분석
- [ ] 사용자 인터뷰 (15~30건)
- [ ] 페르소나·JTBD 정의
- [ ] 서비스 컨셉서 초안
- [ ] Riskiest Assumption 식별

### 핵심 산출물

- [ ] 서비스 컨셉서 v0.1~v1.0
- [ ] 시장·경쟁 분석서
- [ ] 페르소나 (1~3개)
- [ ] 사용자 인터뷰 노트
- [ ] (선택) JTBD 정의서

### 이해관계자 활동

- [ ] 의사결정자·경영진 1차 공유
- [ ] 핵심 팀 (개발·디자인·마케팅) 초기 의견 청취

### Gate 1: 추진 결정

이 단계 종료 시 다음 질문에 답해야 한다:

- [ ] 문제가 실재하고 풀 가치가 있는가
- [ ] 우리가 풀 수 있는가 (역량·리소스)
- [ ] 우리만의 차별화 포인트가 있는가
- [ ] Riskiest Assumption이 식별되었고 검증 경로가 있는가
- [ ] 비즈니스 모델 윤곽이 있는가

**결과**: 🟢 추진 / 🟡 보류·재검토 / 🔴 폐기

## 작성 팁

- **Gate를 엄격히 운영** — 게이트 통과 없이 다음 Phase 진입 X. "대충 됐으니 다음" 가장 흔한 실패
- **Phase 0(Discovery) 충분히** — 신규 서비스 실패의 70%는 Discovery 부실. 4~8주 충분히
- **다른 워크플로우와 산출물로 분기** — 본 워크플로우는 큰 흐름. 세부는 새 프로젝트 시작·MVP·출시 체크리스트 등으로
- **공통 워크플로우 활용** — 새 프로젝트 시작·종료·자산화·인터뷰 등은 공통에서 가져다 씀
- **Phase 별 시간 비율 균형** — Phase 2(Design) 짧고 Phase 3(Build) 길면 폭증. 대략 1:1:1:1 + Discovery 추가
- **Gate 결과를 ADR로** — 추진·보류·폐기 결정은 ADR 작성. 결정의 변천 기록
- **유연한 적용** — 작은 신규 기능엔 Phase 압축 가능. 큰 신사업엔 더 늘려서
- **Phase 0 → Phase 6은 1~2년** — 신규 서비스 라이프사이클은 길다. 단거리 경주가 아닌 마라톤
- **운영 전환(Phase 6)이 진짜 시작** — 출시는 검증의 시작점. 운영 단계에서 진짜 가치 결정
- **변경 시 PRD부터** — 어떤 단계에서든 변경 발생하면 PRD부터 갱신. 단일 진실 소스
- **베타 운영 충분히** — Phase 5 베타 단계는 최소 3개월. 가설 검증의 핵심
- **포트폴리오 가치** — 신규 서비스 전체 라이프사이클을 1회 경험하면 PM·PO의 가장 큰 자산

## 자주 하는 실수

- **Discovery 건너뛰기** — 아이디어 → 바로 PRD → 개발 → 출시 실패. 가장 흔한 실패 패턴
- **Gate 무시** — 게이트 통과 없이 다음 단계로. 게이트 의미 사라짐
- **Phase 비율 불균형** — Design 1주 + Build 12주 → 설계 부실 → Build 폭증
- **PRD 없이 Build 진입** — PRD 합의 없이 개발 → 매번 다른 방향
- **MVP 정의 모호** — MVP가 사실상 v1 → 일정·예산 폭증
- **베타 단계 생략** — Closed Beta 없이 바로 Public → 가설 미검증, 출시 후 발견
- **운영 전환 누락** — Phase 6 없이 "출시했으니 끝" → 개선 사이클 안 돔
- **단계 간 산출물 단절** — PRD와 기능 정의서 따로, 화면 정의서 따로 → 정합성 깨짐
- **Gate 결정 기록 없음** — "추진하기로 했다"만 회의록에. ADR로 기록 필수
- **변경 관리 부재** — Build 중 변경이 들어와도 PRD 안 갱신 → 출시 후 정합성 깨짐
- **회고·자산화 누락** — Phase 6에서 회고만 하고 자산화 안 함 → 다음 신규 서비스에서 또 처음부터
- **포트폴리오 정리 안 함** — 1년 라이프사이클 끝났는데 케이스 스터디 없음 → 가장 비싼 자산 손실
