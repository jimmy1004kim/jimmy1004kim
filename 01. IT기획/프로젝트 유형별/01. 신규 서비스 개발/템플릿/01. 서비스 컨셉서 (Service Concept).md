# T1. 서비스 컨셉서 (Service Concept)

## 이 문서는

새 서비스 아이디어를 **한 장으로 압축한 출발선 문서**.

"이게 무슨 서비스인가, 누구를 위한 건가, 왜 만들어야 하나, 다른 것과 뭐가 다른가" 를 정리한다.

PRD와 헷갈리기 쉬운데 둘은 위치가 다르다.

| 구분  | 서비스 컨셉서            | PRD               |
| --- | ------------------ | ----------------- |
| 시점  | 아이디어 단계            | 컨셉 확정 후           |
| 길이  | 1~2페이지             | 10~30페이지          |
| 청중  | 의사결정자·투자자·동료 (설득용) | 개발·디자인·QA (작업 기준) |
| 깊이  | "왜·무엇" 중심          | "어떻게·어디까지" 중심     |
| 목적  | 추진할지 말지 결정         | 구체적으로 어떻게 만들지     |

**핵심**: 컨셉서가 통과해야 PRD를 쓴다. 컨셉서 없이 PRD부터 쓰면 흔들린다.

## 언제 만드나

- 새 서비스 아이디어가 떠올랐을 때 (가장 먼저)
- 신사업 검토·투자 결정을 위한 사전 자료가 필요할 때
- 팀에 새 서비스 비전 공유가 필요할 때
- PRD 작성 전 합의 단계

**기준**: "이 아이디어 추진할까 말까" 를 묻는 자리에 가져갈 문서.

## 어떤 툴로

|툴|추천도|이유|
|---|---|---|
|**노션**|⭐ 추천|텍스트·표·이미지 자유, 검색·누적|
|**Figma / FigJam**|추천|시각화 비중 클 때 (Lean Canvas 등)|
|PowerPoint / Keynote|보조|외부 발표·투자 제안용|
|Google Docs|보조|코멘트 협업 필요 시|

**팁**: 짧은 만큼 시각적 요소가 효과적. 한 페이지 인포그래픽 형태도 좋음.

## 들어가야 할 것

- 서비스 한 줄 정의
- 누구를 위한가 (타겟·페르소나 윤곽)
- 어떤 문제를 푸나
- 어떻게 풀 것인가 (솔루션 개요)
- 왜 우리가? (차별화 / 기회)
- 어떻게 돈을 버나 (비즈니스 모델 윤곽)
- 핵심 지표 (성공의 정의)
- 리스크·가정

## 작성 절차

1. **문제 먼저** — 솔루션부터 시작하지 말 것. "누구의 어떤 문제인가" 부터
2. **한 줄 정의 만들기** — 가장 어려운 단계. 한 줄에 압축되어야 명확
3. **타겟·차별화 명시** — "누구를 위한, 어떤 점에서 다른"
4. **시각적 요소 1개 이상** — 컨셉 이미지, Lean Canvas, 또는 Before/After
5. **리스크·가정 솔직히** — "지금 모르는 것" 명시. 솔직할수록 신뢰
6. **검토·합의** — 의사결정자 + 동료에게 의견 받기
7. **결정 → PRD 단계 진입 또는 폐기**

# 📌 예시 — TalentMatch 서비스 컨셉서

> 가상 사례. T1 시리즈 전체에서 이 케이스를 일관되게 사용

## 메타

|항목|내용|
|---|---|
|서비스명 (가칭)|**TalentMatch**|
|작성자|홍길동 (PO)|
|작성일|2026-06-01|
|버전|v0.3|
|상태|🟡 검토 중 (6/15 의사결정 회의 예정)|

## 1. 한 줄 정의

**IT 프리랜서와 단기·중기 IT 프로젝트를 가진 기업을 매칭하는 플랫폼.** 기존 프리랜서 마켓(크몽·숨고)이 디자인·일러스트 중심인 것과 달리, 개발자·기획자·PM 등 **IT 직무에 특화**되어 있고, **포트폴리오 자동 검증**과 **에스크로 결제**로 양쪽의 신뢰 비용을 낮춘다.

## 2. 누구를 위한가

### 주요 타겟

- **1차 타겟**: 시리즈 A~B 스타트업 (10~50명 규모). 풀타임 채용은 부담스럽고, 단기·중기 IT 인력이 필요한 회사
- **2차 타겟**: 경력 3년+ IT 프리랜서 (개발자·기획자·PM·디자이너)

### 페르소나 윤곽

|항목|페르소나 A (기업 측)|페르소나 B (프리랜서 측)|
|---|---|---|
|누구|박상준 (34세, 스타트업 CTO, 직원 22명)|김지영 (32세, 프리랜서 풀스택 개발자, 5년차)|
|일상|신규 프로젝트마다 3~6개월 추가 인력 필요, 정규직 채용은 부담|프로젝트 단위 일감, 평균 3개월 사이클로 다음 프로젝트 탐색|
|페인|사람인·잡코리아는 정규직 위주. 지인 네트워크에 의존 → 항상 인력 풀 부족|다음 프로젝트 끊기지 않을지 불안. 단가 협상도 매번 처음부터|
|현재 해결책|지인 추천, 슬랙 커뮤니티, 위시켓·프리모아 게시판|위시켓·프리모아 등록, 지인 소개, 링크드인 메시지|

## 3. 어떤 문제를 푸나

- **문제 정의**: IT 직무에 특화된 프리랜서 매칭 플랫폼이 없어, 기업과 프리랜서 모두 매칭 비용이 높고 신뢰 부족으로 거래가 성사되기 어렵다.
- **이 문제의 크기**:
    - 국내 IT 프리랜서 추정 약 12만명 (KOSA, 2024)
    - 스타트업·중소 IT 기업의 단기 프로젝트 채용 수요 연 추정 8만 건
    - 기존 매칭 플랫폼(위시켓 등) 점유율 30% 미만 → 70%가 비공식 채널
- **왜 지금 풀어야 하나**:
    - 코로나 이후 원격 협업 정착 → 프리랜서 활용 거부감 ↓
    - IT 인력난 심화 → 정규직 대안으로 단기 프리랜서 수요 ↑
    - 에스크로·전자 계약 인프라 성숙 → 결제·계약 자동화 가능

## 4. 어떻게 풀 것인가

### 솔루션 개요

기업이 프로젝트를 등록하면 **AI 매칭**으로 적합한 프리랜서 5명 추천. 프리랜서의 **GitHub·포트폴리오 URL을 자동 검증**해 가짜 이력 차단. 계약·결제는 **에스크로**로 분쟁 방지.

### 핵심 기능

1. **프로젝트 등록 & AI 매칭** — 기업이 직무·기간·예산 입력 → 추천 5명
2. **포트폴리오 자동 검증** — GitHub·노션·블로그 URL 입력 → 활동 데이터 자동 추출·인증 마크 부여
3. **에스크로 결제** — 마일스톤 단위 결제, 양쪽 합의 시 자금 이체
4. **표준 계약서 자동 생성** — IT 프리랜서 표준 계약서 템플릿 기반 자동 생성
5. **분쟁 조정** — 분쟁 시 플랫폼이 1차 중재

### 사용자 시나리오

박상준 CTO가 "백엔드 개발자 1명, 3개월, 월 700만원" 으로 프로젝트 등록 → AI가 GitHub 활동·기술 스택 매칭해 후보 5명 추천 → 박상준이 김지영 선택, 화상 면접 → 표준 계약서 자동 생성, 에스크로로 1차 마일스톤 결제 → 김지영이 결과물 제출, 박상준 승인 → 자금 자동 이체.

## 5. 왜 우리가

### 기존 대안

|대안|장점|한계|
|---|---|---|
|위시켓|국내 인지도, IT 프로젝트 비중 일부|견적 입찰 방식 → 매칭 비효율, 포트폴리오 검증 약함|
|크몽·숨고|사용자 풀 큼|디자인·일러스트 중심, IT 전문성 부족|
|링크드인|글로벌 인재 풀|직접 컨택 부담, 결제·계약 없음|
|지인 네트워크|신뢰 ↑|풀 작음, 확장 불가|

### 우리의 차별점

- **IT 직무 특화** — 위시켓·크몽은 전 직무, 우리는 IT만 (깊이 ↑)
- **포트폴리오 자동 검증** — 다른 플랫폼은 자기 신고 기반, 우리는 GitHub·블로그 활동 데이터로 자동 검증
- **에스크로 + 표준 계약서** — 분쟁 방지 인프라 기본 제공 (위시켓도 일부 있지만 표준 계약서 자동화는 없음)

### Unfair Advantage

- 창업자가 5년차 풀스택 개발자 + 스타트업 CTO 경험 → 양쪽 페인 직접 체험
- IT 개발자 커뮤니티 (15만명 규모) 네트워크 보유 → 초기 프리랜서 풀 확보 가능

## 6. 어떻게 돈을 버나

- **수익 구조**: 거래액의 8% 플랫폼 수수료 (기업 측 부담 5% + 프리랜서 측 부담 3%)
- **단가 수준**: 평균 프로젝트 단가 1,500~3,000만원 → 건당 수수료 120~240만원
- **유료 전환 가설**:
    - 기업: 채용 대비 70% 비용 절감 효과 (정규직 1인 연봉 6천 + 4대보험 등 vs 단기 프리랜서 2~3천)
    - 프리랜서: 위시켓 평균 견적 입찰 5건 중 1건 성공 → 우리는 매칭 추천 5건 중 2건 성공 가설
- **추가 수익**: 프리미엄 검증 마크 (월 구독), 우선 노출 광고 (프리랜서용)

## 7. 성공의 정의

### 핵심 지표 (NSM)

**"성공적으로 계약 완료된 프로젝트 수 (월간)"** — 단순 가입자가 아닌 실제 거래 완료가 가치의 본질

### 단계별 목표

|시점|정량 목표|
|---|---|
|베타 출시 후 3개월|계약 완료 30건/월, 거래액 5억/월|
|정식 출시 후 6개월|계약 완료 200건/월, 거래액 30억/월|
|1년 후|계약 완료 500건/월, 거래액 80억/월, 수수료 매출 6.4억/월|

## 8. 리스크·가정

### 가장 큰 가정 (Riskiest Assumption)

**"IT 프리랜서 시장의 70%가 비공식 채널로 매칭된다는 점이, 플랫폼이 풀 수 있는 문제다."**

이게 사실이 아니면 (예: 비공식 채널이 신뢰·지인 기반이라 플랫폼화 자체가 불가능하다면) 서비스 성립 어려움. **5월 ~ 6월 사용자 인터뷰 30건으로 검증 필요.**

### 알려진 리스크

|#|리스크|영향|대응 방향|
|---|---|---|---|
|1|양면 시장(Chicken & Egg) — 프리랜서 없으면 기업 안 옴, 기업 없으면 프리랜서 안 옴|매우 큼|초기 6개월 프리랜서 측 수수료 면제, 창업자 네트워크로 시드 풀 100명 사전 확보|
|2|위시켓 등 기존 플레이어의 IT 특화 모방|큼|검증 시스템·커뮤니티 자산으로 진입 장벽 구축|
|3|분쟁 시 플랫폼 책임 범위 모호|중|표준 계약서에 분쟁 조정 절차 명시, 법무 자문|

## 작성 팁

- **솔루션보다 문제 먼저** — "이런 서비스 만들고 싶다"가 아니라 "이런 문제가 있다"부터. 문제가 약하면 솔루션도 흔들림
- **한 줄 정의에 가장 시간 들이기** — "(타겟)을 위한 (문제)를 푸는 (종류) 서비스. 차별점은 (X)" 공식. 이게 안 나오면 컨셉이 모호한 상태
- **추상어를 빼기** — "혁신적", "차세대" 같은 단어는 의미 없음. 구체적 표현으로
- **Riskiest Assumption을 명시** — 가장 위험한 가정을 솔직히 적을수록 신뢰 ↑. 숨기면 나중에 폭발
- **기존 대안을 무시하지 말기** — "경쟁사 없음"은 거의 항상 거짓말. 사용자는 무언가로 이미 그 문제를 풀고 있음
- **시각적 요소 1개 이상** — 텍스트만으로 컨셉 전달 어려움. Lean Canvas, 시나리오 일러스트, Before/After 등
- **2페이지 넘기지 말기** — 컨셉서가 길면 안 읽힘. 길어지면 PRD로 가야 할 내용임
- **여러 버전 만들어보기** — v0.1, v0.2 식으로 빠르게 반복. 첫 버전이 완벽할 필요 없음
- **숫자 1개 이상** — 시장 규모·사용자 수·예상 거래액 등 정량 표현 1개라도 있으면 설득력 크게 증가
- **NSM 후보를 정해두기** — 한 줄로 "성공의 정의"를 잡아두면 이후 모든 결정의 나침반이 됨

## 자주 하는 실수

- **솔루션부터 시작** — "이걸 만들고 싶다"에서 출발 → 문제가 약함 → 사용자가 안 옴
- **타겟이 "모두"** — "20~50대 모든 직장인" 같은 타겟은 사실상 타겟이 없는 것
- **한 줄 정의 누락** — 길게 설명할 줄만 알면 본인도 명확하지 않은 상태
- **차별화 추상어** — "더 좋은", "더 빠른", "더 편한" → 무엇이 어떻게 다른지 구체적이지 않음
- **경쟁사 분석 누락** — "없다"고 단언 → 사용자는 이미 어떤 방식으로든 풀고 있음
- **비즈니스 모델 막연** — "광고로 수익화" 한 줄. 누가 왜 광고를 살지가 핵심
- **NSM 없음** — "여러 지표 종합 평가" → 결국 아무것도 평가 안 됨
- **Riskiest Assumption 숨김** — 가장 위험한 가정을 외부 자료에 안 적음 → 의사결정자가 검증을 요구할 기회 상실
- **너무 긴 컨셉서** — 10페이지 컨셉서는 그냥 PRD. 1~2페이지로 압축이 핵심
