## 이 문서는

PRD에서 정의한 각 기능(FR-XXX)을 **개발이 그대로 만들 수 있는 수준으로 풀어쓴** 문서.

"이 기능은 무엇을 하는가, 어떤 입력을 받고 어떤 출력을 내는가, 어떤 정책·예외가 있는가, 어떤 화면과 연결되는가" 를 정리한다.

PRD·화면 정의서·정책 정의서와의 관계:

| 구분  | PRD      | 기능 정의서       | 화면 정의서   | 정책 정의서    |
| --- | -------- | ------------ | -------- | --------- |
| 단위  | 서비스 전체   | 기능 1개        | 화면 1개    | 정책 1개     |
| 깊이  | 무엇을·왜    | **무엇을 어떻게**  | 어떻게 보이게  | 어떤 규칙으로   |
| 청중  | 전체 이해관계자 | 개발·QA        | 디자인·개발   | 개발·QA·CS  |
| 질문  | 무엇을 만들까? | 이 기능 어떻게 작동? | 이 화면 무엇? | 이 규칙 어떻게? |

**핵심**: 기능 정의서는 **PRD와 화면·정책의 다리**. PRD에 "FR-005 AI 매칭 추천" 한 줄이 있다면, 기능 정의서엔 "어떻게 작동하는가" 가 풀어진다.

### 기능 정의서 vs 화면 정의서

가장 헷갈리는 부분. 정리하면:

- **기능 정의서** = 기능 단위 (예: "프로젝트 등록"). 입력·처리·출력·예외 중심
- **화면 정의서** = 화면 단위 (예: "프로젝트 등록 페이지 화면"). 구성·인터랙션·디자인 중심

한 기능이 여러 화면에 걸칠 수 있고(예: 회원가입은 3~4 화면), 한 화면에 여러 기능이 있을 수 있다(예: 대시보드).

## 언제 만드나

- PRD·IA·User Flow 합의 후
- 화면 정의서 작성 직전 또는 병행
- 새 기능군이 PRD에 추가될 때
- 개발 착수 전 (개발자가 이걸 보고 일함)

**기준**: "이 기능 어떻게 작동하는지 정확히 알려달라"는 개발·QA 요청이 나올 때.

### 어디까지 풀어 쓸까

기능 정의서의 깊이는 팀 성숙도에 따라 다르다:

|팀 상황|깊이|
|---|---|
|시니어 개발 중심, 빠른 사이클|간략 (입력·처리·출력 + 예외 몇 개)|
|신규 인력 많음, 외주 협업|상세 (모든 분기·예외·검증 규칙)|
|외주 발주 (유형 2)|매우 상세 (검수 기준이 됨)|

이 가이드는 **중간 깊이** (스타트업·자사 서비스 기준).

# 📌 예시 — TalentMatch / FR-005 AI 매칭 추천

> 가상 사례. PRD의 핵심 기능 중 하나. User Flow F-005 Step 2~3과 연결

## 기능 메타

|항목|내용|
|---|---|
|기능 ID|FR-005|
|기능명|AI 매칭 추천|
|카테고리|매칭|
|우선순위|MVP|
|상태|🟠 검토 중 (개발팀 리드 리뷰 진행 중)|
|버전|v0.3|
|작성자|홍길동 (PO)|
|작성일|2026-06-24|
|의사결정자|CTO|
|리뷰어|개발팀 리드 / ML 엔지니어 / 디자인 리드 / QA|

## 1. 기능 개요

### 한 줄 정의

이 기능은 **기업이 등록한 프로젝트의 요구 조건과 적합한 프리랜서 5명을 AI가 자동으로 추천**하는 기능이다.

### 상세 설명

기업이 프로젝트(직무·기간·예산·요구 기술)를 등록하면, 시스템이 등록된 프리랜서 풀에서 적합도 점수가 높은 5명을 선별해 매칭 점수·검증 마크·간략 프로필과 함께 표시한다. 매칭 알고리즘은 기술 스택 매칭(40%), 활동 데이터(30%), 가용성(15%), 평균 단가(15%) 가중치로 점수를 계산한다.

기업은 추천 결과를 보고 마음에 드는 프리랜서에게 메시지를 보낼 수 있다. 매칭 결과는 24시간 캐시되며, 그 안에 다시 조회 시 동일 결과를 보여준다.

### 비즈니스 가치

- **PRD H1 (매칭 → 계약 전환율 30% 이상)** 가설 검증의 핵심 기능
- 기존 위시켓의 견적 입찰 방식 대비 매칭 비용·시간 절감 (핵심 차별점)
- NSM(계약 완료 건수)의 입구. 이 기능 품질이 매칭률·전환율 결정

## 2. 사용자 권한·진입 조건

|항목|내용|
|---|---|
|사용 가능 권한|기업 회원 (인증 완료 + 결제 수단 등록 완료)|
|진입 경로|기업 대시보드 → 프로젝트 등록 (P-110) → "매칭 시작" 버튼|
|사전 조건|프로젝트 등록 페이지에서 필수 항목 모두 입력 완료|
|사용 빈도|기업당 평균 월 1~3회 (프로젝트당 1회)|

## 3. 입력 (Input)

|#|항목명|타입|필수|검증 규칙|비고|
|---|---|---|---|---|---|
|1|직무 카테고리|select|✅|개발·기획·디자인·PM·기타 5종|단일 선택|
|2|세부 직무|multi-select|✅|직무별 사전 정의 옵션|최대 3개|
|3|요구 기술 스택|tag input|✅|사전 정의된 기술 풀에서 선택|최대 10개|
|4|프로젝트 기간 (개월)|number|✅|1~24||
|5|시작 예정일|date|✅|오늘 + 7일 ~ +90일||
|6|월 예산 (만원)|number|✅|100 ~ 10,000||
|7|근무 형태|select|✅|풀타임·파트타임·하이브리드||
|8|위치|select|⬜|원격·서울·기타 시도|미입력 시 "무관"|
|9|추가 요구사항|text|⬜|0~500자|자유 텍스트|

## 4. 출력 (Output)

- **화면 변화**: 매칭 결과 페이지(P-113) 이동, 추천 프리랜서 5명 카드 형태로 표시
- **알림·이메일·푸시**: 없음 (즉시 화면 응답)
- **데이터 변경**:
    - 프로젝트 상태: `draft` → `matching_done`
    - 매칭 결과: `matching_results` 테이블에 5건 저장 (24시간 유효)
    - 추천된 프리랜서 5명 측에는 노출 사실 기록 (활동 통계용, 알림 X)
- **다른 사용자에게 전달**: 없음 (메시지 전송 전까지 프리랜서 측엔 알림 안 감)

## 5. 동작 흐름 (Step-by-step)

### 정상 흐름

1. 기업 사용자가 프로젝트 등록 페이지(P-110)에서 입력 9개 항목 작성
2. 사용자가 "매칭 시작" 버튼 클릭
3. 시스템이 클라이언트 측 검증 실행 (V-01~V-03)
4. 시스템이 매칭 알고리즘 호출 (서버):
    - a. 등록된 프리랜서 중 직무·기술 스택 매칭 필터 (1차 후보 풀 추출, 통상 50~200명)
    - b. 후보 풀 대상 매칭 점수 계산 (가중치 합산)
    - c. 점수 상위 5명 선별
    - d. 매칭 결과 캐시 (24시간 TTL)
5. 시스템이 매칭 결과 페이지(P-113)로 이동 응답
6. 사용자가 추천 5명을 카드 형태로 확인 (매칭 점수·검증 마크·이름·간략 프로필·평균 단가·평균 평가 점수)
7. 사용자가 카드 클릭 → 프리랜서 상세(P-011)로 이동
8. 사용자가 "연락하기" 클릭 → 메신저(P-300)에서 메시지 발송 (별도 기능 FR-010)

### 분기

- [ ] 매칭 결과 0건 (조건 너무 엄격) → EX-02 처리
- [ ] 매칭 결과 5건 미만 (3명만 매칭됨 등) → 3명만 표시 + "조건을 완화하면 더 많은 후보 추천 가능" 안내
- [ ] 24시간 내 동일 프로젝트 재조회 → 캐시 결과 그대로 반환 (속도 ↑)
- [ ] 24시간 초과 후 재조회 → 알고리즘 재실행

### 매칭 알고리즘 가중치 (참고)

```
매칭 점수 = 기술 스택 매칭 (40%)
         + 활동 데이터 (30%)        ← GitHub 커밋·블로그 글 빈도·최근성
         + 가용성 (15%)             ← 현재 진행 프로젝트 수, 시작 가능 일자
         + 평균 단가 적합도 (15%)   ← 예산 ±20% 범위
```

알고리즘 상세는 별도 정책 정의서 `POL-005. 매칭 알고리즘`에 상세 명세.

|EX-01|필수 입력 누락|빨간 안내 메시지 + 해당 필드 강조|알고리즘 호출 X|같은 화면 재입력|

|EX-04|알고리즘 서버 다운|"일시적 오류입니다. 5분 후 다시 시도해주세요" + 고객센터 안내|운영팀 즉시 알람|5분 후 자동 복구 시도|

## 작성 팁

- **PRD의 FR-ID와 1:1 매칭** — PRD FR-005면 기능 정의서도 FR-005. 양방향 추적 가능해야
- **한 줄 정의 공식** — "이 기능은 ___이 ___을 위해 ___을 하는 기능이다." 빈칸 채우면 명확해짐
- **입력·출력 표 형태로** — 줄글로 적으면 누락. 표로 정리하면 빠진 항목이 한눈에 보임
- **Happy Path → 분기 → 예외 순서** — 정상 흐름부터 그리고 점진적으로 복잡도 추가
- **검증은 클라이언트·서버 둘 다** — 클라이언트만 두면 보안 취약, 서버만 두면 UX 나쁨. 둘 다 명시
- **숫자로 명시** — "빠르게" ❌, "3초 이내" ⭕. "많이" ❌, "1,000건/시간" ⭕
- **알고리즘은 별도 정책 문서로 분기** — 기능 정의서엔 가중치 요약만, 상세는 정책 정의서에
- **이벤트 트래킹 미리 식별** — 출시 후 측정 누락 방지. 기능 정의 단계에서 식별
- **의존성 모두 적기** — 다른 기능·외부 API·인프라. 빠뜨리면 통합 단계에서 폭발
- **QA·CS 리뷰 필수** — QA는 테스트 가능성, CS는 사용자 입장 예외 케이스 발견에 강함
- **변경 이력 누적** — v0.1, v0.2 변경점을 적어두면 결정의 변천이 학습 자산

## 자주 하는 실수

- **PRD를 그대로 복붙** — PRD는 무엇을·왜, 기능 정의서는 어떻게. 깊이가 달라야
- **입력·출력 누락** — "사용자가 입력하면 결과 보여줌" 추상적. 항목·타입·검증까지 명시
- **Happy Path만** — 분기·예외 없이 정상 흐름만 적음 → 개발이 알아서 추측
- **검증 규칙 누락** — 클라이언트·서버 검증 안 적으면 보안·UX 문제
- **숫자 없음** — "빠르게", "많이", "안정적으로" → 측정 불가
- **알고리즘 본문에 길게 적기** — 기능 정의서가 너무 길어짐. 정책 정의서로 분기
- **이벤트 트래킹 누락** — 출시 후 "이 기능 잘 쓰이나?" 측정 불가
- **의존성 불명확** — 다른 기능과의 선행 관계 안 적으면 개발 순서 충돌
- **화면 정의서와 중복** — 화면 디테일(UI 컴포넌트·디자인)이 기능 정의서에 들어감 → 관리 분산
- **변경 시 PRD 갱신 안 함** — 기능 정의서만 바뀌고 PRD가 묵음 → 정합성 깨짐
