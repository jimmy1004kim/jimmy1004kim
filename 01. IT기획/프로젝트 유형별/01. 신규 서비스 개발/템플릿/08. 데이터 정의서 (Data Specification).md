## 이 문서는

서비스에서 다루는 **데이터의 구조·관계·규칙**을 명세한 문서.

"어떤 데이터를 저장하는가, 항목들이 서로 어떻게 연결되는가, 각 필드의 타입·제약은 무엇인가, 데이터는 언제 생성·갱신·삭제되는가" 를 정리한다.

다른 산출물과의 관계:

|구분|데이터 정의서|기능 정의서|API 명세|DB 스키마|
|---|---|---|---|---|
|단위|엔티티·필드|기능 1개|엔드포인트 1개|테이블 1개|
|깊이|**무엇이 저장되는가**|어떻게 작동?|어떻게 주고받는가|어떻게 저장되는가 (물리)|
|청중|개발·기획·QA·법무·BI|개발·QA|백엔드·프론트|백엔드·DBA|
|영역|논리·개념 모델|비즈니스 로직|인터페이스|물리 구현|

**핵심**: 데이터 정의서는 **개발·기획·법무·BI 모두가 합의하는 데이터 청사진**. DB 스키마는 이걸 물리로 구현한 것일 뿐.

### 왜 데이터를 별도로 정의하나

- **데이터는 모든 산출물의 공통 기반** — 기능·화면·API·Analytics 모두 같은 데이터 모델 위에 있음
- **변경 비용이 큼** — 출시 후 스키마 변경은 마이그레이션 비용 발생
- **법적 의무 동반** — 개인정보·결제 정보 등은 보관·삭제 규정 있음
- **분석·BI의 출발점** — 어떤 데이터를 어떻게 저장하느냐가 향후 분석 가능성 결정

## 언제 만드나

- 기능 정의서·User Flow 합의 후
- DB 스키마 설계 직전
- API 명세 작성 직전 또는 병행
- 새 엔티티가 PRD에 추가될 때
- v2.0급 데이터 모델 개편 시

**기준**: "어떤 데이터를 어떻게 저장할지 정해달라"는 개발·BI 요청이 나올 때.

## 데이터 정의서의 3단계

|단계|내용|산출물|
|---|---|---|
|**개념 모델**|어떤 개체가 있고 어떻게 연결되는가|엔티티 리스트 + 관계도|
|**논리 모델**|각 엔티티의 속성·타입·제약|엔티티별 필드 정의|
|**물리 모델**|DB에 어떻게 구현 (테이블·인덱스·SQL)|DB 스키마 (별도)|

이 가이드는 **개념 + 논리 모델** 중심. 물리 모델(SQL)은 개발의 영역이지만 정의서가 명확해야 흔들리지 않음.

## ERD (관계도)

**ERD 이미지**: (dbdiagram.io 링크 예정)

**텍스트 백업** (dbdiagram.io 문법, 발췌):

```
Table users {
  id bigint [pk, increment]
  email varchar [unique, not null]
  password_hash varchar [not null]
  role enum('company','freelancer','admin') [not null]
  status enum('active','suspended','withdrawn') [default: 'active']
  created_at timestamp [default: `now()`]
  updated_at timestamp
}

Table company_profiles {
  id bigint [pk, increment]
  user_id bigint [ref: - users.id, unique]
  company_name varchar [not null]
  business_number varchar [unique]
  representative_name varchar
  industry varchar
}

Table freelancer_profiles {
  id bigint [pk, increment]
  user_id bigint [ref: - users.id, unique]
  display_name varchar [not null]
  years_of_experience integer
  verified boolean [default: false]
  preferred_monthly_rate integer
  avg_rating decimal(2,1)
  review_count integer [default: 0]
}

Table projects {
  id bigint [pk, increment]
  company_id bigint [ref: > users.id]
  title varchar [not null]
  role_category enum
  duration_months integer
  budget_monthly integer
  status enum('draft','matching_done','contracted','completed','cancelled')
  created_at timestamp
}

Table matching_results {
  id bigint [pk, increment]
  project_id bigint [ref: > projects.id]
  freelancer_id bigint [ref: > users.id]
  score decimal(5,2)
  rank integer
  expires_at timestamp
}

Table contracts {
  id bigint [pk, increment]
  project_id bigint [ref: > projects.id]
  freelancer_id bigint [ref: > users.id]
  company_id bigint [ref: > users.id]
  total_amount integer
  status enum('draft','pending_signature','active','completed','cancelled','disputed')
  signed_at timestamp
}

Table milestones {
  id bigint [pk, increment]
  contract_id bigint [ref: > contracts.id]
  sequence integer
  title varchar
  amount integer
  due_date date
  status enum('pending','submitted','approved','paid')
}

Table payments {
  id bigint [pk, increment]
  milestone_id bigint [ref: > milestones.id]
  amount integer
  pg_provider enum('toss','kg_inicis')
  pg_transaction_id varchar
  status enum('pending','escrowed','released','refunded')
  paid_at timestamp
  released_at timestamp
}

Ref: company_profiles.user_id - users.id
Ref: freelancer_profiles.user_id - users.id
Ref: projects.company_id > users.id
Ref: matching_results.project_id > projects.id
Ref: matching_results.freelancer_id > users.id
Ref: contracts.project_id > projects.id
Ref: contracts.freelancer_id > users.id
Ref: contracts.company_id > users.id
Ref: milestones.contract_id > contracts.id
Ref: payments.milestone_id > milestones.id
```

## 핵심 엔티티 상세 (3개 발췌)

### users (E-01)

**설명**: 모든 사용자(기업·프리랜서·관리자)의 공통 정보. 역할에 따라 별도 프로필 엔티티와 1:1 연결.

**관계**:

- 1:1 → company_profiles (role=company인 경우)
- 1:1 → freelancer_profiles (role=freelancer인 경우)
- 1:N → projects (기업의 등록 프로젝트)
- N:M → contracts (기업·프리랜서 양쪽으로 연결)

**필드**:

|#|필드명|타입|필수|PK/FK|기본값|검증·제약|개인정보 등급|설명|
|---|---|---|---|---|---|---|---|---|
|1|id|bigint|✅|PK|auto|unique|-|고유 식별자|
|2|email|varchar(255)|✅|-|-|unique, RFC 5322|🟠 개인|로그인 ID|
|3|password_hash|varchar(255)|✅|-|-|bcrypt 12 rounds|🔴 민감|해시 저장|
|4|role|enum|✅|-|-|company/freelancer/admin|⚪ 비식별|권한 구분|
|5|status|enum|✅|-|active|active/suspended/withdrawn|⚪ 비식별|계정 상태|
|6|phone|varchar(20)|⬜|-|-|본인 인증 시 입력|🔴 민감|본인 인증|
|7|last_login_at|timestamp|⬜|-|-|-|⚪|마지막 로그인|
|8|created_at|timestamp|✅|-|now()|-|⚪|가입일|
|9|updated_at|timestamp|✅|-|now()|auto-update|⚪||
|10|withdrawn_at|timestamp|⬜|-|-|-|⚪|탈퇴 시점|

**인덱스**:

- `email` (로그인 조회)
- `(role, status)` (활성 기업·프리랜서 필터)
- `created_at` (정렬·통계)

**생애주기**:

- 생성: 회원가입 완료 시 (이메일 인증 완료 후 activate)
- 갱신: 프로필 변경 시
- 삭제: 즉시 삭제 X. 탈퇴 시 `status='withdrawn'` + 개인정보 익명화 (email→`deleted_{id}@deleted`, phone→null, password_hash→null)
- 영구 삭제: 탈퇴 후 5년 (전자상거래법 보관 의무) → 5년 후 hard delete

|3|display_name|varchar(50)|✅|-|-|2~50자|🟠 개인|프로필 노출 이름|

### projects (E-06)

**설명**: 기업이 등록한 프로젝트. 매칭·계약의 출발점.

**관계**:

- N:1 → users (company_id, 등록 기업)
- 1:N → matching_results
- 1:1 → contracts (계약 체결 시)
- N:M → skills (요구 기술 스택)

**필드**:

**생애주기**:

- 생성: 기업이 프로젝트 등록 폼 제출 시 (status=draft → matching 시작 시 matching_done)
- 갱신: 기업이 조건 수정 시 (status=draft인 경우만 가능)
- 삭제: 즉시 hard delete X. status=cancelled로 soft delete, 30일 후 hard delete
- 계약 체결 시: status=contracted, 이후 수정 불가

## 작성 팁

- **명사 추출부터** — PRD·기능 정의서를 훑으며 등장하는 명사 모두 추출 → 엔티티 후보. 누락 방지
- **개념·논리·물리 분리** — 데이터 정의서는 개념·논리만. 물리(SQL·인덱스)는 DB 스키마로 분기
- **ERD 먼저 그리기** — 텍스트로 필드부터 적으면 관계 누락. ERD로 큰 그림 확정 후 필드 채움
- **dbdiagram.io 활용** — 텍스트로 ERD 작성하면 자동 시각화 + Git 관리 가능
- **개인정보 등급 모든 필드에** — 5단계 등급(🔴🟠🟡🟢⚪) 모든 필드에 표시. 보안·법적 처리의 자동 기준
- **생애주기 명시** — 언제 생성·갱신·삭제. 특히 삭제는 hard vs soft 명확히
- **법적 보관 의무 확인** — 전자상거래법(5년), 부가세법(5년) 등. 법무 리뷰 필수
- **외래키 관계 도식화** — 1:1·1:N·N:M 명시. 카디널리티 정확하게
- **인덱스를 미리 식별** — 자주 조회되는 필드는 인덱스 후보. BI·검색 요구도 반영
- **enum 값은 모두 나열** — `status enum` ❌, `status enum('draft','active','completed')` ⭕
- **민감 필드 별도 처리 명시** — 결제·계좌·주민번호는 별도 KMS·암호화. "암호화 저장" 한 줄로 끝내지 말고 방법까지
- **BI·분석 관점 포함** — 출시 후 어떤 데이터 분석할지 미리 고려. avg_rating·created_at 같은 분석용 필드 누락 X
- **변경 시 영향 평가** — 데이터 정의서 변경은 마이그레이션 비용. 변경 전 ADR로 영향 명시

## 자주 하는 실수

- **엔티티 누락** — PRD에서 명사 추출 안 하고 머리로만 생각 → 핵심 엔티티 빠짐 (예: audit_logs·notifications)
- **ERD 없이 표만** — 필드 표만 만들고 관계도 안 그림 → 관계 누락·중복 발생
- **개인정보 등급 미표시** — 보안·법적 처리 기준 모호 → 사고 발생
- **생애주기 누락** — 삭제 정책 안 적으면 GDPR·개인정보법 위반 가능
- **법적 보관 의무 무시** — 전자상거래법 5년 의무를 모르고 즉시 삭제 → 법적 위반
- **enum 값 미정의** — `status enum`만 적고 어떤 값들이 있는지 안 적음
- **외래키 카디널리티 모호** — 1:1인지 1:N인지 N:M인지 → 개발 시 추측
- **민감 필드 평문** — 비밀번호·계좌번호를 그냥 varchar로 → 사고
- **인덱스 미고려** — 핵심 조회 필드 인덱스 없음 → 출시 후 성능 문제
- **분석 관점 누락** — BI 요구사항 무시 → 출시 후 "이 데이터 분석 못 한다"
- **물리(SQL)와 혼동** — 데이터 정의서에 인덱스 종류·파티션 등 물리 디테일까지 → 관리 분산
- **변경 이력 없음** — 어떤 필드가 언제 왜 바뀌었는지 추적 불가
