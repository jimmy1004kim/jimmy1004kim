## 이 문서는

서비스에서 **어떤 사용자 행동·시스템 동작을 측정할지** 명세한 문서.

"무엇을 측정할 것인가, 각 이벤트는 언제 발생하고 어떤 속성을 가지는가, 측정한 데이터로 어떤 의사결정을 할 것인가" 를 정리한다.

PRD·기능 정의서·KPI와의 관계:

|구분|PRD·KPI 정의서|이벤트 트래킹 정의|BI 대시보드|
|---|---|---|---|
|단위|지표 (NSM·KPI)|**이벤트 + 속성**|시각화|
|깊이|무엇을 측정할까|**어떻게 측정할까** (구현)|무엇이 보이는가|
|청중|PO·경영진|PO·개발·데이터|전체|
|시점|컨셉 단계|기능 정의 단계|출시 후|

**핵심**: KPI 정의서가 "무엇을 측정할 것인가"라면, 이벤트 트래킹 정의는 **"그 측정값을 어떻게 만들 것인가"**. NSM·KPI에 도달하는 funnel과 행동을 이벤트 단위로 명세한다.

### 왜 출시 전에 정의해야 하나

- **출시 후 측정하면 늦다** — 출시 후 "이거 측정 못 한다" 발견하면 데이터 공백 발생
- **개발과 함께 가야** — 이벤트 발생 코드는 개발 단계에서 심어야 함
- **분석 가능성이 곧 의사결정 가능성** — 측정 못 하면 출시 후 결정 못 함
- **출시 후 추가는 비싸다** — 데이터 누적이 0부터 다시

**원칙**: **PRD 합의 시점에 이벤트 트래킹 정의 v0.1 시작, 출시 전 v1.0 확정.**

### 이벤트 vs 속성 vs 사용자 속성

|구분|의미|예시|
|---|---|---|
|**이벤트 (Event)**|무엇이 일어났는가|`matching_started`, `payment_completed`|
|**이벤트 속성 (Property)**|그 이벤트에 대한 추가 정보|`project_id`, `amount`, `duration_seconds`|
|**사용자 속성 (User Property)**|사용자에 대한 속성 (장기 누적)|`role`, `subscribed`, `signup_date`|

이벤트는 "동사·행동", 속성은 "그 행동의 디테일", 사용자 속성은 "그 사람의 상태".

## 언제 만드나

- PRD 합의 후, 기능 정의서·화면 정의서 작성과 병행
- 화면 정의서의 인터랙션 식별과 동시에 이벤트 식별 (가장 효율적)
- 출시 직전 (v1.0 확정 + 코드 구현 검증)
- 신규 기능 추가 시 (관련 이벤트 추가)

**기준**: "이 기능 잘 쓰이나?" 질문에 답할 수 있는 데이터를 확보하려면.

## 이벤트 명명 규칙 (Naming Convention)

이벤트 명은 한 번 정하면 영원히 못 바꿈 (데이터 누적 끊김). 처음에 잘 정해야 한다.

### 권장 형식

**`object_action`** 형식 (snake_case)

|좋은 예|나쁜 예|이유|
|---|---|---|
|`project_created`|`Created Project`|snake_case 일관성|
|`matching_started`|`start_matching`|명사 우선 (검색 시 그룹화)|
|`payment_completed`|`paid`|명확한 객체+동작|
|`card_clicked`|`click`|너무 모호|

### 시제 통일

- 행동 완료 시 발생 → 과거형: `signed_up`, `paid`, `completed`
- 진행 중 발생 → 진행형: `loading`, `started`
- 둘 중 하나로 통일

### 약어 금지

- ❌ `pmt_done`
- ✅ `payment_completed`

### 페이지 뷰

- 자동 트래킹 ON 권장
- 명시적으로 정의 시 `page_viewed` + `page_name` 속성

## 작성 절차

1. **KPI 매핑** — PRD의 NSM·KPI에서 출발. 각 지표를 어떤 이벤트로 측정할지

3. **화면 정의서 동기화** — 화면별 인터랙션에 이벤트 매핑

5. **속성 정의** — 각 이벤트의 추가 정보 (project_id·amount 등)
6. **사용자 속성 정의** — 장기 누적되는 사용자 상태 (role·subscribed 등)
7. **구현 가이드** — 코드 예시·라이브러리 지정
8. **이해관계자 리뷰** — PO·개발·데이터·법무
9. **개발 구현 → QA 검증** — 코드 심기 + 발생 확인
10. **변경 관리** — 이벤트 추가·삭제 절차

## 핵심 Funnel

### Funnel A. 기업 측 — 가입 → 계약

|Step|이벤트|의미|
|---|---|---|
|1|`signup_started`|기업 회원가입 페이지 진입|
|2|`signup_completed`|가입 완료 (이메일 인증 포함)|
|3|`project_creation_started`|프로젝트 등록 페이지 진입|
|4|`project_created`|프로젝트 등록 완료|
|5|`matching_started`|매칭 알고리즘 실행 시작|
|6|`matching_completed`|매칭 결과 표시 (5명 추천)|
|7|`matching_card_clicked`|프리랜서 카드 클릭|
|8|`matching_contact_clicked`|"연락하기" 클릭|
|9|`contract_created`|표준 계약서 생성|
|10|`contract_signed`|양쪽 서명 완료|
|11|`payment_completed`|1차 마일스톤 결제 완료|
|종료|`contract_completed`|프로젝트 종료·평가 완료|

**기대 전환율 (베타 출시 3개월 기준)**:

- 가입(2) → 프로젝트 등록(4): 50%
- 프로젝트 등록(4) → 매칭(6): 95%
- 매칭(6) → 연락(8): 40%
- 연락(8) → 계약 서명(10): 50%
- 계약 서명(10) → 결제 완료(11): 90%
- **전체 (가입 → 계약 완료): 약 8.5%** (베타 검증값)

**이탈 모니터링**:

## 구현 가이드 발췌

```typescript
// Amplitude SDK + TypeScript

type EventName =
  | 'signup_completed'
  | 'matching_started'
  | 'matching_completed'
  | 'matching_card_clicked'
  | 'matching_contact_clicked'
  | 'contract_signed'
  | 'payment_completed'
  | 'freelancer_verified'
  | 'review_submitted';

interface EventProps {
  signup_completed: {
    role: 'company' | 'freelancer';
    signup_source?: string;
    signup_method: 'email' | 'google_oauth' | 'naver_oauth';
    duration_seconds?: number;
  };
  matching_started: {
    project_id: string;
    role_category: string;
    tech_stack: string[];
    tech_stack_count: number;
    budget_monthly: number;
    duration_months: number;
    start_date_days_from_now: number;
    work_type: 'fulltime' | 'parttime' | 'hybrid';
    has_location: boolean;
    role_detail_count: number;
  };
  // ... 나머지 이벤트들
}

function track<T extends EventName>(event: T, props: EventProps[T]) {
  amplitude.track(event, props);
  // 자체 DB 백업 전송 (장기 보관)
  if (process.env.NODE_ENV === 'production') {
    sendToInternalAnalytics(event, props);
  }
}

// 사용 예
track('matching_started', {
  project_id: 'PRJ-12345',
  role_category: 'backend',
  tech_stack: ['Node.js', 'AWS', 'Docker'],
  tech_stack_count: 3,
  budget_monthly: 700,
  duration_months: 3,
  start_date_days_from_now: 15,
  work_type: 'fulltime',
  has_location: false,
  role_detail_count: 2
});
```

## 작성 팁

- **PRD 합의 시점에 시작** — 출시 직전 시작하면 늦음. PRD 합의 후 KPI 매핑부터
- **KPI 거꾸로 추적** — NSM·KPI에서 출발 → 필요한 이벤트 도출. "혹시 측정할까" 식으로 추가하지 말 것
- **명명 규칙 한 번에 정하기** — 이벤트 명은 한 번 정하면 영원히. 처음에 충분히 토론
- **TypeScript 등으로 타입 강제** — 명명·속성 누락·오타 사전 차단. 가장 강력한 안전 장치
- **이벤트 30~50개가 적정** — MVP는 20개 정도. 100개 넘어가면 노이즈
- **속성을 풍부하게** — 이벤트 1개에 속성 5~10개. 분석 시점에서 더 못 만든다
- **클라이언트·서버 둘 다 발생** — 핵심 이벤트는 이중 트래킹. 데이터 정확성 ↑ (광고 차단·네트워크 오류 방지)
- **사용자 속성 잘 설계** — 코호트 분석의 핵심. `total_contracts`, `subscribed`, `verified` 같은 누적 속성
- **PII 절대 금지** — 이메일·전화·결제 카드 절대 전송 X. 한 번 흘러가면 정정 어려움
- **Funnel 사전 정의** — 출시 후 측정하려고 하면 늦음. 사전에 핵심 Funnel 3~5개 정의
- **자동 트래킹 활용** — 페이지 뷰·세션·디바이스 정보 등은 자동. 명시적 트래킹은 핵심 행동만
- **변경 관리 엄격히** — 이벤트 명 변경·속성 추가는 데이터 누적에 영향. ADR로 기록
- **QA 시나리오에 이벤트 검증 포함** — 기능 QA와 동시에 이벤트 발생 검증

## 자주 하는 실수

- **출시 직전에 시작** — PRD 합의 시점에 시작하지 않아 출시 후 데이터 공백
- **KPI 무관 이벤트 남발** — "혹시 측정"으로 추가 → 노이즈, 진짜 KPI 측정 누락
- **명명 규칙 불일치** — `signup_completed`와 `signupCompleted`가 공존 → 분석 시 혼란
- **속성 부족** — `payment_completed`인데 `amount` 없음 → 매출 계산 불가
- **PII 전송** — 이메일·전화·결제 카드 흘려보냄 → 법적 리스크 + 데이터 정정 어려움
- **클라이언트만 발생** — 광고 차단·네트워크 오류로 데이터 누락 → 핵심 이벤트는 서버 발생
- **사용자 속성 누락** — 코호트 분석 시점에 "verified 누가인지 모름" → 누적 속성 사전 설계
- **Funnel 사후 정의** — 출시 후 funnel 만들려면 이벤트 부족 → 사전 정의 필수
- **타입 강제 없음** — 오타·속성명 불일치 발생 → TypeScript 등 활용
- **변경 관리 없음** — 이벤트 명 임의 변경 → 데이터 누적 끊김 → 분석 불가
- **QA에서 이벤트 검증 누락** — 기능만 검증, 이벤트 미발생 발견은 출시 후
- **분석 플랫폼만 사용** — Amplitude 보관 한계 (2년) → 자체 DB 백업 누락 → 장기 분석 불가
