## 이 문서는

신규 서비스를 만들기 위한 **요구사항·기능·정책·범위를 통합한 단일 기준 문서**.

PRD는 프로젝트 진행 중 **가장 자주 참조되는 문서**. 개발·디자인·QA·마케팅 모두가 이 문서를 기준으로 일한다. 새 인원이 합류해도 PRD 한 장 읽으면 프로젝트 전체 그림이 잡히는 게 목표.

서비스 컨셉서와 헷갈리기 쉬운데 위치가 다르다.

|구분|서비스 컨셉서|PRD|
|---|---|---|
|시점|아이디어 검증 단계|컨셉 확정 후|
|길이|1~2페이지|10~30페이지|
|청중|의사결정자·투자자|개발·디자인·QA|
|깊이|왜·무엇|**어떻게·어디까지**|
|변경 빈도|거의 안 바뀜|살아있는 문서, 자주 갱신|

PRD vs 다른 산출물의 관계:

- **PRD = 마스터 문서** (이게 진실의 소스)
- 기능 정의서·화면 정의서·데이터 정의서 = PRD의 상세 분기
- User Flow·IA = PRD를 시각화·구조화한 것

**핵심 원칙**: PRD는 살아있는 문서다. v0.1로 시작해 v1.0 확정 후에도 변경이 들어오면 갱신하고 버전 올린다.

## 언제 만드나

- 서비스 컨셉서 통과 후 (PRD 착수의 전제)
- 본격 설계·개발 진입 직전
- 서비스의 주요 버전(v2.0급) 개정 시
- 신규 기능군이 PRD 수준으로 새로 추가될 때

**기준**: "여러 사람이 같은 방향으로 일하기 위해 통합 기준이 필요할 때."

## 어떤 툴로

|툴|추천도|이유|
|---|---|---|
|**노션**|⭐ 강력 추천|길이 제약 적음, 표·이미지·DB 자유, 버전 관리 가능|
|**Confluence**|추천|회사 표준이면|
|Google Docs|보조|코멘트 협업 강함, 단 길어지면 관리 어려움|
|Word / PDF|비추|살아있는 문서엔 부적합|

**팁**: 노션 PRD 페이지 안에 기능 정의서·화면 정의서를 하위 페이지로 연결. PRD가 인덱스 역할.

## PRD 구성의 두 가지 스타일

### 스타일 A — 전통적 PRD (긴 형식)

- 분량: 20~30페이지
- 모든 요구사항을 한 문서에
- 대기업·외주 프로젝트에서 흔함

### 스타일 B — Lean PRD (짧은 형식)

- 분량: 5~10페이지
- PRD는 큰 틀만, 상세는 별도 산출물로 분기
- 스타트업·애자일 환경에서 흔함

**이 가이드는 스타일 B 기반.** A 스타일이 필요하면 섹션을 더 풀어 쓰면 됨.

## 작성 절차

1. **컨셉서 확인** — 컨셉서 합의 없이 PRD 쓰면 흔들림
2. **v0.1 초안** — 빠르게 뼈대만. 디테일은 두 번째 사이클에
3. **이해관계자 리뷰** — 개발·디자인·QA·마케팅·CS·법무
4. **v0.x 반복** — 피드백 반영, 보통 v0.3~v0.5에서 안정
5. **v1.0 확정** — 합의 완료 시점
6. **하위 산출물 분기** — 기능 정의서·화면 정의서·데이터 정의서 별도 작성
7. **변경 관리** — PRD 변경은 CR(Change Request)로 기록, 변경 이력에 누적

# 📌 예시 — TalentMatch PRD v0.3

> 가상 사례. T1 시리즈 전체에서 이 케이스 일관 사용

## PRD 메타

|항목|내용|
|---|---|
|서비스명|TalentMatch|
|버전|v0.3|
|상태|🟠 검토 중 (이해관계자 리뷰 진행 중, v1.0 확정 6/30 목표)|
|작성자|홍길동 (PO)|
|작성일|2026-06-10|
|최종 갱신일|2026-06-18|
|의사결정자|대표 + CTO|
|리뷰어|개발팀 리드 / 디자인 리드 / 마케팅 리드 / 법무 자문|

## 1. 개요

### 한 줄 정의

IT 프리랜서와 단기·중기 IT 프로젝트를 가진 기업을 매칭하는 플랫폼. IT 직무 특화 + 포트폴리오 자동 검증 + 에스크로 결제로 양쪽 신뢰 비용을 낮춘다.

### 배경

- IT 프리랜서 시장 약 12만명, 단기 프로젝트 수요 연 8만 건, 그중 70%가 비공식 채널
- 기존 플랫폼(위시켓·크몽)은 견적 입찰 방식·디자인 중심으로 IT 특화 부재
- 코로나 이후 원격 협업 정착 + IT 인력난 → 단기 프리랜서 활용 수요 급증

### 목적

- IT 직무에 특화된 신뢰도 높은 매칭 플랫폼 구축
- 1년 내 월 계약 완료 500건·거래액 80억 달성

### 용어 정의

|용어|정의|
|---|---|
|매칭|기업 프로젝트와 프리랜서 간 추천·연결|
|마일스톤|프로젝트 기간 중 결제·납품 분할 단위 (일반적 3~4분할)|
|에스크로|플랫폼이 자금을 보관 후 양쪽 합의 시 이체|
|검증 마크|포트폴리오 자동 검증 완료된 프리랜서 표시|

## 2. 타겟·페르소나

- 시리즈 A~B 스타트업 (10~50명 규모) 중 IT 직무 단기·중기 인력 필요한 회사
- IT 프리랜서 (개발·기획·PM·디자이너, 경력 3년+)

### 2차 타겟

- 중견기업 IT 부서의 단기 프로젝트 지원 인력 수요
- 경력 1~3년 주니어 프리랜서 (확장 단계)

|목표|3~6개월 단위 프로젝트마다 검증된 IT 인력 빠르게 확보|
|페인|사람인은 정규직 위주, 위시켓은 견적 입찰이 비효율, 결국 지인 추천에 의존|
|행동 패턴|새 프로젝트 시작 2주 전부터 인력 탐색 시작, 평균 3~5개 채널 동시 활용|

|행동 패턴|프로젝트 종료 1개월 전부터 다음 일감 탐색, 위시켓+링크드인+커뮤니티 활용|

별도 페르소나 문서: (링크 예정)

## 3. 문제 정의·핵심 가설

### 문제 정의

IT 직무 특화 + 신뢰 인프라(검증·계약·결제) 갖춘 프리랜서 매칭 플랫폼이 없어, 기업·프리랜서 모두 매칭 비용과 신뢰 비용이 높다.

### 핵심 가설

**[H1]** 기업은 "검증된 IT 프리랜서를 빠르게 추천받는 것"에 거래액의 5%를 지불할 의향이 있다.

- **검증 방법**: 베타 출시 후 3개월 거래 데이터로 결제 전환율 측정
- **성공 기준**: 추천 받은 기업의 30% 이상이 실제 계약·결제 완료

**[H2]** 프리랜서는 "안정적 프로젝트 추천"에 거래액의 3%를 지불할 의향이 있다.

- **검증 방법**: 베타 기간 프리랜서 측 수수료 면제 → 정식 출시 시점 이탈률 측정
- **성공 기준**: 정식 출시 시점 프리랜서 이탈률 30% 이하

**[H3]** 포트폴리오 자동 검증이 매칭 성사율을 30% 이상 향상시킨다.

- **검증 방법**: 검증 마크 보유 vs 미보유 프리랜서의 매칭 성사율 A/B 비교
- **성공 기준**: 검증 마크 보유자가 미보유자 대비 매칭 성사율 1.3배 이상

## 4. 솔루션 개요

기업이 프로젝트(직무·기간·예산) 등록 → AI가 GitHub·블로그 활동 데이터 기반으로 적합 프리랜서 5명 추천 → 기업 검토·면접·선정 → 표준 계약서 자동 생성 → 에스크로 결제(마일스톤 분할) → 양쪽 평가 → 다음 매칭에 반영.

핵심은 **(1) IT 직무 특화 매칭 알고리즘 (2) 자동 검증 인프라 (3) 결제·계약 신뢰 인프라** 3가지의 결합.

## 5. 사용자 시나리오 / Job Stories

### 시나리오 1. 기업의 프로젝트 등록 → 매칭 → 계약

- **상황**: 박상준 CTO가 3개월 백엔드 개발자 1명 필요
- **행동**:
    1. TalentMatch에 프로젝트 등록 (직무·기간·예산·요구 기술)
    2. AI 매칭으로 추천 5명 확인
    3. 검증 마크·포트폴리오·과거 평가 참고하여 후보 3명 선정
    4. 화상 면접 (플랫폼 내 또는 외부 도구)
    5. 김지영 선정 → 표준 계약서 자동 생성 → 1차 마일스톤 에스크로 결제
- **결과**: 프로젝트 등록 후 평균 7일 내 계약 체결

### 시나리오 2. 프리랜서의 매칭 수락 → 작업 → 정산

- **상황**: 김지영이 다음 프로젝트 탐색 중
- **행동**:
    1. TalentMatch 프로필 (GitHub·블로그 URL) 연동 → 자동 검증 마크 획득
    2. 추천받은 프로젝트 3개 중 1개 수락 → 화상 면접 → 계약
    3. 마일스톤 단위로 작업 → 결과물 제출 → 기업 승인 → 자금 이체
    4. 프로젝트 종료 후 양쪽 평가
- **결과**: 매칭 수락 후 평균 5일 내 작업 시작, 종료 후 3일 내 정산

### Job Stories

- When 새 IT 프로젝트가 시작되면, I want to 검증된 프리랜서를 1주 안에 매칭받을 수 있게, so I can 정규직 채용 부담 없이 빠르게 인력 투입할 수 있다.
- When 다음 프로젝트가 끝나가면, I want to 다음 일감을 자동 추천받을 수 있게, so I can 영업 시간을 줄이고 작업에 집중할 수 있다.

## 작성 팁

- **v0.1은 빠르게** — 완벽한 v0.1을 만들려고 시간 들이지 말 것. 70% 상태로 빨리 리뷰 받는 게 가장 빠른 길
- **MVP / Out of Scope 명시가 핵심** — 포함보다 제외가 더 중요. "이번엔 안 한다"가 명확해야 범위 폭주 안 함
- **단일 진실 소스 (Single Source of Truth)** — PRD가 흔들리면 다 흔들림. 변경 시 반드시 PRD 갱신 → 다른 산출물에 전파
- **검증 가능한 가설** — "사용자가 좋아할 것이다" ❌, "추천 받은 기업의 30% 이상이 계약 완료" ⭕
- **NSM 1개 + KPI 5~7개** — 너무 많으면 다 안 봄. 단일 NSM + 단계별 핵심 KPI
- **NFR을 빠뜨리지 말기** — 기능만 적고 성능·보안·접근성 누락 → 출시 직전에 폭발
- **링크 기반 분기** — PRD에 모든 걸 넣으려 하지 말고, 상세는 별도 문서로 분기하고 링크
- **이해관계자별 리뷰** — 개발·디자인·QA·마케팅·CS·법무. 한 명이라도 빠지면 출시 후 발견
- **변경 이력 누적** — v0.x 단계라도 변경 이력 적기. 결정의 변천이 학습 자산
- **포트폴리오용 PRD 한 줄** — "이 PRD는 X 가설 검증을 위한 Y 범위 MVP 정의서"라고 정리하면 외부용으로도 가치 ↑

## 자주 하는 실수

- **PRD를 컨셉서처럼 쓰기** — 추상적·설득용. PRD는 작업 기준이라 구체적이어야
- **MVP 정의 모호** — "최소 기능"이 30개 → 그건 MVP가 아니라 v1
- **Out of Scope 누락** — 안 하는 것을 안 적으면 출시 직전에 추가 요청 폭주
- **NFR 누락** — 성능·보안·접근성 안 적고 가다 출시 직전 발견
- **가설 검증 불가** — "사용자 만족도 향상" → 측정 불가 → 검증 실패
- **너무 긴 PRD** — 50페이지 PRD는 안 읽힘. 상세는 별도 문서로 분기
- **변경 이력 없음** — v0.5인데 무엇이 어떻게 바뀌었는지 기록 없음
- **단일 작성자 폐쇄적** — PO 혼자 다 작성, 리뷰 없이 v1.0 확정 → 출시 후 누락 발견
- **PRD ≠ 기능 정의서 혼동** — PRD는 마스터, 기능 정의서는 분기. PRD에 화면 와이어프레임 다 넣으면 관리 불가
- **NSM 없음** — 성공의 정의를 한 줄로 못 쓰면 PRD가 아직 흐리다는 신호
