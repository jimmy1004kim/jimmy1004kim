## 이 문서는

각 화면이 **무엇으로 구성되고, 어떻게 동작하며, 어떤 정책·예외를 가지는지** 풀어쓴 문서.

"이 화면에 어떤 요소(컴포넌트)들이 있는가, 사용자가 누르면 무엇이 일어나는가, 데이터는 어디서 오는가, 어떤 상태가 있는가" 를 정리한다.

기능 정의서·디자인과의 관계:

| 구분  | 기능 정의서       | 화면 정의서              | 디자인 (Figma)   |
| --- | ------------ | ------------------- | ------------- |
| 단위  | 기능 1개        | 화면 1개               | 화면 1개         |
| 깊이  | 무엇을·어떻게 (로직) | **무엇이·어디·어떻게 (UI)** | 비주얼 (색·여백·폰트) |
| 청중  | 개발·QA        | 디자인·개발·QA           | 개발·QA         |
| 질문  | 이 기능 작동 방식?  | 이 화면 구성·동작?         | 이 화면 어떻게 보일까? |

**핵심**: 화면 정의서는 **기능과 디자인의 다리**. 기능 정의서가 "AI 매칭은 3초 이내 응답" 이라면, 화면 정의서엔 "매칭 결과 화면은 카드 5개·상단에 조건 요약·하단에 재매칭 버튼" 으로 풀어진다.

### 화면 정의서 vs 와이어프레임 vs 시각 디자인

|단계|산출물|도구|
|---|---|---|
|1. 화면 구성·로직 정의|**화면 정의서**|노션 + 와이어프레임 이미지|
|2. 저화질 시각화|와이어프레임 (Wireframe)|Figma·Whimsical|
|3. 비주얼 디자인|High-fidelity 디자인|Figma|
|4. 인터랙션·프로토타입|클릭 프로토타입|Figma·ProtoPie|

화면 정의서는 1~2단계. 3~4단계는 디자이너의 영역이지만 정의서가 명확해야 디자인이 흔들리지 않음.

## 언제 만드나

- 기능 정의서·User Flow 합의 후
- 디자인 착수 직전 또는 병행
- 새 화면이 IA에 추가될 때
- 기존 화면 v2.0급 개편 시

**기준**: "이 화면 어떻게 만들어야 하나요?" 디자이너·개발 질문이 나올 때.

### 어디까지 풀어 쓸까

화면 정의서 깊이는 팀 상황에 따라 다르다:

|상황|깊이|
|---|---|
|디자이너 시니어 + 소규모 팀|간략 (구성·핵심 인터랙션·상태)|
|외주 발주 (유형 2)|매우 상세 (모든 컴포넌트·정책·검수 기준)|
|신규 인력·외주 협업 많음|상세 (분기·예외·복잡한 인터랙션까지)|

이 가이드는 **중간~상세**.

## 어떤 툴로

|툴|추천도|이유|
|---|---|---|
|**노션 페이지**|⭐ 강력 추천|정의서 + 와이어프레임 이미지 임베드|
|**Figma + Description 영역**|⭐ 추천|디자인 옆에 바로 정의 작성 (디자인-정의 분리 X)|
|Confluence|추천|회사 표준이면|
|Word·PDF|비추|살아있는 문서엔 부적합|

**최적 조합**:

- 노션 페이지 1개 = 화면 1개
- 페이지 상단에 와이어프레임 이미지(Figma 임베드)
- 하단에 텍스트 정의서

## 화면 정의서의 구성 (표준)

각 화면은 다음 9개 섹션을 표준으로:

1. 화면 메타 (ID·이름·URL·진입 권한 등)
2. 화면 목적
3. 와이어프레임 (시각)
4. 컴포넌트 구성표 (영역별)
5. 데이터 (어디서 오는가)
6. 상태 (Loading·Empty·Error·Success 등)
7. 인터랙션·이벤트
8. 예외·정책
9. 관련 산출물 링크

## 들어가야 할 것

- 화면 메타 (ID·URL·권한·디바이스)
- 화면 목적·진입 경로
- 와이어프레임 (이미지·임베드)
- 컴포넌트 구성 (영역·요소·상태)
- 데이터 명세 (API·필드)
- 화면 상태 (Loading/Empty/Error/Success 등)
- 인터랙션·이벤트 (클릭·입력·스크롤 시)
- 예외 처리·접근성·반응형
- 관련 기능·정책·데이터 링크

## 작성 절차

1. **IA·User Flow·기능 정의서 확인** — 이 화면이 어느 위치·어느 기능에 속하는지
2. **와이어프레임 v0.1** — Figma 등으로 빠르게 (정의서 작성과 병행)
3. **영역 구분** — 헤더·메인·푸터·사이드 등 영역으로 나누기
4. **컴포넌트별 명세** — 각 컴포넌트의 텍스트·데이터·인터랙션
5. **상태 정의** — 4~6가지 상태 (Loading·Empty·Error·Success·Disabled 등)
6. **인터랙션·이벤트** — 클릭·입력·스크롤 시 동작
7. **예외·정책 명시** — 권한 없음·세션 만료·데이터 없음 등
8. **이해관계자 리뷰** — 디자인·개발·QA·CS
9. **변경 시 와이어프레임·정의서 동시 갱신**

## 작성 팁

- **와이어프레임 먼저** — 텍스트로 화면 정의를 쓰다 보면 추상적이 됨. 와이어 그리고 그걸 명세하는 게 빠르고 정확
- **영역으로 나누기** — 헤더·메인·푸터·사이드 등. 영역마다 컴포넌트 표 → 누락 없음
- **컴포넌트 ID 부여** — 4.1, 4.2 식. QA·개발이 "4.7에 버그 있어요" 라고 정확히 지칭 가능
- **데이터 출처 명시** — "사용자 이름 표시" ❌, "`GET /api/v1/users/me` > name" ⭕
- **상태 4~6가지 정의** — Loading·Empty·Error·Success 빠뜨리지 말기. 흔히 잊는 게 Empty와 Error
- **인터랙션 → Analytics 매핑** — 화면 정의서 단계에서 이벤트 식별. 개발 시점에 추가하면 늘 누락
- **호버·툴팁도 명시** — 단순 클릭만 적지 말고 호버·롱프레스·스와이프까지
- **반응형 변화 표로** — Mobile에서 무엇이 어떻게 바뀌는지 표로. "반응형 적용" 한 줄로 끝내지 말기
- **접근성 체크리스트** — 키보드·스크린 리더·색 대비·Focus 4가지. 출시 직전 발견하면 늦음
- **권한·세션 예외** — 모든 화면 공통. 한 번 정의해두면 화면별 복사
- **정책 링크 — 본문 분기** — 알고리즘·정책 본문은 별도 문서. 화면 정의서엔 링크만
- **외주 발주 시 검수 기준** — 외주 프로젝트면 화면 정의서가 곧 검수 기준. 모호함 없게

## 자주 하는 실수

- **와이어프레임 없이 텍스트만** — 추상적, 디자이너·개발이 다르게 해석
- **영역 구분 없음** — 컴포넌트가 50개 나열 → 어디에 무엇인지 모름
- **데이터 출처 누락** — "표시한다"만 적고 어디서 오는지 안 적음 → API 명세 따로 만나야 함
- **상태 1~2개만** — Success만 정의, Loading·Empty·Error 누락 → 개발이 알아서 처리 → 일관성 깨짐
- **인터랙션 누락** — 호버·롱프레스·스와이프 등 → 디자인은 했는데 동작이 다름
- **Analytics 이벤트 누락** — 화면 정의서에서 식별 안 하면 출시 후 측정 불가
- **반응형 "적용" 한 줄** — Mobile에서 어떻게 바뀌는지 명시 안 함 → 디자인이 PC로만 만들어짐
- **접근성 무시** — 키보드·스크린 리더·색 대비 누락 → WCAG 통과 못 함
- **정책 본문을 화면 정의서에** — 매칭 알고리즘 가중치를 화면 정의서에 길게 → 관리 분산
- **권한·세션 예외 매번 적기** — 공통 예외인데 화면마다 다르게 정의 → 정합성 깨짐
- **변경 시 와이어·정의서 비동기 갱신** — 와이어만 바뀌고 정의서 묵음 → 개발이 혼란
- **화면 ID 누락** — IA의 P-XXX와 매칭 안 됨 → 추적 불가
