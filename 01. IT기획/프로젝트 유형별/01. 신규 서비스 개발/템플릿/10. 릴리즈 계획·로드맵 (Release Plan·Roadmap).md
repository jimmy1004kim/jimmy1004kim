## 이 문서는

서비스의 **버전·기능·일정을 시간 축으로 풀어낸 출시 계획**.

"무엇을 언제 출시할 것인가, 다음 분기·반기에 어디까지 갈 것인가, 어떤 순서로 가치를 누적할 것인가" 를 정리한다.

WBS·MVP·PRD와의 관계:

| 구분    | PRD      | MVP 범위 정의서 | 릴리즈 계획       | WBS         |
| ----- | -------- | ---------- | ------------ | ----------- |
| 단위    | 서비스 전체   | 1차 출시 범위   | **버전·시점·테마** | 작업·일정       |
| 깊이    | 무엇을·왜    | 무엇·무엇 안 함  | **언제 무엇 출시** | 누가 며칠에 끝낼 것 |
| 청중    | 전체 이해관계자 | 의사결정자·팀    | 경영진·외부·팀     | 개발·PM       |
| 시간 단위 | -        | 출시 시점 1개   | 분기·반기·연      | 일·주         |

**핵심**: 릴리즈 계획은 **"중장기 시간 축의 청사진"**. MVP가 출시 1개 시점이라면, 릴리즈 계획은 그 뒤 1~2년의 흐름.

### 릴리즈 계획 vs 로드맵 vs WBS

|산출물|시간 범위|깊이|변경 빈도|
|---|---|---|---|
|**WBS**|1~3개월|일·주 단위 작업|매주|
|**릴리즈 계획**|3~12개월|버전·테마|분기|
|**로드맵** (제품 로드맵)|6~24개월|큰 방향·테마|분기·반기|

세 가지를 합쳐서 부르기도 한다. 이 가이드는 **릴리즈 계획(중기)** 중심, **로드맵(장기)** 섹션도 포함.

### 두 가지 작성 방식

|방식|형태|적합한 상황|
|---|---|---|
|**시점 기반 (Date-driven)**|"12/15 베타 출시, 4/1 정식 출시"|외부 약속·마케팅 이벤트가 정해진 경우|
|**테마 기반 (Theme-driven)**|"Q1: 신뢰 인프라, Q2: 성장"|불확실성 큰 신규 서비스. 시점 약속이 부담|

**스타트업·신규 서비스는 테마 기반이 더 현실적**. 시점 기반은 외부에 약속한 시점만 사용 (베타·정식 출시 등).

## 언제 만드나

- MVP 범위 정의서 합의 후
- 본격 개발 진입 전 (전체 일정 잡기)
- 분기 시작 시점 (Q1·Q2 시작 전 분기 갱신)
- 의사결정자·경영진·투자자 보고 자료 필요할 때
- 외부 이해관계자(파트너·고객)와 약속 잡을 때

**기준**: "다음 분기·반기에 무엇을 할 거야?" 질문이 나올 때.

## 어떤 툴로

|툴|추천도|이유|
|---|---|---|
|**노션 DB + 타임라인 뷰**|⭐ 추천|테마·버전·기능 검색·필터 강함|
|**ProductBoard**|추천|로드맵 전용. 사용자 피드백 연결|
|**Productboard·Aha!·Roadmunk**|추천|로드맵 전용 SaaS|
|Jira 로드맵 (Advanced Roadmaps)|보조|개발 중심·세부 추적 강함|
|Figma·Miro|보조|발표·시각화용|
|PowerPoint|보조|외부·경영진 발표|
|Excel·Google Sheets|보조|단순 표|

**최적 조합**: 노션 DB (내부 관리) + PowerPoint·Figma (외부·경영진 발표용).

## 들어가야 할 것

- 메타 (서비스명·기간·작성자·버전)
- 비전·중장기 목표
- 분기별 테마 (Theme)
- 버전별 출시 계획 (MVP·v1·v2 ...)
- 각 버전의 핵심 기능·KPI 목표
- 일정 타임라인 (시각)
- 의존성·리스크
- 변경 관리 (로드맵 갱신 주기)
- 관련 산출물 링크

## 작성 절차

1. **비전·중장기 목표 확인** — 1~2년 후 어디로 갈 것인가
2. **분기별 테마 도출** — 분기마다 핵심 가치·목표 1개
3. **버전 명명** — MVP / v1 / v2 / v3 ... 또는 코드네임
4. **기능 → 버전 매핑** — PRD의 모든 FR을 어느 버전에 넣을지
5. **일정 타임라인** — 시각화 (간트·타임라인)
6. **KPI 목표** — 각 버전 출시 후 목표 지표
7. **의존성·리스크** — 버전 간 선후관계, 외부 의존성
8. **이해관계자 합의** — 의사결정자 + 경영진 + 팀
9. **변경 절차** — 분기마다 갱신, 외부 변경 시 ADR

## 작성 팁

- **테마 기반으로 시작** — 시점 기반은 외부 약속에만. 내부 계획은 테마 기반이 현실적
- **분기 1테마 원칙** — 한 분기에 여러 테마 → 집중력 분산. 1테마 + 보조 1개까지
- **버전 명명 일관성** — v0.1 / v1.0 / v1.5 / v2.0 명확한 체계. 코드네임 사용 시에도 버전 번호 병기
- **외부 공유 버전 분리** — 내부는 상세, 외부는 테마·KPI만. 외부에 기능 디테일 공개는 위험
- **KPI 목표를 버전마다** — 출시 후 검증 기준이 됨. 목표 없는 출시는 결과 평가 불가
- **다음 버전 진입 조건 명시** — "v0.1이 어떻게 되면 v1.0 시작?" 미리 정의. 안 그러면 매번 회의
- **의존성 사전 식별** — 외부 API·법무·채용 등. 깨지면 일정 연쇄 영향
- **리스크별 피벗 시나리오** — H1·H2 검증 실패 시 어디로 갈지 미리 그림. 위기 시 즉시 대응
- **분기 회고 + 분기 갱신** — 분기마다 회고 → 다음 분기 계획 갱신. 살아있는 로드맵
- **WBS와 정합성** — WBS의 작업이 릴리즈 계획의 버전에 매핑되어야. 분기 시작 시 점검
- **포트폴리오 가치** — 잘 만든 로드맵 + 실제 실행 결과는 PM의 가장 강력한 케이스 스터디
- **시각화 + 텍스트 백업** — 시각형(Figma) 발표용, 텍스트(노션) 검색·연결용
- **버전 출시 ±2주 룰** — 작은 일정 변경은 PM 권한, 큰 변경은 의사결정자 승인. 명문화

## 자주 하는 실수

- **기능 나열만** — "Q1: A 기능, B 기능, C 기능". 테마·목적 없으면 의미 없음
- **시점 기반 약속** — 외부에 "9/1 출시" 약속했다가 지연 → 신뢰 손상. 신규 서비스는 테마 기반 권장
- **KPI 없는 버전** — 출시 후 성공 여부 평가 불가
- **다음 버전 진입 조건 모호** — "베타 끝나면 정식 출시" 막연. 어떤 검증·지표가 충족돼야 하는지 명시 X
- **분기 4테마** — 한 분기에 너무 많은 목표 → 다 못 함. 1~2개로 압축
- **외부 공유 = 내부 그대로** — 기능 디테일·내부 일정을 외부 발표 → 약속 부담 + 경쟁사 노출
- **분기 갱신 안 함** — v0.1 초안 그대로 1년 유지 → 현실과 괴리
- **의존성 누락** — 외부 API·법무·채용 의존성을 안 적음 → 일정 연쇄 영향
- **피벗 시나리오 없음** — 가설 검증 실패 시 어디로 갈지 미정 → 위기 시 결정 못 함
- **WBS와 단절** — 릴리즈 계획과 WBS가 따로 → 실제 작업이 버전에 안 맞음
- **시각화만** — 예쁜 간트만 있고 텍스트 백업 없음 → 검색·연결 못 함
- **포트폴리오 관점 누락** — 로드맵 실행 결과를 케이스 스터디로 안 정리 → 자산 손실

## 작성 후 체크

- [ ] 비전·중장기 목표가 있는가
- [ ] 분기별 테마가 1~2개로 압축되었는가
- [ ] 버전별 출시 계획이 핵심 기능·KPI 목표와 함께 있는가
- [ ] 각 버전의 다음 버전 진입 조건이 명시되었는가
- [ ] 시간 타임라인이 시각화 + 텍스트 백업되었는가
- [ ] PRD의 모든 FR이 어느 버전에 매핑되었는가
- [ ] 외부·내부 의존성이 식별되고 영향 버전이 명시되었는가

- [ ] 변경 관리 절차(분기 갱신·일정 변경 권한)가 명문화되었는가
- [ ] 외부 공유 버전(경영진·투자자용)이 별도로 마련되었는가
- [ ] WBS·MVP·PRD와 정합한가
- [ ] 분기 갱신이 정기적으로 일어나는가
- [ ] 변경 이력이 누적되고 있는가
