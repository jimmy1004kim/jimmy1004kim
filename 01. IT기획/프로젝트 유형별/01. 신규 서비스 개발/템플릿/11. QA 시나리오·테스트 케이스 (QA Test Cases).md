## 이 문서는

서비스의 **기능·화면·시나리오를 어떻게 검증할지**를 정리한 문서.

"어떤 테스트를 할 것인가, 각 테스트는 무엇을 입력하고 어떤 결과를 기대하는가, 통과·실패 기준은 무엇인가" 를 정리한다.

기능 정의서·화면 정의서와의 관계:

| 구분  | 기능 정의서  | 화면 정의서     | QA 시나리오         |
| --- | ------- | ---------- | --------------- |
| 단위  | 기능 1개   | 화면 1개      | **테스트 케이스 1개**  |
| 깊이  | 무엇을·어떻게 | 무엇이·어디·어떻게 | **무엇을 어떻게 검증**  |
| 청중  | 개발·QA   | 디자인·개발·QA  | QA·개발           |
| 시점  | 설계 단계   | 설계 단계      | 설계 + 개발 + 출시 직전 |

**핵심**: QA 시나리오는 **기능·화면·정책이 합쳐서 작동하는지 검증**. 단위 코드 테스트(Unit Test)와 다르다.

### 테스트 유형 (전체 맥락)

|유형|누가|무엇을|시점|
|---|---|---|---|
|**Unit Test**|개발|함수·메서드 단위|개발 중 (자동)|
|**Integration Test**|개발|모듈 간 연동|개발 중 (자동)|
|**QA / E2E Test**|**QA**|**사용자 시나리오**|**설계~출시**|
|**UAT (User Acceptance Test)**|사용자·고객|실제 사용|출시 직전|
|**Performance Test**|개발·QA|성능·부하|출시 직전|
|**Security Test**|보안팀|취약점|출시 직전|

이 가이드는 **QA / E2E Test 시나리오** 중심.

### QA 시나리오의 두 가지 스타일

|스타일|형식|적합|
|---|---|---|
|**체크리스트 방식**|항목별 ✓|간단·반복 검증|
|**시나리오 방식**|Given-When-Then|복잡한 사용자 흐름|

이 가이드는 두 가지 모두 다룬다.

## 언제 만드나

- 기능 정의서·화면 정의서 합의 후 (병행)
- 개발 착수 직전 (개발이 QA 케이스 보고 일함 — 일종의 Spec)
- 출시 직전 (회귀 테스트·릴리즈 QA)
- 신규 기능 추가 시 (관련 케이스 추가)

**기준**: "이 기능 어떻게 검증할 거예요?" 질문 나올 때.

## 어떤 툴로

| 툴                               | 추천도     | 이유                   |
| ------------------------------- | ------- | -------------------- |
| **노션 DB**                       | ⭐ 강력 추천 | 케이스별 페이지·필터·실행 결과 누적 |
| **TestRail / Zephyr / qase.io** | 추천      | QA 전용 도구, 규모 크면      |
| **Excel**                       | 보조      | 간단한 케이스 표            |
| **Jira (Xray 플러그인)**            | 보조      | 개발 연동 강함             |
| Word·PDF                        | 비추      | 살아있는 문서엔 부적합         |

**최적**: 노션 DB로 케이스 1개 = 1행 = 1페이지. 실행 결과(Pass·Fail·Blocked) 속성으로 관리.

## 들어가야 할 것

- 메타 (서비스명·QA 차수·테스트 환경)
- 테스트 범위·제외 범위
- 테스트 유형 (기능·UI·성능·보안·접근성·반응형)
- 테스트 케이스 (ID·시나리오·기대 결과·우선순위)
- 실행 결과 (Pass·Fail·Blocked·N/A)
- 버그 리포트 연결
- 회귀 테스트 계획
- 출시 전 체크리스트
- 관련 산출물 링크

## QA 진행의 5단계

```
1. 테스트 계획     → 범위·환경·일정·인원
2. 케이스 작성     → 기능 정의서·화면 정의서 기반
3. 테스트 실행     → Pass·Fail 기록
4. 버그 리포트     → Fail 케이스에 대해 이슈 등록
5. 회귀·재테스트  → 버그 수정 후 재검증
```

## 작성 절차

1. **테스트 범위 정의** — 이번 QA에서 무엇을 검증할지
2. **케이스 도출 — 기능 정의서·화면 정의서 기반**
3. **시나리오 분류** — 정상·분기·예외·경계·성능·접근성
4. **케이스 작성** — Given-When-Then 또는 체크리스트
5. **우선순위 부여** — Critical / High / Medium / Low
6. **이해관계자 리뷰** — 개발·CS·PO
7. **실행** — 환경 준비 → 케이스 실행 → 결과 기록
8. **버그 리포트** — Fail 케이스에 이슈 등록
9. **회귀 테스트** — 수정 후 재검증
10. **출시 전 체크리스트 통과** — 결정

### TC-501. 매칭 정상 — 5명 추천 결과 표시

#### 케이스 메타

|항목|내용|
|---|---|
|케이스 ID|TC-501|
|케이스명|매칭 정상 — 5명 추천 결과 표시|
|카테고리|기능 (정상 흐름)|

|자동화 가능|✅ (E2E 자동화 권장)|

#### 시나리오 (Given-When-Then)

- **Given**: 기업 회원(test_company_01)이 로그인 상태이고, 결제 수단 등록 완료, 프리랜서 풀에 적합 후보 50명 이상 존재
- **When**: 프로젝트 등록 페이지(P-110)에서 모든 필수 항목 입력 후 "매칭 시작" 클릭
- **Then**:
    1. 매칭 결과 페이지(P-113) 자동 이동
    2. 추천 프리랜서 5명 카드 형태로 표시
    3. 각 카드에 매칭 점수·검증 마크·이름·경력·평가·단가·연락하기 버튼 표시

## 작성 팁

- **케이스는 기능·화면 정의서 기반** — 머리에서 만들지 말고 정의서를 보고 도출. 정의서가 명확해야 케이스도 명확
- **카테고리 분류 표준** — 정상·분기·예외·경계·UI·성능·접근성·보안 8가지. 한 카테고리도 빠뜨리면 누락 발견
- **우선순위 4단계** — Critical·High·Medium·Low. 일정 부족 시 Critical만이라도 100%
- **Given-When-Then 형식** — 시나리오의 전제·행동·기대를 분리. 모호함 없음
- **테스트 데이터 명시** — "어떤 계정·어떤 값"까지. "그냥 입력" ❌
- **환경·전제 명시** — 브라우저·OS·디바이스·권한. 환경 다르면 결과 다름
- **실행 결과 누적** — 1회 Pass가 영원한 Pass 아님. 매 차수 결과 기록
- **자동화 가능 표시** — E2E·UI 자동화 가능한 케이스 표시. 회귀 테스트에서 시간 절감
- **버그 ↔ 케이스 양방향 링크** — Fail 케이스에 버그 ID, 버그 리포트에 케이스 ID
- **회귀 테스트 별도 관리** — 출시·패치 시마다 핵심 케이스 재실행
- **출시 전 체크리스트로 게이트** — 통과 못 하면 출시 차단. 명문화
- **외주 발주 시 검수 기준** — QA 시나리오가 곧 검수 기준. 외주 프로젝트는 더 상세히
- **베타 사용자 피드백 → 케이스 보강** — 실제 사용자 사용 시 발견된 이슈를 다음 케이스로

## 자주 하는 실수

- **케이스가 기능 정의서와 불일치** — QA가 정의서 안 보고 머리로 만듦 → 빠진 케이스 다수
- **Happy Path만** — 정상 흐름만 검증, 예외·경계 누락 → 출시 후 사용자가 발견
- **우선순위 없음** — 모든 케이스 동일 → 일정 부족 시 우선순위 결정 못 함
- **Given-When-Then 모호** — "잘 작동하는지 확인" 추상적 → 매번 다른 사람이 다르게 검증
- **테스트 데이터 누락** — "적당한 값 입력" → 재현 불가
- **환경 누락** — 브라우저·OS 안 적음 → 환경별 이슈 발견 못 함
- **자동화 가능 표시 누락** — 회귀 테스트에서 수동만 반복 → 시간·비용 폭증
- **버그 ↔ 케이스 연결 안 함** — 버그 발견했는데 어떤 케이스에서 발견했는지 추적 불가
- **회귀 테스트 누락** — 신규 기능만 검증, 기존 기능 재검증 안 함 → Regression 발생
- **출시 전 체크리스트 없음** — 출시 GO·NO-GO 결정 모호 → 누락된 검증 후 출시
- **성능·접근성·보안 누락** — 기능만 검증 → 출시 후 다른 영역에서 폭발
- **베타 피드백 미반영** — 실 사용자 이슈를 케이스에 추가 안 함 → 다음 회귀 때 또 발생
