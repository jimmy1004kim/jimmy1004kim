## 이 문서는

서비스 운영의 **규칙·기준·조건**을 명문화한 문서.

"환불은 며칠까지 가능한가, 매칭 점수는 어떻게 계산하는가, 누가 무엇을 볼 수 있는가, 어떤 조건에서 자동 취소되는가" — 이런 "규칙"을 한 곳에 모은다.

기능 정의서·약관과의 관계:

|구분|기능 정의서|정책 정의서|약관|
|---|---|---|---|
|단위|기능 1개|정책 1개|서비스 전체|
|깊이|작동 방식 (how it works)|**규칙·기준 (what's the rule)**|법적 합의|
|청중|개발·QA|개발·QA·CS·법무·운영|사용자·법무|
|변경 빈도|비교적 자주|**매우 드물게 (변경 시 영향 큼)**|매우 드물게|

**핵심**: 정책은 **여러 기능에 걸쳐 일관되게 적용되는 규칙**. 기능 정의서에 같은 규칙을 반복 적으면 불일치 발생. 정책 정의서에 한 번 정의하고 기능들이 참조.

### 왜 정책을 별도로 관리하나

- **변경 영향이 크다** — 환불 정책 1줄 바뀌면 결제·환불·CS·세무 다 영향
- **여러 기능에 공통 적용** — 같은 정책이 여러 화면·기능에 등장
- **법무·CS의 영역** — 개발만의 영역 아님. 법무·CS 검토 필수
- **외부 노출 가능성** — 일부 정책(환불·개인정보)은 약관·고객센터 안내로 노출

## 정책의 종류

|종류|예시|
|---|---|
|**운영 정책**|일일 매칭 한도, 메시지 발송 한도, 활성 기준|
|**결제·환불 정책**|환불 가능 기간, 에스크로 보관 기간, 수수료 정책|
|**권한·접근 정책**|누가 무엇을 볼 수 있는가, 관리자 권한 위계|
|**알고리즘 정책**|매칭 가중치, 추천 우선순위, 랭킹 산정|
|**데이터 정책**|보관 기간, 삭제·익명화, 백업|
|**콘텐츠 정책**|게시 금지 표현, 신고·삭제 기준|
|**분쟁·중재 정책**|분쟁 신청 조건, 중재 절차, 처리 시한|
|**약관·법적 정책**|가입 자격, 책임 범위, 면책|

## 언제 만드나

- 기능 정의서 작성 중 "이건 정책으로 빼야겠다" 싶을 때
- 같은 규칙이 여러 기능·화면에 반복될 때
- 법무·CS 검토가 필요한 규칙
- 변경 시 다른 산출물에 영향이 큰 규칙

**기준**: "이 규칙은 한 기능에만 속하는가, 여러 기능에 공통인가" — 여러 기능에 공통이면 정책으로 분기.

|툴|추천도|이유|

**최적**: 노션 DB로 정책 1개 = 1페이지. 정책 ID로 기능·화면·API에서 참조.

# 📌 예시 — TalentMatch / POL-005 매칭 알고리즘 정책 v1.0

> 가상 사례. FR-005에서 분기된 정책 본문

## 정책 메타

|항목|내용|
|---|---|
|정책 ID|POL-005|
|정책명|매칭 알고리즘 정책 (가중치·필터·우선순위)|
|카테고리|알고리즘|
|상태|🟢 발효|
|버전|v1.0|
|발효일|2026-09-01 (MVP 출시 시점)|
|작성자|홍길동 (PO)|
|승인자|대표 + CTO|
|리뷰어|ML 엔지니어 / 개발팀 리드 / 법무 (공정성 검토)|
|사용자 노출|⬜ 노출 안 함 (내부 운영용). 단, 매칭 점수 산출 근거 일부는 화면 툴팁(P-113)에 공개|

## 1. 정책 목적·배경

### 목적

기업이 등록한 프로젝트와 프리랜서를 자동으로 매칭하는 알고리즘의 **계산 기준·가중치·필터 조건**을 명문화하고, 이를 통해 매칭 품질·공정성·일관성을 보장한다.

### 배경

- 매칭 알고리즘은 NSM(계약 완료 건수)의 입구. 알고리즘이 흔들리면 서비스 핵심 가치 흔들림
- 가중치·필터가 코드에만 있으면 비즈니스 영향 추적 불가
- 공정성·차별 이슈 (성별·나이·지역 차별 등) 사전 차단 필요
- 알고리즘 변경 시 영향을 추적·롤백할 수 있어야 함

## 2. 정책 본문

### 핵심 규칙

매칭 점수는 다음 4가지 요소의 가중 합산으로 0~100점 산출된다.

|요소|가중치|측정 기준|
|---|---|---|
|기술 스택 매칭|**40%**|프로젝트 요구 기술 ∩ 프리랜서 보유 기술 / 요구 기술 수|
|활동 데이터|**30%**|GitHub 커밋·블로그 글 빈도·최근성 (검증 데이터 기반)|
|가용성|**15%**|현재 진행 프로젝트 수 + 시작 가능 일자 적합도|
|평균 단가 적합도|**15%**|프로젝트 예산 ±20% 범위에 들어오는 정도|

### 상세 규칙

#### 2-1. 1차 필터 (점수 계산 대상 추출)

다음 조건을 모두 충족하는 프리랜서만 점수 계산 대상.

- [x] 직무 카테고리 일치 (예: 개발·기획·디자인·PM·기타)
- [x] 요구 기술 스택 중 **최소 1개 이상 보유**
- [x] 가입 후 14일 이상 경과 (이메일·전화 인증 완료)
- [x] 최근 90일 내 활동 기록 있음 (로그인 또는 프로필 갱신)
- [x] 강제 정지 상태 아님 (POL-009 활성 정책 참조)
- [x] 본인이 등록한 프로젝트와 동일 기업의 프로젝트 매칭 제외 (이해 충돌)

#### 2-2. 가중치 계산 상세

**기술 스택 매칭 (40점 만점)**

- 점수 = (매칭된 기술 수 / 요구 기술 수) × 40
- 예: 요구 5개 중 4개 보유 → (4/5) × 40 = 32점
- 보유 기술이 요구 기술의 상위 호환이면 1로 카운트 (예: 요구 "React", 보유 "Next.js")

**활동 데이터 (30점 만점)**

- GitHub 활동 점수 (15점): 최근 90일 커밋 수 × 0.5 (최대 15점, 30커밋 = 15점)
- 블로그 활동 점수 (10점): 최근 180일 게시물 수 × 2 (최대 10점)
- 검증 마크 보너스 (5점): GitHub·블로그 자동 검증 완료 시 5점

**가용성 (15점 만점)**

- 현재 진행 프로젝트 수: 0개 (10점) / 1개 (7점) / 2개 (3점) / 3개 이상 (0점)
- 시작 가능 일자 적합도 (5점): 프로젝트 시작일 기준 ±7일 내 가능 (5점) / ±14일 (3점) / ±30일 (1점) / 그 외 (0점)

**평균 단가 적합도 (15점 만점)**

- 프리랜서 선호 단가가 프로젝트 예산의 **±20% 범위**: 15점
- ±20~30% 범위: 10점
- ±30~40% 범위: 5점
- 40% 초과: 0점

#### 2-3. 최종 선별

- 계산된 점수 상위 5명 선별 (동점 시 활동 데이터 점수 우선)
- 최소 점수 미달 (50점 미만)이면 5명 미달 가능 → 도착한 수만 표시 (S-03 Partial 상태)
- 매칭 결과 0건이면 S-02 Empty 상태로 전환

#### 2-4. 공정성·차별 방지

다음 항목은 점수 계산·필터에 **절대 사용 안 함**:

- 성별·나이·지역
- 학력·졸업 학교
- 사진·외모
- 종교·정치 성향
- 결혼·자녀 유무

위반 시 즉시 알고리즘 코드 리뷰 + ADR 작성 + 법무 검토 의무.

## 3. 적용 범위

- **적용 대상**: FR-005 AI 매칭 추천 기능 (P-113 매칭 결과 페이지)
- **적용 시점**: 매칭 요청 시점부터 (24시간 캐시 만료까지 동일 결과)
- **지역·플랫폼 제약**: 국내 한정 (해외 확장 시 별도 정책 필요)

## 4. 예외

- **베타 출시 초기 90일** — 프리랜서 풀이 작아 1차 필터의 "최근 90일 활동" 조건을 "최근 180일"로 완화
- **추천 프리랜서 0건 발생 시** — 1차 필터의 "요구 기술 1개 이상" 조건만 유지하고 점수 임계치 (50점) 무시한 채 상위 5명 표시
- **관리자가 수동 매칭 요청 시** — 본 정책 우회 가능 (분쟁 조정 등 특수 상황)
- **VIP 기업 (대기업·연 거래액 1억 이상)** — v1 출시 이후 "우선 추천 풀" 별도 운영 검토 (현재 정책엔 미포함)

## 5. 위반 시 처리

> 알고리즘 정책의 "위반"은 코드·운영의 정책 미준수를 의미

|위반 유형|1차 처리|2차|최종|
|---|---|---|---|
|가중치·필터 코드 변경 시 ADR 누락|코드 리뷰 반려 + ADR 작성 요청|반복 시 코드 머지 차단|정책 위반 명시·재발 방지 회의|
|공정성·차별 항목 사용 발견|즉시 알고리즘 롤백|법무 보고 + 사후 분석|외부 공지 및 법적 검토|
|알고리즘 결과가 정책 본문과 불일치|운영 알람 + 즉시 조사|임시 fallback 알고리즘 적용|정책·코드 정합성 회복|

## 6. 의사결정 근거

### 가중치 결정 근거

- 기술 스택 매칭 40% — 핵심 매칭 요인 (사용자 인터뷰 30건 중 27건이 "기술 매칭이 가장 중요"라 응답)
- 활동 데이터 30% — 검증된 활동이 매칭 신뢰도의 핵심 차별점 (PRD H3 가설)
- 가용성 15% — 매칭 성공 후 실제 계약 가능성을 좌우
- 단가 적합도 15% — 예산 차이가 30% 넘으면 계약 성사율 급락 (위시켓 사례 분석)

### 1차 필터 결정 근거

- "최소 1개 기술 보유" — 0개면 매칭 의미 없음, 너무 엄격하면 풀 부족
- "가입 14일 경과" — 어뷰징 어카운트 차단
- "최근 90일 활동" — 비활성 프리랜서 노출 시 매칭 실패율 ↑

### 공정성 조항 근거

- 차별 항목 사용 시 법적 리스크 (남녀고용평등법·국가인권위법)
- 알고리즘 차별 이슈는 회복 불가한 평판 손상 (글로벌 사례 다수)

### 참고 벤치마크

- 위시켓 매칭 알고리즘 (공개 자료)
- LinkedIn Talent Insights 매칭 기준
- Upwork Best Match 알고리즘

상세는 **ADR-008 매칭 알고리즘 가중치 결정** 참조.

## 작성 팁

- **정책 ID로 추적** — POL-XXX 형식. 기능·화면·API가 정책 ID로 참조 → 정책 변경 시 영향 범위 즉시 파악
- **본문은 규칙·기준 중심** — "이렇게 작동한다" (기능 정의서) ❌, "이런 규칙이 있다" (정책 정의서) ⭕
- **예외를 반드시 명시** — 정책 본문만 적고 예외 안 적으면 영원히 분쟁 소지. "VIP는 예외", "베타 기간은 예외" 등 모두 적기
- **위반 시 처리도 정책의 일부** — 위반했는데 처리가 모호하면 정책 무의미
- **의사결정 근거를 본문에 포함** — 왜 가중치가 40%인지 안 적으면 6개월 후 본인도 모름. ADR 링크 + 요약
- **변경 절차 명문화** — 누가 승인하면 바꿀 수 있는지 미리 정의. 안 그러면 매번 합의 필요
- **사용자 노출 여부 결정** — 일부 정책(환불·개인정보)은 약관·고객센터에 노출 필요. 명시
- **법무·CS 리뷰 필수** — PO 혼자 작성 X. 법무는 법적 리스크, CS는 운영 현실성
- **공정성·차별 조항** — 알고리즘·콘텐츠 정책엔 차별 방지 조항 표준 포함
- **외부 사례·벤치마크** — 정책은 무에서 만들지 말고 외부 사례 참조. 위시켓·크몽·해외 플랫폼 등
- **약관과의 연결** — 약관 1조에 "본 약관에서 정하지 않은 사항은 정책 정의서를 따른다" 명시. 그래야 정책이 법적 효력
- **변경 이력 + ADR 양방향 링크** — 정책 변경은 영향 큼. ADR로 결정 맥락 보존
- **숫자로 명시** — "충분히", "적절히" 같은 표현 X. "최근 90일", "±20%" 같은 수치
