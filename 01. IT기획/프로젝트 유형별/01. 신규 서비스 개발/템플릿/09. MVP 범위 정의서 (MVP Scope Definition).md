## 이 문서는

**1차 출시(MVP) 범위에 무엇을 포함하고 무엇을 제외할지** 명시적으로 합의하는 문서.

"이번에 무엇까지 만들 것인가, 다음으로 미루는 것은 무엇인가, 왜 그 결정인가" 를 정리한다.

PRD·릴리즈 계획과의 관계:

|구분|PRD|MVP 범위 정의서|릴리즈 계획|
|---|---|---|---|
|단위|서비스 전체|**1차 출시 범위**|시간 축으로 풀어낸 출시 계획|
|깊이|무엇을·왜|**포함·제외 + 의사결정 근거**|언제·어떻게|
|청중|전체 이해관계자|의사결정자·팀 전체|개발·QA·마케팅|
|변경 빈도|자주|**거의 안 바뀜** (바뀌면 큰 영향)|자주|

**핵심**: MVP 범위 정의서는 **"NO" 의 문서**다. 무엇을 안 할지가 무엇을 할지보다 더 중요. MVP를 정의 못 하는 게 신규 서비스 실패의 가장 흔한 원인.

### MVP의 진짜 의미

흔히 오해되는 MVP의 의미:

|❌ 흔한 오해|✅ 진짜 의미|
|---|---|
|최소한의 화면만 있는 v1|**가장 작은 검증 가능한 가설**|
|베타 버전·시제품|시장에 내놓을 수 있는 가장 작은 단위|
|기능 줄이기|가설을 검증하기 위해 꼭 필요한 것만|
|"그냥 출시" 못함|**반드시 사용자가 쓸 수 있어야**|

**MVP = Minimum Viable Product**:

- **Minimum**: 최소
- **Viable**: 실제로 쓸 수 있는 (작동하는)
- **Product**: 시장에 내놓을 수 있는 형태

"최소한"이지만 "쓸 수 있어야" 한다. 절반만 작동하는 건 MVP 아님.

### MVP 정의의 3가지 함정

|함정|증상|
|---|---|
|**욕심 MVP**|"이것도 있어야지" 가 30개. MVP가 v1이 됨|
|**빈약 MVP**|사용자가 "이거 뭔데?" → 가치 검증 불가|
|**모호 MVP**|포함·제외 경계가 흐려서 매번 논쟁|

이 문서는 위 3가지를 모두 막기 위한 명시적 합의 장치.

## 언제 만드나

- PRD 합의 후, 본격 설계·개발 진입 직전
- 일정·예산 제약이 명확해질 때
- 의사결정자 간 범위 해석이 다를 때
- v2.0급 개편 시 (Re-MVP)

**기준**: "이번에 어디까지 만들지 명확히 해달라" 는 요청·논쟁이 나올 때.

## 어떤 툴로

|툴|추천도|이유|
|---|---|---|
|**노션 페이지**|⭐ 추천|표·체크리스트·링크 자유|
|Confluence|추천|회사 표준이면|
|Google Sheets|보조|우선순위 매트릭스 작업 시|
|PowerPoint|보조|의사결정 발표용|

**팁**: PRD 안에 MVP 섹션이 있어도, 별도 문서로 분리하는 게 좋음. PRD가 자주 갱신되더라도 MVP 범위는 안 흔들려야.

## MVP 정의의 5단계

```
1. 검증할 가설 명확화  → "MVP로 무엇을 검증할 것인가"
2. 핵심 가치 흐름 식별  → "사용자가 가치를 받는 단일 경로"
3. 기능 우선순위         → 가설 검증에 필수 vs 보조
4. 포함·제외 의사결정    → 시간·비용·기술 제약 반영
5. 검증 지표 정의        → "MVP 성공/실패 판단 기준"
```

## 들어가야 할 것

- 메타 (서비스명·MVP 출시 목표일·결정자)
- 검증할 가설 (Riskiest Assumption)
- 핵심 가치 흐름 (Core User Journey)
- MVP 포함 기능 (Must-have)
- MVP 제외 기능 (Won't-have, 분류·사유)
- 우선순위 매트릭스 (MoSCoW 등)
- 검증 지표 (성공·실패 기준)
- 의사결정 근거
- 변경 관리 (범위 변경 시 절차)
- 관련 산출물 링크

## 작성 절차

1. **검증할 가설 명확화** — "MVP로 무엇을 검증하는가"가 가장 중요
2. **핵심 가치 흐름 식별** — 사용자가 첫 번째 가치를 받는 최단 경로
3. **기능 분류** — PRD의 FR 리스트를 MoSCoW로 분류
4. **포함·제외 결정 회의** — 의사결정자 + 핵심 팀
5. **제외 사유 명시** — "다음 버전", "비용 대비 가치", "기술 한계" 등
6. **검증 지표 정의** — MVP 출시 후 무엇으로 성공·실패 판단할지
7. **이해관계자 합의** — 모두가 같은 그림인지 확인
8. **범위 변경 절차 명문화** — 출시 전까지 추가 요청을 어떻게 처리할지

# 📌 예시 — TalentMatch MVP 범위 정의서 v1.0

> 가상 사례. PRD의 MVP 범위를 별도 문서로 명시화

## MVP 메타

|---|---|

|MVP 버전 명|Closed Beta (MVP v1.0)|
|출시 목표일|2026-12-15|
|의사결정자|대표 + CTO|
|작성자|홍길동 (PO)|
|작성일|2026-07-05|
|상태|🟢 합의·발효 (2026-07-12 의사결정 회의)|
|관련 PRD|TalentMatch PRD v1.0|

## 1. 검증할 가설

### 핵심 가설

**[MVP-H1]** 기업은 "검증된 IT 프리랜서를 1주 안에 매칭받는 것"에 거래액의 5% 수수료를 지불할 의향이 있다.

- **현재 신뢰 수준**: 중간 (사용자 인터뷰 15건 긍정 답변)
- **검증 방법**: 베타 3개월 동안 매칭 → 계약 → 결제 funnel 측정
- **성공 기준**: 추천받은 기업의 **30% 이상**이 실제 결제까지 도달
- **실패 기준**: 전환율 10% 미만 → 매칭 알고리즘 전면 재설계 또는 BM 재검토

**[MVP-H2]** IT 프리랜서는 "안정적 프로젝트 추천"에 거래액의 3% 수수료를 지불할 의향이 있다.

- **현재 신뢰 수준**: 낮음 (베타 기간 면제로 직접 검증 불가)
- **검증 방법**: 정식 출시 시점(수수료 부과 시작) 프리랜서 이탈률 측정
- **성공 기준**: 정식 출시 시점 이탈률 **30% 이하**
- **실패 기준**: 이탈률 50% 이상 → 수수료율 인하 또는 프리미엄 모델 전환

**[MVP-H3]** 포트폴리오 자동 검증이 매칭 성사율을 30% 이상 향상시킨다.

- **검증 방법**: 검증 마크 보유자 vs 미보유자의 매칭 → 계약 전환율 A/B 비교
- **성공 기준**: 검증 보유자의 전환율이 미보유자 대비 **1.3배 이상**
- **실패 기준**: 1.1배 미만 → 검증 시스템 ROI 재검토

## 2. 핵심 가치 흐름

기업이 첫 번째 가치를 받는 최단 경로:

```
[기업 가입]
   ↓
[프로젝트 등록]
   ↓
[AI 매칭 5명 추천] ← 첫 번째 "와우 모먼트"
   ↓
[프리랜서 선택 + 메시지]
   ↓
[표준 계약 체결]
   ↓
[1차 마일스톤 결제]
   ↓
[작업 시작] ← 가치 완성
```

프리랜서가 첫 번째 가치를 받는 최단 경로:

```
[프리랜서 가입]
   ↓
[프로필 + GitHub·블로그 연동]
   ↓
[자동 검증 마크 획득] ← 첫 번째 "와우 모먼트"
   ↓
[매칭 제안 수신]
   ↓
[계약 수락 + 작업 시작] ← 가치 완성
```

MVP는 이 두 흐름이 끝까지 작동해야 함. 중간 어디라도 끊기면 가설 검증 불가.

## 5. 우선순위 매트릭스 (MoSCoW)

|구분|비율|기능 ID|
|---|---|---|
|🟢 **Must** (출시 불가능 시 차단)|10개 / 15개 (67%)|FR-001 ~ FR-010|
|🟡 **Should** (중요하나 출시 가능)|-|(해당 없음 — MVP에선 Must로만 구성)|
|🟠 **Could** (시간 남으면 추가)|-|평가 우수 프리랜서 자동 배지·메시지 알림 푸시 (앱 출시 시)|
|🔴 **Won't** (이번엔 안 함)|5개 / 15개|FR-011 ~ FR-015 + 모바일 앱|

**경고**: Must 67%는 약간 높은 편. 일정 압박 시 가장 먼저 Should·Could 카테고리로 강등 가능한 기능 사전 식별 필요:

- FR-008 (양쪽 평가) — 베타 초기엔 단순 5점 별점만으로 시작 가능
- FR-009 (분쟁 조정) — 베타 초기엔 수동 운영(CS 직접 대응)으로 대체 가능

## 7. 의사결정 근거

### 포함 결정 근거

- **FR-001 ~ FR-010 모두 핵심 가치 흐름의 일부** — 빠지면 사용자가 끝까지 못 감
- 양면 시장 특성상 **양쪽 흐름 모두 작동해야** 검증 가능. 기업 측·프리랜서 측 모두 Must 포함

### 제외 결정 근거

- **모바일 앱 제외**: 모바일 웹으로 대체 가능. 앱은 매칭 → 계약 전환율 측정엔 영향 미미. 개발 비용·일정 부담만 큼
- **프리미엄·랭킹 제외**: 사용자 풀이 작을 때 의미 없음. 1,000명 이상 누적 후 활성화
- **화상 면접 영구 제외**: Zoom·Meet이 이미 성숙. 자체 개발은 가치 미만의 비용
- **정규직 매칭 영구 제외**: 정체성 모호화 차단. **"IT 단기 프리랜서"** 포지셔닝 보호

### 트레이드오프

|항목|트레이드오프|
|---|---|
|일정 ↔ 범위|**일정 우선** (12/15 비공개 베타 절대 사수). 범위 추가 요청은 강하게 거절|
|비용 ↔ 품질|**품질 우선** (결제·계약은 외부 신뢰가 핵심). PG·법무는 외부 전문가 비용 감수|
|사용자 만족 ↔ 출시 속도|**출시 속도 우선** (가설 검증이 더 중요). 완벽한 UX는 정식 출시 시점에|
|양면 균형 ↔ 한쪽 집중|**양면 균형**. 프리랜서 풀 100명 사전 확보 후 기업 측 모집 시작|

## 작성 팁

- **검증할 가설부터** — "무엇을 만들지" 보다 "무엇을 검증할지" 가 먼저. 가설이 흔들리면 MVP 흔들림
- **"NO" 가 핵심** — 포함 리스트보다 제외 리스트가 더 길어야 정상. 욕심 MVP 방지
- **핵심 가치 흐름 1개에 집중** — 여러 흐름을 동시에 검증 X. 메인 흐름 1개가 끝까지 작동하는지가 가장 중요
- **양면 시장은 양쪽 흐름 모두 Must** — 한쪽만 작동하면 가설 검증 불가. 풀 시드 전략 사전 마련
- **MoSCoW 비율 체크** — Must가 60% 이상이면 MVP가 아닐 가능성 ↑. 강등 후보 사전 식별
- **외부 도구로 대체 가능한 것 적극 활용** — 화상·결제·인증은 외부 도구가 더 성숙. 자체 개발 ROI 따져보기
- **출시 D-30 차단 룰** — MVP 출시 30일 전부터 신규 기능 추가 차단. 안정화에 집중. 명문화 필수
- **영구 제외(Out of Scope) 의미** — 정체성 모호화 차단. 정규직 매칭·디자인 외주 같은 항목은 절대 추가 안 함
- **검증 지표 = 출시 후 의사결정 기준** — 성공/실패 기준이 모호하면 출시 후 결정 못 함. 사전 합의 필수
- **사전 강등 후보 명시** — 일정 압박 시 Must → Should 강등할 후보 미리 표시. 위기 시 즉시 결정 가능
- **트레이드오프 명문화** — "일정 우선, 범위 양보" 같은 원칙을 사전에. 출시 직전 갈등 방지
- **포트폴리오 자산** — MVP 정의 잘 한 PM은 케이스 스터디로 가장 가치 있음

## 자주 하는 실수

- **검증할 가설 없는 MVP** — "이 정도면 출시" 식 결정 → 출시 후 무엇이 검증됐는지 모름
- **욕심 MVP** — Must 30개. 사실상 v1을 MVP라 부름. 일정 폭주 + 검증 불가
- **빈약 MVP** — 사용자가 가치 못 받음. "이거 뭔데?" → 가설 검증 불가
- **양면 시장 한쪽만** — 기업 측만 만들고 프리랜서 풀 0명 → 가치 흐름 못 돔
- **포함만 적고 제외 누락** — 출시 직전 "이것도 해주세요" 요청 폭주
- **제외 사유 모호** — "v2에서" 만 적고 왜 v1엔 못 하는지 안 적음 → 매번 재논쟁
- **검증 지표 모호** — "사용자 만족도 향상" 같은 추상 지표. 출시 후 결정 못 함
- **변경 절차 없음** — 추가 요청 처리 절차 없으면 출시 직전 매번 회의
- **D-30 차단 룰 없음** — 출시 직전까지 기능 추가 → 안정화 부족 → 출시 후 장애
- **PRD와 분리 안 함** — MVP를 PRD 섹션으로만 두면 PRD 갱신 때마다 흔들림. 별도 문서 권장
- **사전 강등 후보 누락** — 일정 압박 시 즉시 결정 못 함 → 일정 지연
- **포트폴리오 관점 누락** — MVP 정의는 PM 역량의 핵심. 케이스 스터디로 명확히 정리

## 작성 후 체크

- [ ] 검증할 가설(MVP-H)이 명확하고 측정 가능한가
- [ ] 핵심 가치 흐름이 그려졌고 양면 시장이면 양쪽 모두 그려졌는가
- [ ] Must 기능이 60% 이내인가 (이상이면 MVP 아닐 가능성)
- [ ] 제외 기능에 모두 제외 사유와 다음 시점이 명시되었는가
- [ ] Out of Scope(영구 제외) 항목이 정체성 보호 차원에서 명시되었는가
- [ ] 외부 도구로 대체 가능한 항목을 식별했는가
- [ ] 검증 지표가 단계별로 정의되었고 성공·실패 기준이 명확한가
- [ ] 의사결정 근거와 트레이드오프 원칙이 명문화되었는가
- [ ] 변경 관리 절차가 있는가 (특히 D-30 차단 룰)
- [ ] 사전 강등 후보가 식별되었는가
- [ ] 의사결정자 합의가 끝나고 발효되었는가
- [ ] PRD·릴리즈 계획·Analytics 등 관련 산출물과 정합한가
- [ ] 변경 이력이 누적되고 ADR과 연결되어 있는가
