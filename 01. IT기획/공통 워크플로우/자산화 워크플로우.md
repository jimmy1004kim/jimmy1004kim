## 이 문서는

프로젝트에서 만든 산출물·기법·교훈을 **다음 프로젝트에서 재사용 가능한 형태**로 일반화하여 공통 또는 유형별 템플릿으로 옮기는 절차.

이게 없으면 매 프로젝트가 처음부터 시작된다. 매번 PRD 양식을 새로 만들고, 매번 같은 함정에 빠진다. 자산화는 **"한 번 한 일을 다시는 처음부터 안 하기 위한"** 시스템이다.

회고와 헷갈리기 쉬운데 둘은 다르다.

| 구분    | 회고                 | 자산화                     |
| ----- | ------------------ | ----------------------- |
| 무엇    | 무엇이 잘 됐고 안 됐는지 정리  | 다음에 쓸 수 있게 일반화          |
| 결과물   | 회고 보고서 + 액션 아이템    | 재사용 가능한 템플릿·가이드·체크리스트   |
| 시점    | 정기·구간 종료·프로젝트 종료 시 | 회고 직후 + 사건 발생 시 + 일상적으로 |
| 끝나는 곳 | 다음에 어떻게 할지 합의      | 실제 자산이 누적된 폴더           |
|       |                    |                         |

회고에서 **"이런 가이드가 있었으면 좋았겠다"** 가 나왔다면, 자산화는 **그 가이드를 실제로 만들어 폴더에 넣는 일.**

## 언제 사용하나

- 프로젝트 종료 시 (필수)
- Phase 종료 시 (해당 Phase에서 나온 자산)
- 사후 분석(Post-mortem) 직후 (장애에서 나온 체크리스트·플레이북)
- 회고에서 자산화 항목이 식별됐을 때
- 일상 중 좋은 산출물을 만들었을 때 (즉시 자산화)
- 외부 자료(아티클·강의)를 학습했을 때 (자료 모음으로)

**기준**: "한 번 더 쓸 일이 있으면 자산화한다."

## 어떤 툴로

|툴|용도|
|---|---|
|**노션**|자산 저장소 (공통·유형별 폴더 구조 그대로)|
|Jira / 이슈 트래커|자산화 작업을 백로그 항목으로 추적|
|Git (선택)|코드성 자산 (스크립트·설정 파일)|

**팁**: 노션 메인 페이지에 **"자산화 대기 큐"** 를 두면, 회고에서 식별한 자산화 항목을 임시로 모았다가 한꺼번에 처리할 수 있다.

## 자산화 가능한 것의 종류

| 종류                  | 예시                              | 이동 위치                        |
| ------------------- | ------------------------------- | ---------------------------- |
| **양식 (Template)**   | PRD 양식, RFP 양식                  | 공통 / 유형별 > 템플릿               |
| **워크플로우 (Process)** | 인터뷰 진행 절차                       | 공통 / 유형별 > 워크플로우             |
| **체크리스트**           | 출시 체크리스트, 보안 검토 체크리스트           | 공통 / 유형별 > 템플릿               |
| **플레이북**            | 장애 대응 플레이북, 결제 사고 플레이북          | 공통 / 툴-환경                    |
| **가이드**             | Playwright 자동화 가이드, Jira 셋업 가이드 | 툴/환경                         |
| **사례 (Case)**       | 잘 만든 PRD 예시, 실패한 외주 사례          | 공통 / 유형별 > 템플릿 (예시) 또는 자료 모음 |
| **메트릭·지표**          | KPI 정의 예시, 알람 임계치 기준            | 공통 / 툴-환경                    |
| **외부 자료**           | 좋은 아티클·강의 노트                    | 자료 모음                        |

## 자산화 5단계 (큰 그림)

```
1. 식별   → "이게 자산이 될 수 있는가" 판단
2. 일반화 → 특정 프로젝트 색채를 빼고 보편화
3. 분류   → 어디에 넣을지 결정 (공통 / 유형별 / 툴-환경)
4. 저장   → 실제 폴더에 넣고 형식 정리
5. 발견성 → 다른 사람·미래의 본인이 찾을 수 있게
```

## 자산 1. AS-IS 업무 분석서

### 1단계. 식별

- 재사용 가치: 유형 4(내부 시스템) 프로젝트 매번 필요 ✅
- 기존 자산: 없음
- **판단: 진행**

### 2단계. 일반화

- "샵플링", "음수재고" → "(대상 시스템)", "(대상 업무)"
- "운영팀 김OO·박OO·이OO" → "실무자 3명"
- "월 30시간" → "(시간 절감량)"
- 추가: 작성 절차·인터뷰 가이드 링크·자주 하는 실수

### 3단계. 분류

- 유형 4(내부 시스템)에서만 쓰는가? → 사실상 그렇다 (외부 사용자 대상이면 다른 양식)
- **위치: 유형별 > 유형 4 > 템플릿**

### 4단계. 저장

- 페이지 생성: `T4_AS-IS_업무분석서_template_v1.0`
- 표준 형식 적용
- 예시 섹션에 샵플링 케이스 일부 보존 (익명화)

### 5단계. 발견성

- 유형 4 인덱스에 링크 추가
- 산출물 인덱스의 "유형 4 필수 산출물" 항목 매칭
- 출처: 샵플링 프로젝트 (2026)

## 자산 2. ROI 분석서

### 1단계. 식별

- 재사용: 유형 4 + 유형 6(컨설팅·진단)에도 쓸 수 있음
- **판단: 진행, 공통으로 둘지 유형 4로 둘지 고민 필요**

### 2단계. 일반화

- 시간 절감 계산식 일반화 (수작업 시간 × 빈도 × 인건비 단가)
- 인건비 단가는 별도 변수로 분리

### 3단계. 분류

- 유형 4에서 가장 자주 씀, 유형 6에서도 가끔
- 1년 후 유형 6에서도 쓰면 공통으로 이동하기로 결정
- **위치: 유형별 > 유형 4 > 템플릿** (잠정)

### 4단계. 저장

- 페이지 생성: `T4_ROI분석서_template_v1.0`
- 계산식을 변수화하여 다른 프로젝트에서 숫자만 바꿔 쓸 수 있게

### 5단계. 발견성

- 유형 4 인덱스에 링크
- 페이지 본문에 "ROI", "비용 편익", "절감 효과" 키워드 포함

## 자산 3. Playwright 자동화 가이드

### 1단계. 식별

- 재사용: Playwright는 다른 자동화 프로젝트에서도 쓸 도구
- **판단: 진행 (가장 가치 있는 자산)**

### 2단계. 일반화

- 샵플링 특화 부분 제거, 패턴만 추출
- 핵심 패턴: 셀렉터 추상화 (페이지 객체), 재시작 로직, 캡차 fallback, 모니터링 알람
- 사후 분석(셀렉터 변경 사건)의 교훈을 가이드에 흡수

### 3단계. 분류

- 도구 의존성 큼 → 툴/환경
- **위치: 툴/환경 > 기타 도구 > Playwright** (신규 페이지)

### 4단계. 저장

- 신규 페이지: `툴/환경 > Playwright 자동화 가이드 v1.0`
- 코드 예제 포함
- 함정·실수·해결 패턴 정리

### 5단계. 발견성

- 툴/환경 인덱스에 추가
- 유형 4 워크플로우에서 "자동화 도구 선택 시" 참고 링크
- 사후 분석 보고서에 양방향 링크

---

## 자산 4. 운영팀 인터뷰 가이드

### 1단계. 식별

- 재사용: 유형 3(서비스 개선)·유형 4(내부 시스템)·유형 6(컨설팅) 모두 사용자 인터뷰 필요
- 단, 외부 사용자 인터뷰 가이드는 별도 (B2C 등)
- **판단: 진행**

### 2단계. 일반화

- "샵플링 음수재고 작업" → "(대상 업무)"
- "운영팀" → "사내 사용자" / "실무자"
- 추가: 인터뷰 진행 절차, 노트 정리 방법

### 3단계. 분류

- 유형 3·4·6에서 모두 쓰는가? → YES
- **위치: 공통 > 공통 템플릿** (인터뷰 가이드 — 사내 사용자 편)

### 4단계. 저장

- 페이지 생성: 공통 템플릿 > 인터뷰 가이드 (사내 사용자 편) v1.0
- 외부 사용자 편은 별도 페이지로 (필요 시 추가)

### 5단계. 발견성

- 공통 템플릿 인덱스에 추가
- 유형 3·4·6 인덱스에서 양방향 링크

---

## 자산 5. 변화 관리 체크리스트

### 1단계. 식별

- 재사용: 자동화 도입 시 매번 필요
- 기존 자산: 유형 4 정의 페이지에 "변화 관리 계획" 산출물 목록만 있음, 실제 체크리스트는 없음
- **판단: 진행 (기존 산출물 항목을 실체화)**

### 2단계. 일반화

- 자동화 도입 일반에 적용 가능하게 추상화
- 항목: 영향 범위 식별 / 담당자 역할 재정의 / 교육 계획 / 저항 대응 / 도입 후 점검

### 3단계. 분류

- 유형 4에서만? → 유형 3 개선 사이클에서도 큰 변경이면 필요
- 일단 유형 4에 두고 1년 후 재검토
- **위치: 유형별 > 유형 4 > 템플릿**

### 4단계. 저장

- 페이지 생성: `T4_변화관리_체크리스트_v1.0`
- 자동화 도입 사례 (샵플링)를 예시로 포함

## 작성 팁

- **자산화는 "다음 프로젝트가 더 쉬워지게"가 목적** — 추상적 정리가 아님. 다음에 누가 봐도 바로 쓸 수 있게 만드는 게 핵심
- **즉시 자산화 vs 모아서 자산화** — 큰 자산은 즉시(가이드·플레이북), 작은 항목은 자산화 대기 큐에 모았다가 종료 회고 후 한 번에
- **일반화의 함정** — 너무 추상화하면 "결국 아무에게도 안 맞는 양식"이 됨. **예시(📌)로 구체성 복원이 필수**
- **분류 애매하면 공통에 둔다** — 1년 후 다른 유형에서 안 쓰면 유형별로 이동. 처음부터 완벽하게 분류하려고 하지 말 것
- **자산도 버전 관리** — v1.0으로 시작해서 사용하면서 v1.1, v2.0으로 발전. 변경 이력 남기기
- **자산화 안 하면 자산이 없는 것** — 회고에서 "이건 좋은 사례였다" 라고만 적고 끝나면 6개월 후 그 사례 못 찾는다
- **외부 자료도 자산** — 좋은 아티클은 링크만이 아니라 핵심 요약을 자료 모음에. 6개월 후 그 페이지 사라져도 본인 자산은 남음
- **자산화 작업 자체를 일정에 포함** — 종료 시점에 별도 작업으로 잡지 않으면 늘 뒤로 밀림. WBS에 자산화 항목을 별도로

## 자주 하는 실수

- **자산화 단계 생략** — 회고에서 "자산화하자" 결심만 하고 실제 폴더로 옮기지 않음
- **너무 추상화** — "프로젝트는 잘 정의해야 한다" 같은 일반론. 누구에게도 안 도움됨
- **너무 구체적** — 특정 프로젝트 문서를 그대로 옮겨놓음. 다음 프로젝트에서 못 씀
- **예시 누락** — 빈 양식만 두고 채워진 예시 없음. 다음 사용자가 "어떻게 채우라는 거지" 막힘
- **분류 무한 고민** — 어디에 둘지 1주일 고민하다가 자산화 자체를 포기. 일단 어디든 두고 나중에 이동
- **발견성 무시** — 폴더에 넣어두기만 함. 인덱스 갱신·키워드 없음 → 6개월 후 본인이 못 찾음
- **출처 미표기** — 어디서 나온 자산인지 안 적어둠. 나중에 맥락 확인이 안 됨
- **변경 이력 없음** — v1.0에서 멈춰있거나 무성의하게 갱신. 어느 버전이 왜 바뀌었는지 모름

## 작성 후 체크

- [ ] 자산이 일반화되었는가 (특정 프로젝트 색채 제거)
- [ ] 빈 양식(🔲)과 예시(📌)가 모두 있는가
- [ ] 분류 위치가 결정되었고 인덱스에 링크가 추가되었는가
- [ ] 출처 프로젝트와 변경 이력이 표기되었는가
- [ ] 다음 사용자가 5분 안에 찾고 쓸 수 있는 상태인가
- [ ] 회고·종료 보고서에 자산화 결과가 명시되었는가
