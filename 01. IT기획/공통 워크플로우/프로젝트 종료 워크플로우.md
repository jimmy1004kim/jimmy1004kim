## 이 문서는

프로젝트가 끝날 때 **"무엇을, 어떤 순서로, 어디까지 마무리할 것인가"** 의 표준 절차.

프로젝트는 "개발이 끝났다"고 끝나는 게 아니다. **검수·인계·회고·자산화·문서 정리**까지 마쳐야 진짜 종료다. 이 절차가 없으면 끝났는데 끝난 게 아닌 상태가 길게 이어지고, 다음 프로젝트에 자산도 못 남는다.

새 프로젝트 시작 워크플로우(공통 > 공통 워크플로우)와 한 쌍이다. 시작과 종료가 표준화되어 있어야 프로젝트가 깔끔하게 닫힌다.

## 언제 사용하나

- 프로젝트 산출물이 완성되어 종료 단계 진입 시
- 외주 프로젝트의 납품 확정 시
- 내부 시스템 도입·안정화 완료 시
- 프로젝트가 중단·취소되는 경우 (이 경우에도 종료 절차를 거쳐야 자산화·교훈이 남음)
- Phase 종료 시 (간소화 버전 적용 가능)

## 어떤 툴로

|툴|용도|
|---|---|
|**노션**|프로젝트 페이지의 종료 체크리스트, 산출물 인덱스, 회고|
|Jira / 이슈 트래커|미해결 이슈 정리, 잔여 백로그 이관|
|Slack|종료 공지, 채널 아카이브|
|외부 메일|외부 이해관계자에게 공식 종료 통보|

## 종료의 5단계 (큰 그림)

```
1. 종료 판단     → "정말 끝났는가" 확인
2. 검수·확정     → 산출물 최종 점검, 합의
3. 인계          → 운영·유지보수 측에 넘김
4. 회고·자산화   → 학습과 재사용 가치 추출
5. 공식 종료     → 통보·아카이브·채널 정리
```

각 단계에 빠뜨리면 안 되는 항목들이 있어서 체크리스트로 관리한다.

# 🔲 양식 — 프로젝트 종료 체크리스트

## 종료 메타

|---|---|
|프로젝트명||
|종료 사유|정상 종료 / 조기 종료 / 중단·취소|
|종료 결정일|YYYY-MM-DD|

## 1단계. 종료 판단

> "끝났다"의 정의가 명확한지 먼저 확인

- [ ] Charter의 성공 기준 충족 여부 확인
- [ ] 합의된 산출물 목록 대비 누락 항목 확인
- [ ] 미해결 이슈·블로커 0건 또는 인계 가능 상태
- [ ] Sponsor·의사결정자의 종료 동의
- [ ] 외부 이해관계자(고객 등)의 검수·승인 (해당 시)

**판단 기준이 모호하면 → Charter로 돌아가 성공 기준을 다시 확인**

## 2단계. 검수·확정

> 산출물이 합의된 수준으로 완성되었는지

### 산출물 점검

- [ ] 모든 산출물이 최종 버전(v1.0 이상)으로 정리됨
- [ ] 산출물 인덱스 / 진행 현황판 100% 체크
- [ ] 외부 납품 산출물 (해당 시) — 검수 기준서 대조 완료
- [ ] 검수 확인서·인계 확인서 수령 (해당 시)

### 품질 확인

- [ ] QA 체크리스트 모든 항목 통과
- [ ] 알려진 이슈 처리 또는 인계 대상으로 정리
- [ ] 보안·법무 검토 (해당 시)
- [ ] 운영 환경 안정성 확인 (서비스 프로젝트)

### 계약·정산 (외주·구축 프로젝트 한정)

- [ ] 계약상 범위 100% 이행 확인
- [ ] 변경 관리 대장의 모든 CR 처리 완료
- [ ] 최종 정산 청구 / 지급 처리

## 3단계. 인계

> 다음 책임자에게 매끄럽게 넘기기

### 운영 인계 (서비스·시스템 프로젝트)

- [ ] 운영 매뉴얼 / 사용자 가이드 작성 완료
- [ ] 인계 대상자에게 1회 이상 교육 진행
- [ ] 운영 책임자·연락처 명확화
- [ ] 모니터링·알람 셋업 완료
- [ ] 장애 대응 플레이북 작성
- [ ] 인계 확인서 서명

### 외부 인계 (외주·납품 프로젝트)

- [ ] 납품 산출물 리스트 전달
- [ ] 소스코드·계정·라이선스 인계
- [ ] 유지보수 계약 (해당 시) 발효 확인
- [ ] 사후 지원 기간·범위 합의

### 내부 인계

- [ ] 후속 프로젝트 (개선 사이클 등) 책임자 지정
- [ ] 잔여 백로그를 후속 프로젝트로 이관
- [ ] 미해결 이슈를 운영 이슈 관리로 이관

## 4단계. 회고·자산화

> 학습과 재사용 가치를 명시적으로 뽑아내기

### 회고

- [ ] 프로젝트 종료 회고 진행 (회고 템플릿 사용)
- [ ] 회고 보고서 작성·공유
- [ ] 액션 아이템에 담당자·기한 명시
- [ ] 회고 결과를 노션 회고 DB에 누적

### 자산화 (가장 중요)

- [ ] 재사용 가능한 산출물 식별
- [ ] 산출물을 공통 또는 해당 유형 템플릿으로 이동·일반화
- [ ] 새로 발견한 워크플로우·체크리스트를 자산으로 등록
- [ ] 사후 분석(Post-mortem) 발생분이 있다면 그 결과도 자산화 완료

자산화 워크플로우(공통 > 공통 워크플로우 참조)에 따라 진행.

### 케이스 스터디 (포트폴리오용)

- [ ] 케이스 스터디 페이지 작성 (커리어 > 케이스 스터디 모음)
- [ ] 정량·정성 성과 명시
- [ ] 본인의 역할·기여·학습 정리

## 5단계. 공식 종료

> 사람들에게 알리고, 환경을 정리

### 통보·공지

- [ ] Sponsor·의사결정자에게 종료 보고
- [ ] 전체 관련자에게 종료 공지 (이메일 또는 Slack)
- [ ] 외부 이해관계자 (해당 시) 종료 통보
- [ ] 사용자(서비스 프로젝트) 안내 (해당 시)

### 환경 정리

- [ ] Slack 채널 아카이브 (운영 채널은 별도 유지)
- [ ] Jira 보드 정리 (잔여 이슈 이관 후 클로즈)
- [ ] 노션 프로젝트 페이지에 "종료" 태그 부여
- [ ] 사용 도구·계정 정리 (불필요한 권한 회수)
- [ ] 임시 환경(스테이징·테스트 서버 등) 정리

### 메타데이터 갱신

- [ ] 프로젝트 페이지 상단에 종료일·최종 상태 기록
- [ ] 산출물 인덱스에 최종 버전 명시
- [ ] 명명 규칙에 따라 파일·문서 상태를 "🟢 확정"으로 갱신

- [ ] 위 5단계 체크리스트 100% 완료

## 작성 팁

- **종료 기준은 시작 시점에 정해놓는다** — Charter의 성공 기준이 곧 종료 판단 기준. 끝날 때 새로 정하면 늘 모호함
- **체크리스트 형태로 운영** — 종료는 빠뜨리기 쉬워서 명시적 체크리스트가 필요. 머리로 기억하지 말 것
- **인계 없이는 종료도 없다** — 만든 사람만 아는 시스템은 종료된 게 아님. 인계 확인서까지 받아야 종료
- **자산화는 종료의 핵심** — 회고만 하고 자산화 안 하면 다음 프로젝트가 처음부터 다시 시작
- **중단·취소도 정식 종료 절차를 거친다** — 중단된 프로젝트에서도 자산·교훈이 나옴. 그냥 흐지부지 끝내면 학습 0
- **Phase 종료에도 간소화 버전 적용** — Phase 회고 + 자산화 + 다음 Phase 준비 정도로 줄여서 매 Phase마다 적용
- **종료 공지에 정량 성과 포함** — "감사합니다" 인사만 보내지 말고 무엇이 어떻게 좋아졌는지 숫자로 알릴 것 — 본부장이 다음 자동화 예산 승인할 때 근거가 됨
- **종료 회고 ≠ 종료 보고** — 회고는 솔직한 학습용 (내부), 종료 보고는 성과 강조 (대외용). 둘을 분리

## 자주 하는 실수

- **종료 기준 모호** — "대충 됐으니 끝내자"로 끝나면 다음에 또 호출됨
- **인계 누락** — 만든 사람이 계속 호출되는 상태가 됨. 1년 후에도 호출됨
- **자산화 누락** — 좋은 산출물·기법을 프로젝트 폴더 안에만 묻어둠. 다음에 또 처음부터
- **회고 생략** — 잘 끝났다고 회고 안 하면 다음 프로젝트도 똑같이 진행 → 같은 문제 반복
- **공식 종료 없이 흐지부지** — Slack 채널은 아카이브 안 되고, Jira 보드 살아있고, 사람들이 가끔 호출하고 → 영원히 안 끝남
- **중단·취소를 정식 절차 없이 묻어둠** — "이건 실패라서 회고할 거 없음" → 가장 비싼 교훈을 그냥 버림
- **종료 공지를 안 함** — 관련자들이 "그 프로젝트 어떻게 됐어?"를 계속 물어봄
